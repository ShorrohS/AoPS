Module 8.5 — TLS/SSL: Securing the Transport

Type A — Chapter Hero FIG 8.5-A TLS 1.3 Handshake — 1-RTT Connection with Forward Secrecy
TLS 1.3 handshake — the mechanism behind HTTPS. After the TCP 3-way handshake, the client sends its Diffie-Hellman public key in ClientHello. The server responds with its own DH public key, its X.509 certificate, a signature proving it holds the private key, and a Finished HMAC. Both sides now derive an identical session key from the DH exchange without ever transmitting it — a man in the middle sees only public keys, from which deriving the session key is computationally infeasible. The client verifies the certificate chain and sends its own Finished HMAC. All subsequent HTTP data is encrypted with AES-256-GCM. Forward secrecy ensures that even if the server's private key is later compromised, past sessions (recorded by an attacker) cannot be decrypted.
Type B — Concept Diagram FIG 8.5-B Certificate Chain — Root CA, Intermediate CA, Leaf Certificate
X.509 certificate chain of trust. Root CAs are the anchors: ~150 of them are pre-installed in every operating system and browser trust store, and their private keys are kept offline in Hardware Security Modules. Root CAs sign Intermediate CAs, which are kept online and issue leaf certificates to websites. This two-level structure limits blast radius: if an intermediate CA is compromised, only certificates it issued are affected — the root remains secure. The leaf certificate contains the domain's public key, the allowed hostnames (SANs), validity period (90 days for Let's Encrypt), and the intermediate CA's signature. When you connect to example.com over HTTPS, your browser verifies the entire chain: leaf → intermediate → root, ensuring the certificate was issued by a trusted authority.
Type E — Comparison FIG 8.5-C TLS Encryption Roles — Asymmetric for Key Exchange, Symmetric for Data
TLS uses asymmetric and symmetric cryptography for complementary purposes. Asymmetric cryptography (RSA, ECDSA, ECDH) solves the key distribution problem — two parties can establish a shared secret over a public channel without ever transmitting the secret. But asymmetric operations are 1000× slower than symmetric ones. Symmetric cryptography (AES-256-GCM) is fast enough for bulk data — modern CPUs include AES-NI hardware instructions, enabling 10+ Gbps encrypted throughput. TLS therefore uses asymmetric crypto only in the handshake (to authenticate the server and derive the session key), then switches to symmetric AES-GCM for all application data. The session key exists only for the duration of the connection and is never stored — this is forward secrecy.
