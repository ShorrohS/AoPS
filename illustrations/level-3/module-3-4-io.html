Type A — Chapter Hero FIG 3.4-A Memory-Mapped I/O — Peripherals as Memory Addresses
Memory-mapped I/O maps peripheral hardware registers into the CPU's address space alongside RAM. Addresses 0x0000–0x7FFF are normal RAM. Addresses 0x8000–0x8005 map to hardware registers: reading 0x8000 returns the last keypress; writing to 0x8002 sets a display pixel. The CPU uses the exact same MOV instructions for both — no special I/O instructions needed. The memory controller routes the access to the appropriate hardware based on the address range. This is how virtually all modern embedded and desktop systems handle peripherals.
Type E — Comparison FIG 3.4-B Polling vs Interrupts — Two Ways to Handle I/O Events
Polling vs interrupt-driven I/O. Polling (left): the CPU checks a status register on every loop iteration, wasting cycles even when no input is available. Suitable only for very simple embedded systems where the CPU has nothing better to do. Interrupts (right): the peripheral asserts an IRQ (Interrupt Request) line when it has data. The CPU hardware pauses the current instruction stream, saves state on the stack, and jumps to the Interrupt Service Routine (ISR). After the ISR completes, execution resumes exactly where it was interrupted. Modern OSs handle keyboard, network, disk, and timer events exclusively via interrupts — polling would waste 99.9% of CPU cycles.
Type E — Comparison FIG 3.4-C Polling vs Interrupts — CPU Utilisation Under I/O Wait
CPU timeline comparison between polling and interrupt-driven I/O. With polling, the CPU repeatedly checks a status register — burning cycles even when the device has nothing to report. With interrupts, the CPU runs uninterrupted until the I/O controller raises a hardware signal (IRQ), triggering the Interrupt Service Routine (ISR). After the ISR completes, the CPU resumes exactly where it left off. Modern operating systems use interrupts for virtually all I/O: keyboards, network cards, disk controllers, and timers all signal the CPU rather than requiring it to ask.
