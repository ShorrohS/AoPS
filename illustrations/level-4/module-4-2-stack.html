Module 4.2 — The Stack and Calling Conventions

Type A — Chapter Hero FIG 4.2-A Stack Frames — main() calling add(5, 3)
Stack frame layout for main() calling add(5, 3). The stack grows downward (high addresses at top). main's frame contains its locals (x=5, y=3, r). When main calls add, the CALL instruction pushes the return address onto the stack. add's prologue saves main's RBP and establishes a new stack frame pointer. Parameters a=5 and b=3 are passed in registers (x86-64 System V ABI) but the stack also shows their spilled copies. add's epilogue restores RBP and SP, then RET pops the return address back into RIP, resuming execution in main. This precise bookkeeping is how recursion, exception handling, and debuggers all work.
Type C — Architecture Diagram FIG 4.2-B Stack Frame Layout During Nested Function Calls
The call stack during nested function calls main() → foo(3) → bar(7). Each function call pushes a new stack frame containing the return address, saved registers, parameters, and local variables. RSP (Stack Pointer) always points to the top of the stack; RBP (Base Pointer) anchors each frame, allowing variables to be accessed via fixed offsets from RBP. When bar() returns, its frame is destroyed and RSP moves back up — restoring the exact execution state of foo() at the call site. The same mechanism underlies exceptions, coroutines, and stack traces in every debugger.
Type D — Simulation Figure FIG 4.2-C push / pop Mechanics — How the Stack Pointer Moves
push and pop mechanics. push rax: RSP decrements by 8 (one 64-bit word), then the value of RAX is written to the new top of stack. pop rcx: the value at the current RSP is read into RCX, then RSP increments by 8. The stack grows towards lower addresses on x86-64. This LIFO structure means function parameters and return addresses are naturally cleaned up in reverse order — the last function called is the first to return.
