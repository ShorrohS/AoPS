Type A — Chapter Hero FIG 4.5-A Inodes and Directory Trees — How Files Are Named and Located
Filesystem structure on Linux ext4. The directory tree (left) stores name-to-inode mappings only — the file name "hello.txt" exists only in the directory alice/. The inode (centre, inode 203) stores all file metadata: permissions, owner, timestamps, size, and an array of disk block pointers. The first direct block pointer (block[0] = 7821) points to the 4KB disk block that contains the actual file data "Hello, World!\n" (13 bytes). The critical insight: the file name and the file data are completely separate. This enables hard links (multiple names pointing to the same inode) and explains why renaming a file within the same filesystem is instant (just changes the directory entry, the inode is untouched).
Type B — Concept Diagram FIG 4.5-B Inode Structure — Separating File Metadata from File Data
The inode architecture used by ext4, XFS, and most Unix file systems. A directory entry maps a filename to an inode number. The inode stores all metadata (permissions, timestamps, size, owner) and a set of block pointers: 12 direct pointers for small files, and an indirect pointer (pointing to a block full of more pointers) for larger ones. Critically, the filename is not stored in the inode — it lives only in the directory. This enables hard links: multiple directory entries pointing to the same inode. The file persists on disk until its link count reaches zero, at which point the OS frees its data blocks.
Type C — Process Diagram FIG 4.5-C Path Resolution — Walking /home/user/hello.txt from the Root
Path resolution in a Unix file system. Opening /home/user/hello.txt requires the kernel to walk each path component: read the root inode (#2) to find "home"→#100, read inode #100 to find "user"→#450, read inode #450 to find "hello.txt"→#4821, read inode #4821 to get block pointers, then finally read the data block. This is a minimum of 4 inode accesses before any file content is transferred. The kernel's directory cache (dcache) keeps recently resolved path components in memory, reducing this cost to near zero for hot paths — but cold path performance explains why deep directory hierarchies can be slower on filesystem-heavy workloads.
