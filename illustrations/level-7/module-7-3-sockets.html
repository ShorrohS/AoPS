Type A — Chapter Hero FIG 7.3-A TCP Socket Lifecycle — Server bind/listen/accept, Client connect
TCP socket lifecycle showing the exact sequence of system calls on both sides. The server creates a socket, binds to a port, marks it as listening, then blocks on accept() waiting for a client. When the client calls connect(), the OS performs the TCP three-way handshake (SYN → SYN-ACK → ACK) and accept() returns a new connected socket file descriptor. Both sides then exchange data via send()/recv() — these are just file I/O operations on the socket fd. Both sides call close() when finished, which triggers a TCP FIN exchange (four-way teardown). Every socket is a file descriptor — it can be passed between processes, selected with select()/poll(), or used with epoll for non-blocking I/O.
Type E — Comparison FIG 7.3-B TCP vs UDP — Reliability, Ordering, and Overhead Trade-offs
TCP and UDP trade reliability for efficiency. TCP guarantees delivery, ordering, and flow control through sequence numbers, acknowledgements, and retransmission — at the cost of a 3-way handshake on every connection, per-packet ACKs, and a 20-byte minimum header. UDP sends datagrams independently with an 8-byte header and no handshake — packets may arrive out of order, be duplicated, or be dropped silently. DNS uses UDP because its queries fit in one small packet and the application can retry if needed. Video streaming uses UDP because a retransmitted old frame would arrive too late to display. HTTP/3 runs over QUIC, which implements reliability and congestion control inside UDP packets — combining UDP's low latency with TCP's reliability at the application layer.
Type D — Process Diagram FIG 7.3-C Client-Server Data Flow — HTTP Request over TCP Socket
End-to-end HTTP GET request traced at the socket system call level. The 3-way TCP handshake (SYN/SYN-ACK/ACK) establishes the connection before any data is exchanged — this alone adds one full network round-trip latency. The HTTP request is sent via send() as raw bytes in the TCP stream. The server's recv() returns those bytes, parses the HTTP request, and uses send() to write the response. Connection teardown requires a FIN/FIN-ACK exchange. HTTP/1.1 persistent connections reuse the TCP connection for multiple requests, amortising the handshake cost. HTTP/2 multiplexes multiple requests over one connection. Understanding this trace is essential for debugging network latency and optimising server performance.
