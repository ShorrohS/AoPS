Type A — Chapter Hero FIG 7-A Threads vs Processes — Shared vs Isolated Memory
Processes vs threads. Two separate processes (left) each have completely private virtual address spaces — they cannot read or write each other's memory. Communication requires explicit IPC mechanisms (pipes, sockets, shared memory via mmap). Threads within one process (right) share the heap, code segment, global variables, and open file descriptors, but each thread has its own stack and register state. This sharing makes threads faster to create and communicate with, but it introduces the need for synchronisation primitives (mutexes, semaphores) to prevent race conditions.
Type C — Concept Diagram FIG 7-B Deadlock — The Four Coffman Conditions
Deadlock occurs when Thread A holds mutex1 and waits for mutex2, while Thread B holds mutex2 and waits for mutex1 — a circular dependency with no exit. Deadlock requires all four Coffman conditions simultaneously: mutual exclusion (only one holder), hold-and-wait (holding while waiting), no preemption (cannot be forced to release), and circular wait. Prevention strategy: impose a global lock ordering (always acquire mutex1 before mutex2) — this breaks the circular wait condition. Other strategies: trylock with timeout (breaks no-preemption), or lock-free data structures (breaks mutual exclusion).
Type D — Process Diagram FIG 7-C TCP Socket Communication — Server and Client Handshake
TCP socket client-server communication. The server creates a socket, binds to port 8080, and blocks on accept() waiting for connections. The client creates a socket and calls connect(), which triggers the TCP 3-way handshake (SYN → SYN-ACK → ACK). Once connected, the client sends a request and the server processes it and sends a response. Sockets use the same read/write/close API as file descriptors — everything is a file in Unix. Blocking calls (accept, recv) are typically paired with threads or non-blocking I/O (select/epoll) in production servers.
