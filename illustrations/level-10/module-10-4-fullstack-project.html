Module 10.4 — Full-Stack Architecture
3 figures · Three-Tier Architecture · Request Lifecycle · Authentication Flow
Type A — Chapter Hero FIG 10.4-A Three-Tier Architecture — Client, Application Server, Database
Three-tier architecture — the dominant pattern for web applications. The Client tier (browser, mobile app) only renders UI and makes HTTP requests; it never has direct database access. The Application Server tier handles all business logic — authentication, validation, business rules, database queries — and exposes a clean REST or GraphQL API. The Data tier persists state. This separation enables each tier to scale independently: add more app servers behind a load balancer without changing the client or database. It also enforces security: the client cannot bypass business logic to make direct database queries, and the database is not exposed to the public internet. An application server crash doesn't lose data; a database crash doesn't affect the app server's availability for cached responses.
Type C — Process Diagram FIG 10.4-B Full-Stack Request Lifecycle — Browser to CDN to Load Balancer to App to DB
Production request lifecycle for a scaled web application. The browser's request first hits a CDN — for static assets (JS, CSS, images) the CDN responds from edge cache in ~5ms. Dynamic API requests pass through a load balancer that distributes across stateless app server replicas (round-robin or least-connections). Each app server checks Redis for a cached result (~1ms) before querying the primary database. Read-heavy queries may hit a read replica to scale reads independently. The 80/20 rule of web performance: 80% of requests are static assets served by CDN; optimising CDN cache-hit rate has more impact than database tuning.
Type E — Comparison FIG 10.4-C Authentication — Session Cookies vs JWT Tokens
Two approaches to stateful authentication in stateless HTTP. Session cookies store an opaque ID in the client cookie jar; the server looks up the session record on every request. Simple and revocable (delete the session from the store to log out any session), but requires a shared session store accessible to all app server replicas. JWT (JSON Web Token) embeds the user's identity and claims in a cryptographically signed token — any server that knows the signing key can verify it without a database lookup. This scales horizontally without a shared store but makes revocation hard: a valid JWT remains valid until its expiry time regardless of logout. The industry pattern: short-lived JWT access tokens (15 minutes) plus long-lived refresh tokens stored server-side (supporting revocation). OAuth 2.0 uses this pattern for third-party authentication (Sign in with Google).
