Module 10.1 — HTML, CSS, and JavaScript
3 figures · Web Technology Stack · CSS Box Model · JavaScript Event Loop
Type A — Chapter Hero FIG 10.1-A Web Technology Stack — HTML Structure, CSS Presentation, JavaScript Behaviour
The web's three-layer architecture. HTML (HyperText Markup Language) defines structure and semantic meaning — an h1 is a top-level heading, a nav is navigation, a button is interactive. CSS (Cascading Style Sheets) separates visual presentation from structure — changing the button colour requires only CSS changes. JavaScript adds dynamic behaviour — responding to user events, fetching data from APIs, updating the DOM without page reloads. This separation of concerns (SoC) means a screen reader can navigate HTML semantics without CSS, and a designer can restyle the page without touching HTML. Progressive enhancement: the page works with only HTML, looks better with CSS, and becomes interactive with JavaScript.
Type B — Concept Diagram FIG 10.1-B CSS Box Model — Content, Padding, Border, Margin
The CSS box model — every HTML element is rendered as a rectangular box with four layers. Content holds the actual text and images. Padding adds transparent space between content and border. Border is the element's visible edge. Margin is transparent space between elements. The box-sizing property controls what "width" means: content-box (default) makes width apply only to content — a 200px element with 24px padding and 2px border is actually 252px wide. border-box makes width include padding and border — a 200px element stays 200px regardless of padding. The industry standard reset * { box-sizing: border-box } applies border-box universally, eliminating the mental arithmetic of content-box layout.
Type C — Architecture Diagram FIG 10.1-C JavaScript Event Loop — Call Stack, Task Queue, Microtask Queue
JavaScript's event loop enables non-blocking I/O on a single thread. When fetch() is called, the HTTP request is handed to the browser's C++ networking layer — the JS thread continues executing. When the response arrives, the callback enters the Task Queue. The event loop checks: if the call stack is empty, drain the Microtask Queue (Promise .then chains), then take one task from the Task Queue and push it onto the stack. This ordering explains why Promise callbacks run before setTimeout callbacks — microtasks are always drained before the next task. setTimeout(fn, 0) doesn't mean "immediately" — it means "at least 0ms later, after the current task and all microtasks complete". This model prevents blocking the UI thread with I/O while maintaining single-threaded simplicity.
