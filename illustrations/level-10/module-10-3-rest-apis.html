Type A — Chapter Hero FIG 10.3-A REST Resource Model — URLs as Nouns, HTTP Methods as Verbs
REST (Representational State Transfer) architectural style. URLs name resources (nouns: /users, /users/42), and HTTP methods specify the action (verbs: GET, POST, PUT, PATCH, DELETE). This clean separation makes APIs predictable and self-documenting. GET is idempotent and safe (no side effects). PUT is idempotent but modifying. POST creates and is neither idempotent nor safe. DELETE is idempotent. Statelessness is the critical constraint: each request must contain all information needed to process it — the server holds no client session state. This enables horizontal scaling (any server can handle any request) and caching (GET responses are cacheable by URL).
Type B — Reference Diagram FIG 10.3-B JSON Data Format — Types, Structure, and API Response Anatomy
JSON (JavaScript Object Notation) is the dominant API data format — lightweight, human-readable, and supported natively in every modern language. Six value types: string (always double-quoted), number (integer or float), boolean, null, object ({} key-value pairs), and array ([] ordered list). JSON has no comments, no functions, no undefined. Typical REST API responses wrap the payload in an envelope: a status field (numeric or string), a data field (the actual resource), and meta (pagination info, request ID for tracing). ISO 8601 timestamps ("2024-01-15T10:30:00Z") are the universal standard for date serialisation — never use Unix timestamps in JSON APIs without documentation.
Type D — Reference Table FIG 10.3-C HTTP Status Codes — The Full Reference for REST API Design
HTTP status codes — the standard language of REST API responses. 2xx indicates success. 3xx signals a redirect — the client should request a different URL. 4xx signals client error: the request was wrong, not authorised, or targeted a non-existent resource. 5xx signals server error — the request was valid but the server failed to process it. The critical design rule: never return HTTP 200 with an error message in the body ("200 OK: error: not found") — this breaks every monitoring tool, logging system, and client library that depends on status codes. 401 (Unauthorized) means "not authenticated yet"; 403 (Forbidden) means "authenticated but not allowed" — conflating them breaks client retry logic.
