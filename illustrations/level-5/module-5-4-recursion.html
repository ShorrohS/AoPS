Type A — Chapter Hero FIG 5.4-A Recursive Call Tree — factorial(5) Unrolled
Recursive call tree for factorial(5). The function descends through 6 levels of calls, each generating a new stack frame. The base case (factorial(0) = 1) terminates the descent. The return phase propagates back up: 1 × 1 = 1 → 2 × 1 = 2 → 3 × 2 = 6 → 4 × 6 = 24 → 5 × 24 = 120. Every recursive algorithm has this two-phase structure: a descent phase that reduces the problem, and an ascent phase that combines sub-results. The depth of recursion determines stack space consumption — factorial(5) uses 6 frames, factorial(10000) would use 10001.
Type E — Comparison FIG 5.4-B Fibonacci: Naive Recursion vs Memoisation — Eliminating Redundant Work
Naive recursive Fibonacci (left) recomputes overlapping subproblems: fib(3) is called twice, fib(2) three times, for a total of 15 calls to compute fib(5). For fib(50) the naive approach makes approximately 2⁵⁰ ≈ 10¹⁵ calls — infeasible. Memoisation (right) stores each result in a dictionary on first computation and returns the cached value on subsequent lookups. fib(5) with memoisation makes exactly 5 unique calls — O(n). This insight — that recursive problems with overlapping subproblems can be solved in polynomial time by storing sub-results — is the core idea of dynamic programming.
Type D — Simulation Figure FIG 5.4-C Tail Recursion — When the Compiler Can Eliminate Stack Frames
Tail recursion places the recursive call as the absolute last operation, with no work remaining for the caller after the recursive call returns. A compiler can recognise this and reuse the same stack frame instead of pushing a new one — Tail Call Optimisation (TCO). Regular factorial must keep its frame alive to perform the final multiplication; tail-recursive factorial with an accumulator parameter has no such obligation. Languages with mandatory TCO (Scheme, Haskell) can recurse indefinitely without stack overflow. Python deliberately does not implement TCO to preserve readable tracebacks.
