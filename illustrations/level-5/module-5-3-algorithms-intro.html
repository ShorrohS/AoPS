Type A — Chapter Hero FIG 5.3-A Big-O Growth Curves — How Different Complexities Scale
Big-O growth curves showing seven complexity classes. O(1) is constant — runtime does not depend on input size at all (array index lookup). O(log n) barely grows (binary search). O(n) grows linearly (linear scan). O(n log n) is the best possible for comparison-based sorting (merge sort, heap sort). O(n²) grows quickly (bubble sort, nested loops). O(2ⁿ) and O(n!) are computationally infeasible beyond tiny inputs — an O(2ⁿ) algorithm processing n=100 items would require more operations than atoms in the observable universe.
Type E — Comparison FIG 5.3-B Linear Search vs Binary Search — The Algorithmic Advantage
Linear search versus binary search finding value 73 in a sorted 16-element array. Linear search checks every element left to right — finding 73 at index 11 requires 12 comparisons, and the worst case is 16. Binary search exploits the sorted order: compare the middle element (61 at index 7), determine which half contains the target, repeat. Found in 2 comparisons. For a 1-million-element array, linear search may require 1,000,000 checks; binary search needs at most 20 (log₂ 1,000,000 ≈ 20). The right algorithm dominates hardware speed.
Type D — Reference Table FIG 5.3-C Algorithm Complexity Reference — Real Operation Counts at Scale
Concrete operation counts for seven complexity classes across four input sizes. The table makes the abstract growth rates visceral: an O(n log n) algorithm handles a million inputs in ~20 million operations — fine for a modern processor. An O(n²) algorithm requires a trillion — still possible but slow. An O(2ⁿ) algorithm on 100 inputs requires 10³⁰ operations — physically impossible on any computer that could ever be built. Algorithm selection is not an optimisation — it is the difference between a program that finishes and one that never will.
