Type A — Chapter Hero FIG 5.2-A Interpreted vs Compiled — Two Paths from Source to Execution
Compiled vs interpreted execution models. C (top): source compiles directly to native CPU instructions — the CPU executes them directly at hardware speed. Python (bottom): source compiles to platform-independent bytecode, which a Python Virtual Machine (CPython) interprets one opcode at a time. Each Python bytecode LOAD_CONST or BINARY_ADD triggers a C function call inside the VM, adding overhead. Python's 50–100× slowdown versus C comes from this interpretation loop plus the dynamic type-checking overhead on every operation. JIT compilers (PyPy) watch which bytecode loops run frequently and compile them to native code at runtime, recovering much of the speed gap.
Type C — Concept Diagram FIG 5.2-B Python Object Model — Everything Is an Object
Python's uniform object model. Every value in Python — integers, strings, lists, functions, even types — is a PyObject structure on the heap containing a type pointer, a reference count, and the value. When you write b = a, Python does not copy the integer 42; it increments the reference count on the existing integer object and makes b point to it. When a variable goes out of scope or is reassigned, the reference count decrements. When it hits zero, the memory is freed immediately (reference counting garbage collection). Cyclic collector handles the edge case of objects that reference each other in a cycle. This model explains why Python variables behave differently from C variables in assignments and why mutating a list through one reference affects all references to it.
