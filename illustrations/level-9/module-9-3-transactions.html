Type A — Chapter Hero FIG 9.3-A ACID Properties — Four Guarantees Every Transaction Must Satisfy
ACID properties illustrated with a bank transfer (debit account A, credit account B). Atomicity ensures both operations succeed or both are rolled back — no money disappears or is created. Consistency enforces business rules: balance cannot go negative. Isolation ensures Transaction 2 cannot read the intermediate state where A is debited but B isn't yet credited — it sees either the before or after state, never the in-between. Durability means that once the database confirms COMMIT, the transfer is permanent even if the server crashes one millisecond later. These four properties are what distinguish a database from a file system.
Type B — Reference Table FIG 9.3-B SQL Isolation Levels — Anomalies Permitted at Each Level
SQL isolation levels define which read anomalies are permitted in exchange for concurrency. Dirty reads: reading uncommitted data that may be rolled back. Non-repeatable reads: the same row returns a different value on two reads within one transaction (because another transaction committed between reads). Phantom reads: a range query returns different rows on re-execution (because another transaction inserted/deleted rows matching the range). Higher isolation requires more locking or MVCC snapshot management, reducing concurrency. PostgreSQL implements all levels via MVCC (each transaction sees a snapshot of committed data at transaction start), making REPEATABLE READ and SERIALIZABLE available with lower overhead than traditional locking.
Type C — Process Diagram FIG 9.3-C Write-Ahead Log (WAL) — Crash Recovery with Before/After Images
Write-Ahead Logging (WAL) implements both Durability and Atomicity. The rule: before modifying any data page, write the change to the WAL log file and fsync it to disk. Only then modify the in-memory buffer pool. When COMMIT is called, the WAL record for that transaction is fsynced — the application receives confirmation. Actual data pages are written to disk later in bulk (checkpointing). On crash: the ARIES recovery algorithm reads the WAL, replays all changes from the last checkpoint (redo phase), then rolls back any transactions that hadn't committed (undo phase). Committed transactions are always recoverable because their WAL records are on disk; uncommitted transactions are cleanly reversed. This is why PostgreSQL's WAL directory and MySQL's redo log are so critical to backup procedures.
