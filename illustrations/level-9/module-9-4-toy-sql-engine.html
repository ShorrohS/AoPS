Type A — Chapter Hero FIG 9.4-A SQL Parsing Pipeline — From Text to Execution Plan
SQL engine pipeline from text string to result rows. The lexer tokenises the SQL string into keywords, identifiers, operators, and literals. The parser uses a grammar to build an Abstract Syntax Tree (AST) representing the query structure. The analyser resolves names — "age" becomes "users.age" by checking the schema catalog. The planner generates a logical plan (abstract operations). The optimiser rewrites the plan to use indexes and optimal join ordering based on table statistics. The executor evaluates the physical plan using the Volcano iterator model, streaming rows from leaf operators (index scan) through intermediate operators (filter, sort) to the client. A toy SQL engine implementing this pipeline in ~500 lines of Python teaches more about databases than any number of SQL tutorials.
Type C — Architecture Diagram FIG 9.4-B Volcano Execution Model — Iterator Chain Pull Model
The Volcano (iterator) execution model — the architecture used by PostgreSQL, SQLite, MySQL, and most SQL databases. Each physical operator implements three methods: open() initialises the operator and opens its children, next() returns the next output row (or EOF), and close() releases resources. The query tree is evaluated lazily: the client calls Sort.next(), which calls Filter.next(), which calls SeqScan.next(). Rows flow upward from leaves (data sources) to the root (output). This pull-based model is elegant and composable — adding a new operator requires implementing just three methods. Modern databases add batching (vectorised execution, returning 1024 rows per next() call) and compilation (JIT-compiling the operator pipeline) for performance.
Type D — Concept Diagram FIG 9.4-C Query Optimisation — Predicate Pushdown and Join Reordering
Predicate pushdown — the single most impactful query optimisation. A naive execution plan joins users and orders first (producing up to 5 million joined rows), then applies the WHERE age > 25 filter. The optimiser recognises that the filter only references columns from the users table and can be pushed below the join: first filter users down to ~50,000 rows (age > 25), then join only those 50,000 rows with orders. This reduces the input to the join by 20×, making the overall query ~100× faster. Query optimisers apply dozens of such algebraic rewriting rules (predicate pushdown, join reordering, subquery flattening, constant folding) automatically — the reason declarative SQL ("what you want") outperforms hand-written imperative code for complex queries.
