Type A — Chapter Hero FIG 9.2-A B-Tree Structure — Why Databases Use Fan-Out Trees, Not Binary Search Trees
B-Tree structure optimised for disk-based storage. Unlike a binary search tree (fan-out = 2), a B-Tree node is sized to fill exactly one disk page (typically 8–16 KB). A page can hold hundreds of keys, giving a fan-out of 100–500. With fan-out 200 and height 3, a B-Tree indexes 200³ = 8 million rows with at most 3 disk reads. A binary search tree with 8 million entries has height log₂(8M) ≈ 23 — 23 disk reads at ~5ms each = 115ms per lookup. The B-Tree version: 15ms. Leaf nodes in B+-Trees (the variant used by PostgreSQL, MySQL, and most databases) store the actual row pointers and are doubly-linked for efficient range scans (SELECT WHERE id BETWEEN 40 AND 70 traverses leaf nodes directly).
Type C — Process Diagram FIG 9.2-B B-Tree Search — Finding Key 55 in 3 Disk Reads
B-Tree search for key 55 traced through three disk reads. At the root, 30 < 55 < 70 directs the search to the middle child pointer. That internal page (40 | 60) confirms 40 < 55 < 60, following the middle pointer again. The leaf page contains [50, 55, 58] — key 55 found with its row pointer (heap file offset). A fourth read fetches the actual row data from the heap file. For 1,000,000 rows with fan-out 200, the tree has height 3 — at most 3 page reads regardless of which key is searched. Without the index, a sequential scan reads all ~125,000 pages (1M × 8 bytes ÷ 8KB per page). The index is why SELECT WHERE id = 42 runs in milliseconds on a billion-row table.
Type E — Comparison FIG 9.2-C Clustered vs Non-Clustered Index — Physical Row Ordering
Clustered vs non-clustered indexes. A clustered index physically orders the table data in B-Tree key order — the leaf nodes contain the actual row data, eliminating a separate heap read. MySQL InnoDB automatically clusters all tables on the primary key. Because data has one physical ordering, only one clustered index is possible per table. Non-clustered (secondary) indexes maintain a separate B-Tree whose leaves contain key values plus row pointers (heap addresses). Looking up by email requires: index B-Tree traversal (3 reads) + one heap read per matched row. If matched rows are scattered across different heap pages, each requires a separate random I/O — this "index lookup amplification" is why secondary indexes can actually be slower than sequential scans for low-selectivity queries.
