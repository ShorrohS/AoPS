Type A — Chapter Hero FIG 9.1-A Relational Model — Tables, Keys, and Foreign Key Relationships
The relational model organises data into tables (relations) where each row (tuple) represents one entity and each column (attribute) holds a typed value. The primary key uniquely identifies each row and cannot be NULL. A foreign key is a column whose value must exist as a primary key in another table — this enforces referential integrity: you cannot create an order for a user that doesn't exist, and you cannot delete a user who has orders (without cascading). The relational model was proposed by E.F. Codd in 1970 and remains the dominant data model for transactional systems 50+ years later because its mathematical foundation (set theory and first-order logic) enables powerful, declarative querying via SQL.
Type B — Reference Diagram FIG 9.1-B SQL JOIN Types — INNER, LEFT, RIGHT, FULL OUTER
SQL JOIN types visualised as Venn diagrams. INNER JOIN returns only rows where the join condition matches in both tables — user Dave (no orders) is excluded. LEFT JOIN returns all rows from the left table (users) and matching rows from the right (orders); unmatched rows get NULL in the order columns — Dave appears with NULL order columns. RIGHT JOIN mirrors LEFT JOIN (rarely used in practice — rewrite as LEFT JOIN with tables swapped). FULL OUTER JOIN returns all rows from both tables with NULLs filling gaps. The LEFT JOIN is the most practically important: it answers "show me all X and any matching Y" — essential for reports that must include entities with no related records.
Type D — Process Diagram FIG 9.1-C SQL Query Execution Plan — SELECT with WHERE, JOIN, ORDER BY
SQL query execution pipeline. The parser converts SQL text into an Abstract Syntax Tree. The planner generates possible execution plans (which indexes to use, which join algorithm). The optimiser uses table statistics (row counts, value distributions) to estimate the cost of each plan and select the cheapest. Execution: scan or index-lookup to find matching rows, apply the WHERE filter, perform the join (hash join, nested-loop, or merge join), aggregate with GROUP BY, sort with ORDER BY. EXPLAIN ANALYZE reveals the actual execution plan and real row counts — the essential tool for identifying slow queries. An index on orders.date and orders.user_id can eliminate sequential scans entirely for this query.
