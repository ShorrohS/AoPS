Type A — Chapter Hero FIG 9-A Relational Model — Tables, Keys, and JOIN Operations
Relational model: two tables with a foreign key relationship. users.id (primary key, red) is referenced by orders.user_id (foreign key, green). The INNER JOIN operation matches rows where the foreign key equals the primary key, producing a combined result set. Dave (user_id=4) has no matching orders, so he is excluded from the INNER JOIN result — a LEFT JOIN would include him with NULL order fields. The relational model's power is that any question expressible as a set operation can be answered with SQL without knowing how the data is physically stored.
Type C — Concept Diagram FIG 9-B B-tree Index — Why Databases Use B-trees Instead of BSTs
B-tree index (order 3 shown). Unlike a binary search tree, each B-tree node can hold multiple keys and have multiple children. This high branching factor keeps the tree very shallow — a real database B-tree with branching factor 200 can hold 200³ = 8 million keys in just 3 levels. All leaves are at the same depth, guaranteeing O(log n) worst case. B+ trees (the variant used by MySQL InnoDB, PostgreSQL) keep all data in leaf nodes and link leaves together in a sorted linked list — making range queries (WHERE age BETWEEN 20 AND 30) efficient because they only need to find the start node and scan forward.
