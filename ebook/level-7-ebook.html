﻿# Module 7.1 — Multithreading and Concurrency

The Problem

A web server must handle 10,000 simultaneous connections. A video game must update physics, render frames, and play audio simultaneously. A data pipeline must download, process, and store data in parallel.

A single-threaded program does one thing at a time. The world does not.

Concurrency is about dealing with multiple things happening at the same time. Parallelism is about doing multiple things at the same time. They are related but distinct — and confusing them leads to bugs that are nearly impossible to reproduce.

The Story

From Sequential to Concurrent

The earliest computers were strictly sequential: one program ran, finished, then the next ran. Time-sharing (Module 4.3) created the illusion of concurrency by rapidly context-switching between processes.

Threads (1960s–70s) took this further: lightweight "processes" sharing the same address space. Switching between threads in the same process is cheaper than between processes (no address space switch). Threads share heap memory, file descriptors, and global variables — enabling communication at the cost of coordination complexity.

Dijkstra formalised many of the synchronisation problems in the 1960s: the mutual exclusion problem (1965), semaphores (1965), the dining philosophers problem (1965). These problems, posed 60 years ago, are still the foundational examples taught in every operating systems course.

Intel's Hyper-Threading (2002) put two logical CPU cores on one physical core, enabling true thread-level parallelism within a single chip. Modern CPUs have 8–32 physical cores, each with hardware multithreading. Writing correct parallel code became a survival skill for systems programmers.

The Concept

Processes vs Threads

Property Process Thread
Address space Own (isolated) Shared with other threads
Memory Own heap, stack, data Own stack; shared heap, data
Communication IPC (pipes, sockets, shared mem) Direct memory access
Context switch cost High (TLB flush, page table switch) Low (same address space)
Failure isolation Crash doesn't affect others Crash kills all threads in process
Creation cost High (fork + exec) Low (1–10 µs)

In Python:

import threading

def worker(n):
    print(f"Thread {n} running")
    # compute something
    print(f"Thread {n} done")

threads = [threading.Thread(target=worker, args=(i,)) for i in range(4)]
for t in threads: t.start()
for t in threads: t.join()   # wait for all threads to finish

The Race Condition

The fundamental problem of concurrent programs:

counter = 0   # shared variable

def increment():
    global counter
    for _ in range(100_000):
        counter += 1   # NOT atomic!

t1 = threading.Thread(target=increment)
t2 = threading.Thread(target=increment)
t1.start(); t2.start()
t1.join(); t2.join()
print(counter)   # Expected: 200,000. Actual: some random smaller number!

counter += 1 compiles to three machine instructions:

  1. LOAD counter into register
  2. ADD 1 to register
  3. STORE register back to counter

If two threads interleave between any of these steps, one thread's increment is lost. This is a race condition — the outcome depends on timing, making it non-deterministic and nearly impossible to reproduce consistently.

Critical Sections and Mutual Exclusion

A critical section is any code that accesses a shared resource and must not be executed by two threads simultaneously.

Mutex (Mutual Exclusion Lock): only one thread can hold the lock at a time. Others block until the holder releases it.

import threading

counter = 0
lock = threading.Lock()

def safe_increment():
    global counter
    for _ in range(100_000):
        with lock:           # acquire on entry, release on exit
            counter += 1    # critical section — only one thread at a time

t1 = threading.Thread(target=safe_increment)
t2 = threading.Thread(target=safe_increment)
t1.start(); t2.start()
t1.join(); t2.join()
print(counter)   # Always 200,000

The with lock: context manager ensures the lock is always released, even if an exception occurs.

Thread Safety Patterns

Immutable objects: if shared data never changes, no synchronisation is needed. Pure functions and immutable data structures are inherently thread-safe.

Thread-local storage: data stored per-thread, not shared. Each thread has its own copy.

import threading
local_data = threading.local()

def worker():
    local_data.x = threading.current_thread().name   # each thread writes its own
    print(local_data.x)   # each thread reads its own, no conflict

Producer-Consumer pattern: producers add work to a queue; consumers take from it.

from queue import Queue

q = Queue(maxsize=10)

def producer():
    for i in range(20):
        q.put(i)           # blocks if queue full
    q.put(None)            # sentinel: no more work

def consumer():
    while True:
        item = q.get()     # blocks if queue empty
        if item is None: break
        process(item)

threading.Thread(target=producer).start()
threading.Thread(target=consumer).start()

Python's queue.Queue is thread-safe — all operations are internally synchronised.

The GIL and True Parallelism in Python

Python's Global Interpreter Lock (GIL) prevents multiple threads from executing Python bytecode simultaneously. This means:

  • Python threads are concurrent (interleaved) but not truly parallel for CPU-bound code
  • For CPU-bound parallelism, use multiprocessing (separate processes, no GIL)
  • For I/O-bound tasks (network, disk), threads work fine — the GIL is released during I/O
# For CPU-bound parallel work:
from multiprocessing import Pool

def compute(x):
    return x * x

with Pool(processes=4) as pool:
    results = pool.map(compute, range(1_000_000))

Async/Await — Cooperative Concurrency

For I/O-bound tasks with thousands of concurrent operations, threads waste memory (each thread has a ~8 MB stack). Asyncio uses a single thread with cooperative multitasking:

import asyncio

async def fetch(url):
    # When awaiting I/O, control returns to the event loop
    await asyncio.sleep(1)   # simulate network request
    return f"data from {url}"

async def main():
    # Launch 1000 concurrent "requests" with one thread
    tasks = [fetch(f"http://example.com/{i}") for i in range(1000)]
    results = await asyncio.gather(*tasks)

asyncio.run(main())

One thread handles thousands of concurrent I/O operations by switching between them when each is waiting. Memory: ~1 KB per coroutine vs ~8 MB per thread.

Going Deeper

Memory model and visibility: on a multi-core CPU, each core has its own cache. One thread writing to counter may not be immediately visible to another thread reading it — the value might be in the writing thread's cache only. CPU memory models (x86's TSO, ARM's weakly-ordered model) define exactly what ordering guarantees exist. The C++ std::atomic and Java volatile keyword ensure proper memory visibility without full mutex overhead.

Lock-free data structures: using CPU atomic compare-and-swap (CAS) instructions to update shared data without acquiring a lock. Lock-free queues, stacks, and hash tables can outperform lock-based ones under high contention. But they are extremely difficult to write correctly — even experts make mistakes. See Module 6.2 (Going Deeper) for Michael-Scott lock-free queue.

﻿# Module 7.2 — Mutexes, Semaphores, and Deadlocks

The Problem

Module 7.1 introduced race conditions and the basic mutex. But real concurrent systems have more complex coordination needs:

  • Allow up to N threads to access a resource simultaneously (database connection pool)
  • Signal that an event has occurred (producer notifies consumer)
  • Prevent a circular wait where threads block each other forever

These needs require richer synchronisation primitives — and the coordination bugs they prevent are replaced by a new class of bugs that are often harder to detect: deadlocks, livelocks, and starvation.

The Story

Dijkstra's Semaphore

Edsger Dijkstra introduced the semaphore in his 1965 paper "Solution of a Problem in Concurrent Programming Control." He was solving the mutual exclusion problem: how can N processes share a resource safely?

A semaphore is an integer with two atomic operations:

  • P (proberen/wait): decrement, block if result is negative
  • V (verhogen/signal): increment, wake a blocked thread if any

Dijkstra was also the first to formally describe the dining philosophers problem (1965): five philosophers sit at a round table, each alternating between thinking and eating. To eat, a philosopher needs both the left and right fork. If all pick up their left fork simultaneously and wait for the right, they deadlock — a simple model of circular waiting.

This single thought experiment has driven 60 years of research into deadlock avoidance, lock ordering, and concurrent algorithm design.

The Concept

Mutex (Revisited)

A mutex is a binary semaphore with ownership semantics: only the thread that locked it can unlock it. Used for mutual exclusion — one thread in the critical section at a time.

import threading
lock = threading.Lock()

with lock:              # acquire
    # critical section
    pass               # release on exit (even on exception)

Reentrant mutex (RLock): a thread can acquire the same lock multiple times without deadlocking. Must release the same number of times.

rlock = threading.RLock()
with rlock:
    with rlock:    # safe with RLock, deadlock with Lock
        pass

Semaphores — Counting Synchronisation

A semaphore with initial value N allows up to N threads to be in the critical section simultaneously:

sem = threading.Semaphore(3)   # allow 3 concurrent accesses

def access_database():
    with sem:          # acquire (blocks when count reaches 0)
        # use database connection (max 3 simultaneous)
        query_db()
    # release: another thread can now enter

Binary semaphore (initial=1): equivalent to a mutex, but any thread can release it — useful for signalling.

Signalling with semaphores — producer/consumer:

filled = threading.Semaphore(0)   # how many items available to consume
empty  = threading.Semaphore(10)  # how many spaces available to produce
mutex  = threading.Semaphore(1)   # protect buffer

def producer():
    while True:
        item = produce()
        empty.acquire()    # wait for empty slot
        mutex.acquire()
        buffer.append(item)
        mutex.release()
        filled.release()   # signal: item is available

def consumer():
    while True:
        filled.acquire()   # wait for item
        mutex.acquire()
        item = buffer.pop()
        mutex.release()
        empty.release()    # signal: slot freed
        consume(item)

Condition Variables

A condition variable allows threads to wait for a specific condition while atomically releasing a mutex:

lock = threading.Lock()
condition = threading.Condition(lock)
buffer = []

def producer():
    while True:
        item = produce()
        with condition:
            buffer.append(item)
            condition.notify()   # wake one waiting consumer

def consumer():
    while True:
        with condition:
            while not buffer:    # spurious wakeup protection
                condition.wait() # release lock, block, re-acquire on wake
            item = buffer.pop(0)
        consume(item)

The key operations:

  • wait(): atomically release lock + block thread + re-acquire lock on wake
  • notify(): wake one waiting thread
  • notify_all(): wake all waiting threads

Deadlock — The Circular Wait

A deadlock occurs when:

  1. Thread A holds lock L1 and waits for lock L2
  2. Thread B holds lock L2 and waits for lock L1
  3. Neither can proceed
lock1 = threading.Lock()
lock2 = threading.Lock()

def thread_a():
    with lock1:              # acquires lock1
        with lock2: pass     # waits for lock2 → DEADLOCK if B holds it

def thread_b():
    with lock2:              # acquires lock2
        with lock1: pass     # waits for lock1 → DEADLOCK if A holds it

The four conditions for deadlock (Coffman, 1971):

  1. Mutual exclusion: resources cannot be shared
  2. Hold and wait: threads hold resources while waiting for more
  3. No preemption: resources cannot be forcibly taken
  4. Circular wait: a cycle of threads, each waiting for the next

Breaking any one condition prevents deadlock:

Lock ordering (break circular wait): always acquire locks in the same global order. If all threads acquire lock1 before lock2, circular wait is impossible:

def thread_a():
    with lock1:
        with lock2: pass   # same order as thread_b

def thread_b():
    with lock1:            # both acquire lock1 first
        with lock2: pass

Timeout with trylock (break hold-and-wait):

def safe_acquire(lock1, lock2, timeout=1.0):
    if lock1.acquire(timeout=timeout):
        if lock2.acquire(timeout=timeout):
            return True
        else:
            lock1.release()   # back off — try again later
    return False

Livelock and Starvation

Livelock: threads keep responding to each other, constantly changing state, but making no progress. Like two people meeting in a hallway, each stepping aside in the same direction repeatedly.

Starvation: a thread never gets CPU time because other threads always have higher priority or are always preferred by the scheduler. A low-priority thread may wait indefinitely — not blocked, just never scheduled.

Solution: aging — gradually increase priority of waiting threads so every thread eventually gets scheduled.

The Dining Philosophers — Solutions

Resource hierarchy (Dijkstra's solution): number forks 1–5. Each philosopher picks up the lower-numbered fork first. The philosopher who would create the cycle (the one who wants fork 5 then fork 1) picks fork 1 then fork 5 instead — no cycle possible.

Arbitrator (waiter solution): a central mutex (the "waiter") that philosophers must acquire before picking up any fork. Only one philosopher eats at a time — correct but serialised.

Chandy/Misra (1984): each fork has an owner. A hungry philosopher sends a "request" message. The fork owner sends the fork only if not eating; otherwise defers. Works for distributed systems.

Going Deeper

Read-write locks: many operations are reads (multiple threads can read simultaneously) and only occasionally writes (exclusive access required). A threading.RWLock allows multiple concurrent readers OR one exclusive writer. This dramatically improves throughput for read-heavy workloads.

Monitors: a higher-level abstraction combining a mutex and condition variable into a single object. Java's synchronized keyword and wait()/notify() implement a monitor. Every Java object has an intrinsic monitor. Python's threading.Condition is effectively a monitor.

class BoundedBuffer:
    def __init__(self, capacity):
        self._buffer   = []
        self._capacity = capacity
        self._cond     = threading.Condition()

    def put(self, item):
        with self._cond:
            while len(self._buffer) >= self._capacity:
                self._cond.wait()         # releases lock, waits
            self._buffer.append(item)
            self._cond.notify_all()       # wake consumers

    def get(self):
        with self._cond:
            while not self._buffer:
                self._cond.wait()
            item = self._buffer.pop(0)
            self._cond.notify_all()       # wake producers
            return item

﻿# Module 7.3 — Network Sockets from Scratch

The Problem

Two programs. Different machines. Possibly different continents. How do they exchange data?

The answer — at every layer above bare hardware — is sockets. A socket is the API that Unix and Windows expose for network communication. Every web server, every game server, every chat application, every database client ultimately calls socket(), bind(), listen(), accept(), send(), recv().

Understanding sockets means understanding how every networked application is built.

The Story

The Birth of the Socket API

The Berkeley Software Distribution (BSD) Unix at UC Berkeley introduced the socket API in 1983 (4.2BSD). The goal was to create a uniform interface for network communication that abstracted over different network protocols (TCP/IP, Xerox NS, UNIX domain sockets).

The BSD socket API was so well-designed that it was adopted by every Unix-like system, then by Windows (as WinSock, 1993), and is now the standard network API on every major platform. It has been essentially unchanged for 40 years.

The core insight: a socket is a file descriptor — it behaves like a file. You open() it (socket()), you read() from it (recv()), you write() to it (send()), you close() it. The "everything is a file" Unix philosophy (Module 4.3) applied to networking.

The Concept

TCP Socket — Client-Server Model

Server side:

import socket

# 1. Create socket — IPv4, TCP (stream)
server = socket.socket(socket.AF_INET, socket.SOCK_STREAM)

# 2. Allow reuse of address immediately after process ends
server.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)

# 3. Bind to address and port
server.bind(('0.0.0.0', 8080))

# 4. Listen for incoming connections (backlog = 5)
server.listen(5)
print("Server listening on port 8080")

while True:
    # 5. Accept a new connection (blocks until client connects)
    conn, addr = server.accept()
    print(f"Connection from {addr}")

    # 6. Receive data (up to 1024 bytes)
    data = conn.recv(1024)
    print(f"Received: {data.decode()}")

    # 7. Send response
    conn.send(b"Hello from server!")

    # 8. Close this connection
    conn.close()

Client side:

import socket

# 1. Create socket
client = socket.socket(socket.AF_INET, socket.SOCK_STREAM)

# 2. Connect to server
client.connect(('127.0.0.1', 8080))

# 3. Send data
client.send(b"Hello from client!")

# 4. Receive response

print(f"Received: {data.decode()}")

# 5. Close
client.close()

The TCP Handshake (Behind the Scenes)

When client.connect() is called, the OS performs the TCP three-way handshake:

  1. Client sends SYN (synchronise) to server
  2. Server replies SYN-ACK (synchronise-acknowledge)
  3. Client sends ACK (acknowledge)
  4. Connection established — bidirectional byte stream ready

This handshake takes one round trip (~10 ms on a LAN, ~50–100 ms across the internet). HTTPS adds TLS handshake on top: 1–2 more round trips. Modern TLS 1.3 reduces this to 1 round trip.

UDP Sockets — Fire and Forget

UDP is connectionless — no handshake, no guarantee of delivery or ordering.

# UDP server
server = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
server.bind(('0.0.0.0', 9090))
data, addr = server.recvfrom(1024)   # returns data + sender address
server.sendto(b"ACK", addr)          # reply (optional)

# UDP client
client = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
client.sendto(b"Hello", ('127.0.0.1', 9090))   # no connect() needed

UDP is used when: low latency matters more than reliability (gaming, video streaming, DNS lookups), or when the application handles its own reliability (QUIC, DTLS).

Handling Multiple Clients

A single-threaded server handles clients one at a time. For concurrent connections, three approaches:

1. Threaded server (one thread per connection):

import threading

def handle_client(conn, addr):
    data = conn.recv(1024)
    conn.send(b"Hello " + data)
    conn.close()

server = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
server.bind(('', 8080)); server.listen()
while True:
    conn, addr = server.accept()
    threading.Thread(target=handle_client, args=(conn, addr)).start()

Scales to ~1,000 clients (memory/thread overhead). Does not scale to 10,000+ connections (C10K problem).

2. select/poll/epoll — I/O multiplexing. One thread monitors many sockets simultaneously:

import selectors
sel = selectors.DefaultSelector()
# Register multiple sockets
# sel.select() blocks until any socket is ready
# No threads — one event loop handles all connections

This is how nginx handles 50,000+ concurrent connections on one thread — the event-driven model.

3. asyncio (Python's event-driven networking):

import asyncio

async def handle_client(reader, writer):
    data = await reader.read(1024)
    writer.write(b"Echo: " + data)
    await writer.drain()
    writer.close()

async def main():
    server = await asyncio.start_server(handle_client, '127.0.0.1', 8080)
    async with server:
        await server.serve_forever()

asyncio.run(main())

Building a Tiny HTTP Server

HTTP/1.0 is just text over a TCP socket. A minimal server:

import socket, os

server = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
server.bind(('', 8080)); server.listen(5)

while True:
    conn, _ = server.accept()
    request = conn.recv(4096).decode()
    first_line = request.split('\r\n')[0]  # e.g., "GET /index.html HTTP/1.0"
    path = first_line.split(' ')[1]        # e.g., "/index.html"

    filename = '.' + path
    if os.path.exists(filename):
        with open(filename, 'rb') as f:
            body = f.read()
        response = (b"HTTP/1.0 200 OK\r\n"
                   b"Content-Type: text/html\r\n\r\n" + body)
    else:
        response = b"HTTP/1.0 404 Not Found\r\n\r\nNot Found"

    conn.send(response)
    conn.close()

This ~20-line server serves static files. A production server (nginx, Apache) is this same concept with: non-blocking I/O, TLS, HTTP/2 multiplexing, gzip compression, virtual hosting, and hundreds of configuration options.

Going Deeper

TCP internals — flow control and congestion control: TCP ensures neither end overwhelms the other. The receive window (advertised by the receiver) limits how much data can be in flight. import struct

# Header: [msg_type: 1B][length: 2B] = 3 bytes total
HEADER_FMT = '!BH'   # big-endian: unsigned byte + unsigned short

    if isinstance(data, str): data = data.encode()

    buf = b''
    while len(buf) < n:
        chunk = sock.recv(n - len(buf))
        if not chunk: raise ConnectionError("Connection closed")
        buf += chunk
    return buf

    msg_type, length = struct.unpack(HEADER_FMT, header)
    data = recv_exact(sock, length)

﻿# Module 7.4 — Building a Tiny Shell

The Problem

The shell is the user's interface to the operating system. Every time you type ls -la | grep .py > output.txt, something reads that line, parses it, and executes it.

Building a tiny shell from scratch teaches you:

  • How fork() + exec() work together to create processes
  • How pipes are implemented at the OS level
  • How input/output redirection works
  • What the shell actually does when you type a command

The Story

The Shell as the First Application

The shell was the very first interactive program run by Unix — it was already present in the initial PDP-7 Unix system in 1969. Ken Thompson wrote the first Unix shell (the Thompson shell, sh) in a single weekend.

Stephen Bourne rewrote it in 1977 as the Bourne shell (/bin/sh) — the ancestor of every POSIX-compatible shell today. Bill Joy (founder of Sun Microsystems) wrote the C shell (csh) in 1978, adding job control and command history. David Korn wrote the Korn shell (ksh) in 1983, combining features of both. The Bash shell (Bourne Again SHell, Brian Fox, 1989) is the default on most Linux systems today.

All of these shells — despite their different features and syntaxes — implement the same fundamental mechanics: read a line, parse it, fork(), exec(), wait().

The Concept

The Core Loop: REPL

A shell is a Read-Eval-Print Loop:

import os, sys, subprocess

def shell():
    while True:
        # 1. Print prompt
        try:
            line = input(f"{os.getcwd()} $ ")
        except (EOFError, KeyboardInterrupt):
            print(); break

        line = line.strip()
        if not line: continue

        # 2. Parse
        parts = line.split()

        # 3. Built-in commands
        if parts[0] == 'exit':
            break
        if parts[0] == 'cd':
            try: os.chdir(parts[1] if len(parts) > 1 else os.environ.get('HOME', '/'))
            except FileNotFoundError as e: print(f"cd: {e}")
            continue

        # 4. Execute external command
        try:
            proc = subprocess.run(parts)
        except FileNotFoundError:
            print(f"{parts[0]}: command not found")

shell()

fork() + exec() — The Unix Process Model

Under the hood, subprocess.run(['ls', '-la']) does exactly this:

import os

pid = os.fork()
if pid == 0:
    # Child process
    os.execvp('ls', ['ls', '-la'])   # replace child with 'ls'
    # execvp never returns on success
    sys.exit(1)
else:
    # Parent process (the shell)
    os.waitpid(pid, 0)               # wait for child to finish

fork() creates an exact copy of the current process. exec() replaces the running program with a new one. The child never returns from exec() on success. The parent waits.

This two-step design gives the shell a window between fork() and exec() to manipulate file descriptors — which is how pipes and redirections are implemented.

I/O Redirection

ls > output.txt       # stdout → file
cat < input.txt       # stdin ← file
ls 2> errors.txt      # stderr → file

Between fork() and exec(), the shell redirects file descriptors using dup2():

if redirect_stdout:
    fd = os.open(output_file, os.O_WRONLY | os.O_CREAT | os.O_TRUNC, 0o644)
    os.dup2(fd, 1)    # make stdout (fd 1) point to the file
    os.close(fd)      # close original (now duplicated)

dup2(src, dst): makes dst a duplicate of src. After dup2(fd, 1), writes to stdout go to the file. The exec()'d program never knows — it just uses fd 1 as normal.

Pipes

ls | grep .py | wc -l

A pipe | connects stdout of one process to stdin of the next.

def run_pipeline(commands):
    # commands = [['ls'], ['grep', '.py'], ['wc', '-l']]
    n = len(commands)
    pipes = [os.pipe() for _ in range(n - 1)]  # n-1 pipes for n commands

    pids = []
    for i, cmd in enumerate(commands):
        pid = os.fork()
        if pid == 0:  # child
            # Connect stdin to previous pipe's read end
            if i > 0:
                os.dup2(pipes[i-1][0], 0)  # stdin ← pipe read
            # Connect stdout to next pipe's write end
            if i < n - 1:
                os.dup2(pipes[i][1], 1)    # stdout → pipe write
            # Close all pipe fds (child doesn't need them)
            for r, w in pipes:
                os.close(r); os.close(w)
            os.execvp(cmd[0], cmd)
            sys.exit(1)
        pids.append(pid)

    # Parent: close all pipe fds
    for r, w in pipes:
        os.close(r); os.close(w)

    # Wait for all children
    for pid in pids:
        os.waitpid(pid, 0)

The kernel's os.pipe() creates a pair of file descriptors: (read_end, write_end). Data written to write_end is buffered by the kernel and can be read from read_end. This is why ls | grep works: ls's stdout writes to the pipe buffer; grep's stdin reads from it.

Job Control

Real shells support background jobs (cmd &), job suspension (Ctrl+Z), and foreground/background switching (fg, bg). This requires Unix signal handling:

  • SIGCHLD: sent to parent when a child changes state
  • SIGINT (Ctrl+C): interrupt the foreground job
  • SIGTSTP (Ctrl+Z): suspend the foreground job
  • SIGCONT: resume a suspended job

A minimal implementation:

import signal

background_jobs = []

def run_background(cmd):
    pid = os.fork()
    if pid == 0:
        os.execvp(cmd[0], cmd); sys.exit(1)
    background_jobs.append(pid)
    print(f"[{len(background_jobs)}] {pid}")

▸ Part D.11 — 2>&1 ordering

2>&1 means "redirect fd 2 (stderr) to wherever fd 1 (stdout) currently points."

Order matters: > out.txt 2>&1 means:

  1. dup2(open("out.txt"), 1) — redirect stdout to file
  2. dup2(1, 2) — redirect stderr to current stdout (= the file)

If reversed (2>&1 > out.txt): step 1 redirects stderr to terminal (current stdout before any redirection), step 2 redirects stdout to file. Stderr still goes to terminal — wrong.

﻿# Module 7.5 — Building a Tiny HTTP Server

The Problem

Every website you visit is served by an HTTP server. nginx, Apache, Express, Django, Flask — they all do the same core job: listen on a port, accept TCP connections, parse HTTP requests, return HTTP responses.

When you understand how a tiny HTTP server works from the socket layer up, every web framework becomes transparent. You understand what Flask's @app.route is doing underneath. You understand what "middleware" means mechanically. You understand why HTTP/1.1 keep-alive matters for performance.

The Story

HTTP Was Designed on a Napkin

Tim Berners-Lee invented HTTP at CERN in 1989. The original HTTP/0.9 was extraordinarily simple: one command (GET /path) over a TCP connection, response is the file content, connection closes. No headers, no status codes, no response format.

HTTP/1.0 (1996) added headers, status codes (200, 404, etc.), and support for content types — enabling images, not just text. Each request required a new TCP connection.

HTTP/1.1 (1997, still dominant) added keep-alive (reuse connections for multiple requests), chunked transfer encoding, host headers (enabling virtual hosting — multiple websites on one IP), and caching directives. It is the protocol powering the majority of the web today.

HTTP/2 (2015) added multiplexing (multiple requests per connection, no head-of-line blocking), header compression, and server push. HTTP/3 (2022) runs over QUIC instead of TCP.

A working understanding of HTTP/1.1 is sufficient to understand everything built on top of it.

The Concept

HTTP Request Format

An HTTP/1.1 request is plain text over a TCP connection:

GET /index.html HTTP/1.1\r\n
Host: www.example.com\r\n
User-Agent: Mozilla/5.0\r\n
Accept: text/html\r\n
\r\n

Structure:

  • Request line: METHOD PATH HTTP/VERSION
  • Headers: Name: Value pairs, each ending \r\n
  • Blank line: \r\n marks end of headers
  • Optional body: for POST/PUT requests (e.g., form data, JSON)

HTTP Response Format

HTTP/1.1 200 OK\r\n
Content-Type: text/html; charset=utf-8\r\n
Content-Length: 138\r\n
Connection: keep-alive\r\n
\r\n
<html>...</html>

Structure:

  • Status line: HTTP/VERSION STATUS_CODE REASON_PHRASE
  • Headers: content type, length, caching, cookies, etc.
  • Blank line
  • Body: the actual content

Parsing an HTTP Request

def parse_request(raw: bytes) -> dict:
    text  = raw.decode('utf-8', errors='replace')
    lines = text.split('\r\n')

    # Request line
    method, path, version = lines[0].split(' ', 2)

    # Headers
    headers = {}
    i = 1
    while i < len(lines) and lines[i] != '':
        key, _, value = lines[i].partition(': ')
        headers[key.lower()] = value
        i += 1

    # Body (everything after the blank line)
    body = '\r\n'.join(lines[i+1:]) if i+1 < len(lines) else ''

    return {
        'method':  method,
        'path':    path,
        'version': version,
        'headers': headers,
        'body':    body,
    }

Building the Server — Step by Step

import socket, os, mimetypes
from pathlib import Path

STATIC_ROOT = Path('./static')

STATUS = {200: 'OK', 404: 'Not Found', 405: 'Method Not Allowed',
          500: 'Internal Server Error'}

def build_response(status, headers, body=b''):
    header_lines = f"HTTP/1.1 {status} {STATUS[status]}\r\n"
    for k, v in headers.items():
        header_lines += f"{k}: {v}\r\n"
    return header_lines.encode() + b"\r\n" + body

def handle_request(raw):
    try:
        req = parse_request(raw)
    except Exception:
        return build_response(400, {'Content-Length': 0})

    if req['method'] not in ('GET', 'HEAD'):
        return build_response(405, {'Allow': 'GET, HEAD', 'Content-Length': 0})

    # Resolve path (security: prevent directory traversal)
    rel_path = req['path'].lstrip('/')
    if not rel_path: rel_path = 'index.html'
    file_path = (STATIC_ROOT / rel_path).resolve()

    # Security: ensure file is inside STATIC_ROOT
    if not str(file_path).startswith(str(STATIC_ROOT.resolve())):
        return build_response(403, {'Content-Length': 0})

    if not file_path.exists():
        return build_response(404, {'Content-Type': 'text/plain',
                                    'Content-Length': str(len(b'Not Found'))}, b'Not Found')

    body = b'' if req['method'] == 'HEAD' else file_path.read_bytes()
    mime = mimetypes.guess_type(str(file_path))[0] or 'application/octet-stream'
    return build_response(200, {
        'Content-Type': mime,
        'Content-Length': str(len(body)),
        'Connection': 'close',
    }, body)

def run_server(host='', port=8080):
    server = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
    server.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
    server.bind((host, port))
    server.listen(5)
    print(f"Serving on http://localhost:{port}")
    while True:
        conn, addr = server.accept()
        raw = b''
        while b'\r\n\r\n' not in raw:
            chunk = conn.recv(4096)
            if not chunk: break
            raw += chunk
        response = handle_request(raw)
        conn.sendall(response)
        conn.close()

Middleware

A middleware is a function that wraps a handler — adding behaviour before and after:

def logging_middleware(handler):
    def wrapper(req):
        print(f"→ {req['method']} {req['path']}")
        response = handler(req)
        status = response[:15].decode()
        print(f"← {status}")
        return response
    return wrapper

# Apply to all routes:
for path, fn in routes.items():
    routes[path] = logging_middleware(fn)

This is the exact pattern used by Express.js middleware, Django middleware, and Flask before_request hooks.

Going Deeper

Keep-alive connections: HTTP/1.1 by default keeps TCP connections open for multiple requests (Connection: keep-alive). Without this, every image, stylesheet, and script requires a new TCP handshake — dramatically slowing page loads. A production server must handle multiple requests per connection efficiently.

WebSockets: HTTP can be "upgraded" to a persistent, bidirectional connection using the WebSocket protocol. After the upgrade handshake (an HTTP request with Upgrade: websocket), the connection becomes a raw TCP stream with a simple framing protocol. Used for real-time chat, live dashboards, collaborative editing, and multiplayer games.

import re

class Router:
    def __init__(self):
        self._routes = []

    def route(self, method, pattern):
        def decorator(fn):
            regex = re.sub(r'\{(\w+)\}', r'(?P<\1>[^/]+)', pattern) + '$'
            self._routes.append((method, re.compile(regex), fn))
            return fn
        return decorator

    def dispatch(self, req):
        for method, regex, fn in self._routes:
            if req['method'] != method: continue
            m = regex.match(req['path'])
            if m:
                return fn(req, **m.groupdict())
        # Check if path matches but method doesn't
        for _, regex, _ in self._routes:
            if regex.match(req['path']):
