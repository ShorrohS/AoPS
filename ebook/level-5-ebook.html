﻿# Module 5.1 — C: Close to the Metal

The Problem

Assembly language gives you full control over the hardware. But assembly is architecture-specific: x86-64 assembly won't run on ARM. Writing an operating system, a compiler, or a database in pure assembly means rewriting it for every CPU.

In 1972, Dennis Ritchie at Bell Labs asked: Can we have a language that is portable across hardware but still compiles down to efficient machine code with no hidden overhead?

The answer was C — and it changed computing permanently.

C sits at the exact boundary between human-readable and machine-executable. Every concept in C maps directly to a small number of machine instructions. There is no garbage collector, no runtime, no virtual machine. If you write x++, the CPU executes one instruction. This is why C is called "portable assembly."

The Story

Why C Was Invented

Before C, operating systems were written in assembly. The PDP-7 version of Unix (1969) was written entirely in assembly. Porting it to a new machine meant rewriting every line.

Ritchie's predecessor language, B (1969), was portable but too slow for OS work — it had no types, so every operation treated data as machine words, requiring extra work to handle bytes or floats.

C added:

  • Types: int, char, float, struct — the compiler uses type information to generate correct machine code without programmer overhead
  • Structs: group related data into a single compound type
  • Pointers: explicit memory addresses — full hardware access
  • Arrays: contiguous memory blocks with typed access

In 1973, the Unix kernel was rewritten in C. This was the first major operating system written in a high-level language. It could now be ported to new hardware in weeks instead of years. This single decision — rewriting Unix in C — is why C became universal.

The Compilation Pipeline (Review)

Source (.c)  →  Preprocessor  →  Compiler  →  Assembler  →  Linker  →  Executable

Preprocessor (cpp): expands #include, #define, #ifdef. Produces pure C.
Compiler (cc1): translates C to assembly. Performs optimisation.
Assembler (as): translates assembly to object code (.o).
Linker (ld): combines object files, resolves symbols, produces final binary.

Understanding this pipeline explains why a missing semicolon in foo.c can produce an error message referencing foo.h — the preprocessor merged them first.

The Concept

Pointers — The Core of C

A pointer is a variable that holds a memory address.

int  x = 42;      // x is an int stored at some address
int *p = &x;      // p holds the address of x (& = "address of")
int  y = *p;      // y = the value at address p (* = "dereference")
*p = 100;         // write 100 to the address p points to → x is now 100

This is not abstraction — this is exactly what the CPU does. p contains a 64-bit integer that happens to be a memory address. The dereference *p compiles to a single MOV instruction using an indirect addressing mode.

Why pointers matter:

  • Pass large data to functions without copying (pass by reference)
  • Build dynamic data structures (linked lists, trees) that grow at runtime
  • Interface with hardware registers (embedded systems)
  • Implement your own memory allocator

Common pointer mistakes:

  • Null pointer dereference: int *p = NULL; *p = 5; → segfault
  • Dangling pointer: pointer to memory that has been freed
  • Buffer overrun: writing past the end of an array via pointer arithmetic
  • Memory leak: allocating with malloc() without ever calling free()

Memory Allocation

C has two kinds of memory:

Stack — automatic, managed by the compiler:

void fn() {
    int x = 5;      // allocated on stack when fn() called
    char buf[64];   // 64 bytes on stack
}                   // all freed when fn() returns

Heap — manual, managed by the programmer:

int *arr = malloc(100 * sizeof(int));  // allocate 400 bytes
if (arr == NULL) { /* handle error */ }
arr[0] = 42;        // use it
free(arr);          // you must free it — no garbage collector
arr = NULL;         // good practice: clear the pointer after free

This manual memory management is what makes C fast and dangerous simultaneously. No GC pause, but also no safety net.

Structs — User-Defined Types

struct Point {
    int x;
    int y;
};

struct Point p1;
p1.x = 10;
p1.y = 20;

struct Point *pp = &p1;
pp->x = 30;          // arrow operator: (*pp).x = 30

Structs are laid out contiguously in memory. struct Point occupies 8 bytes: 4 for x, 4 for y. The compiler may add padding bytes to ensure alignment rules are met, which is why sizeof(struct) can surprise you.

Functions and the Call Stack

C functions map directly to the calling convention from Module 4.2:

int add(int a, int b) {
    return a + b;
}

int main() {
    int result = add(3, 4);  // a→rdi, b→rsi; return→rax
    return 0;
}

Recursion works naturally because each call gets its own stack frame:

int factorial(int n) {
    if (n <= 1) return 1;         // base case
    return n * factorial(n - 1);  // recursive case
}

Building a Memory Allocator

To truly understand C, you build a simplified malloc(). The core idea:

// A minimal slab allocator — conceptual sketch
static char heap[65536];  // 64 KB of pretend heap
static int  top = 0;      // current allocation pointer

void *my_malloc(int size) {
    if (top + size > sizeof(heap)) return NULL;  // out of memory
    void *ptr = &heap[top];
    top += size;
    return ptr;
}
// (No free() in this sketch — a real allocator needs a free list)

A real malloc() implementation (like ptmalloc in glibc) manages a free list of blocks, coalesces adjacent free blocks, and calls brk()/mmap() to request more memory from the OS when needed.

Going Deeper

undefined behaviour: C has a large category of operations that are "undefined behaviour" (UB) — the language standard makes no guarantee about what happens. Signed integer overflow, reading uninitialised memory, modifying a string literal: all UB. The compiler is allowed to assume UB never happens, which means it can and does optimise away code that would prevent UB from being exploited. This is a major source of security vulnerabilities. Tools like AddressSanitizer and UBSanitizer catch UB at runtime during development.

C in 2024: Despite being 50+ years old, C is still the primary language for operating system kernels (Linux, Windows, macOS, iOS), embedded systems (microcontrollers), and anywhere that raw performance and minimal runtime overhead are required. Every Python interpreter, every JavaScript engine, every database is written substantially in C or C++.

Trace the following C code. For each line, write the value of every variable and the state of memory.

Part B — Stack vs Heap

void bad_function() {
    int local = 42;
    int *p = &local;
    return;          // local goes out of scope here
    // p is now a DANGLING POINTER

int *create_int(int val) {
    int *p = malloc(sizeof(int));
    *p = val;

int main() {

  4. Write a version of create_int that allocates an array of n integers and fills them with values 1, 2, ..., n. The caller is responsible for freeing.

Solutions

▸ Part A
  1. p = address of arr[0] (e.g., 0x7FFF0000). *p = 10.
  2. p advances by 4 bytes (sizeof int = 4). Pointer arithmetic scales by the pointed-to type size.
  3. Line 8 prints 2. q - p computes the number of elements (not bytes) between the two pointers: (arr+4) - (arr+2) = 2.
  4. If int were 8 bytes: p++ would advance by 8 bytes, but the element count difference (q - p) would still be 2.
▸ Part B.8 — Array creation
int *create_array(int n) {
    int *arr = malloc(n * sizeof(int));
    if (!arr) return NULL;
    for (int i = 0; i < n; i++) arr[i] = i + 1;
    return arr;
}
// Caller: int *a = create_array(5); ... free(a);
▸ Part C — strlen
// Array index version
size_t my_strlen(const char *s) {
    if (!s) return 0;
    size_t n = 0;
    while (s[n] != '\0') n++;
    return n;
}

// Pointer arithmetic version
size_t my_strlen_ptr(const char *s) {
    if (!s) return 0;
    const char *p = s;
    while (*p) p++;
    return (size_t)(p - s);
}
▸ Part D

  1. struct A: char(1) + 3 padding + int(4) + char(1) + 3 padding = 12 bytes. Padding after c aligns i to 4-byte boundary. Trailing padding aligns struct size to multiple of 4.

  2. struct B: int(4) + char(1) + char(1) + 2 padding = 8 bytes. Both chars after the int don't require inter-field padding.

  3. Each field must be aligned to its own size. int requires 4-byte alignment, so padding is added after any smaller field that precedes it.

  4. double(8) + int(4) + char(1) + 3 padding = 16 bytes. Optimal order: double first (largest), then int, then char.

▸ Part E

  1. Bug 1: malloc(len) allocates len bytes but a C string needs len + 1 bytes (for the null terminator '\0'). Writing to result[len] in the loop is out of bounds — undefined behaviour.

  2. The free(result) is after the return statement — unreachable code. The compiler may warn. The fix is either to not free (let the caller free) or restructure. Here the correct fix is removing the dead free.

  3. Bug 3: free(s) is missing after printf. Corrected:

int main() {
    char *s = duplicate_upper("hello");
    if (!s) return 1;
    printf("%s\n", s);
    free(s);
    return 0;
}

The corrected duplicate_upper also needs malloc(len + 1) and result[len] = '\0'.

﻿# Module 5.2 — Python: Abstraction for Humans

The Problem

C gives you total control and total responsibility. Writing a web scraper in C means managing memory, parsing strings byte by byte, handling network sockets manually.

Most programmers most of the time are not writing operating systems. They are solving problems: process this data, build this web service, train this model.

What if the language handled memory, types, and low-level details automatically so the programmer could focus entirely on the problem?

This question produced Python (1991), and then a generation of languages with similar philosophy. Python's design principle: readability counts. Code is read far more than it is written. A program that takes 10 lines in C and 2 lines in Python is almost always faster to write, debug, and maintain — even if it runs 50× slower at execution time.

The Story

Guido van Rossum and the Christmas Holiday

Guido van Rossum was a Dutch programmer working at CWI (Netherlands) in December 1989. During the holiday break, he decided to write a new scripting language as a personal project — something easier to use than C for quick programming tasks, better-designed than the shells and AWK scripts he was using.

He named it Python after Monty Python's Flying Circus, not the snake. His design goals:

  • Elegant syntax that reads almost like pseudocode
  • A comprehensive standard library ("batteries included")
  • Automatic memory management — no malloc/free
  • Dynamic typing — no type declarations needed
  • A single, clear way to do each thing

Python 1.0 was released in 1994. Python 2.0 (2000) added garbage collection and list comprehensions. Python 3.0 (2008) was a backward-incompatible redesign that fixed accumulated design mistakes. By 2020, Python was the most-used programming language in the world by survey.

The Concept

Interpreted vs Compiled

C source code is compiled to machine code once; the CPU runs the machine code directly.

Python source code is interpreted at runtime by the Python interpreter (CPython, written in C):

Python source (.py)
      ↓ Compilation (fast, at runtime)
Bytecode (.pyc)
      ↓ Interpretation (CPython virtual machine)
Result

The CPython VM executes bytecode instructions in a loop. Each Python operation (like x + y) may compile to hundreds of machine instructions — type-checking, object dispatch, reference counting. This is why Python is 50–100× slower than C for CPU-intensive code.

When Python speed doesn't matter:

  • I/O-bound tasks (network requests, file reads) — most time is waiting, not computing
  • NumPy/SciPy/PyTorch operations — these call into C/Fortran/CUDA code, so the speed is C speed
  • Prototyping — development time matters more than runtime for one-off scripts

Dynamic Typing

In C: int x = 5; — the type int is fixed at compile time.

In Python: x = 5 — the type is attached to the value, not the variable. x can point to any type:

x = 5         # x refers to an int object
x = "hello"   # now x refers to a str object
x = [1, 2, 3] # now x refers to a list object

Under the hood, every Python value is a C struct (PyObject) containing:

  • A reference count (for garbage collection)
  • A pointer to the type object
  • The actual value

This indirection — going through a type pointer for every operation — is most of Python's overhead compared to C.

The Python Data Model

Everything in Python is an object. Integers, strings, functions, classes, modules — all objects. Every object has:

  • An identity (id(x) — the memory address)
  • A type (type(x))
  • A value

Immutable types: int, float, str, tuple, frozenset — cannot be changed after creation.
Mutable types: list, dict, set, custom objects — can be modified in-place.

# Immutable: creates a NEW object
x = "hello"
y = x.upper()    # y is a new string "HELLO", x unchanged

# Mutable: modifies IN PLACE
lst = [1, 2, 3]
lst.append(4)    # lst is now [1, 2, 3, 4] — same object

This distinction matters for correctness and performance. Passing a list to a function and modifying it changes the original (pass by reference to the object). Passing an int and "modifying" it just rebinds the local variable (pass by value of the reference — effectively pass by value for immutables).

Garbage Collection

Python uses reference counting as its primary GC mechanism:

x = [1, 2, 3]    # ref count of the list = 1
y = x             # ref count = 2
del x             # ref count = 1
del y             # ref count = 0 → object freed

When an object's reference count reaches 0, it is immediately freed. This is fast and deterministic — no GC pause.

Problem: circular references:

a = {}
b = {}
a['other'] = b    # b's ref count = 2 (b itself + a['other'])
b['other'] = a    # a's ref count = 2
del a             # a's ref count = 1 (still referenced by b)
del b             # b's ref count = 1 (still referenced by a)
# Both are now unreachable but neither is freed!

Python's cycle garbage collector (runs periodically) detects and collects such cycles. This is why Python can have occasional GC pauses for long-lived programs.

Key Built-in Types and Their Internals

List — a dynamic array of object pointers:

lst = [1, 2, 3]
lst.append(4)     # O(1) amortised — pre-allocates extra space
lst.insert(0, 0)  # O(n) — shifts all elements right
lst[2]            # O(1) — direct index access

Dict — a hash table:

d = {'name': 'Alice', 'age': 30}
d['name']         # O(1) average — hash lookup
d['city'] = 'NYC' # O(1) average — insert
'name' in d       # O(1) average — membership test

Python dicts since 3.7 maintain insertion order. The implementation uses open addressing with a compact layout since Python 3.6.

Set — a hash table without values:

s = {1, 2, 3, 4}
s.add(5)           # O(1) average
3 in s             # O(1) average
s1 & s2            # set intersection — O(min(len(s1), len(s2)))

Decorators — Functions That Transform Functions

import time

def timer(func):
    def wrapper(*args, **kwargs):
        start = time.time()
        result = func(*args, **kwargs)
        end = time.time()
        print(f"{func.__name__} took {end - start:.4f}s")
        return result
    return wrapper

@timer
def slow_function():
    time.sleep(1)

slow_function()   # prints: slow_function took 1.0003s

@timer is syntactic sugar for slow_function = timer(slow_function). The decorator wraps the function in new behaviour without modifying its source. This pattern is used extensively in Python frameworks — Flask's @app.route, Django's @login_required, pytest's @pytest.mark.parametrize.

The Python Object Model: Everything is an Object

def add(a, b):
    return a + b

print(type(add))        # <class 'function'>
print(add.__name__)     # 'add'
print(add.__code__)     # code object with bytecode
print(add(3, 4))        # 7

Functions are first-class objects. They can be passed to other functions, stored in lists, returned from functions. This enables functional programming patterns and closures.

Going Deeper

The GIL (Global Interpreter Lock): CPython has a single lock that any thread must hold to execute Python bytecode. This means multiple Python threads cannot run Python code truly in parallel, even on a multi-core CPU. CPU-bound multithreaded Python code often runs slower than single-threaded code due to GIL contention. The workarounds: use multiprocessing (separate processes, no GIL), use asyncio (cooperative concurrency for I/O-bound code), or use libraries that release the GIL (NumPy, I/O operations). Python 3.13 introduced experimental GIL removal (python3.13t).

CPython vs alternatives: CPython is the reference implementation. PyPy uses a JIT compiler and runs many Python programs 5–10× faster. Cython compiles Python-like code to C extensions. Numba JIT-compiles numerical Python to LLVM IR. MicroPython runs on microcontrollers with 256 KB of RAM.

﻿# Module 5.3 — Algorithms: Thinking in Steps

The Problem

You have a program that works. It processes 100 records in 0.01 seconds. You run it on 1,000,000 records. It takes 27 hours.

What went wrong?

Nothing crashed. The logic is correct. But the algorithm — the sequence of steps used to solve the problem — scales so poorly that the program becomes useless at the scale it was designed for.

Understanding algorithms means understanding not just how to solve a problem, but how efficiently — and being able to predict what happens when the input grows by 10×, 100×, or 1,000,000×.

The Story

The Algorithm Predates the Computer

The word algorithm comes from the name of the 9th-century Persian mathematician Muhammad ibn Musa al-Khwarizmi, whose book Kitab al-mukhtasar fi hisab al-jabr wal-muqabala (825 AD) introduced systematic procedures for solving equations. "Algorithm" is a Latinisation of al-Khwarizmi. "Algebra" comes from "al-jabr" in the title.

Long before computers, people described algorithms: Euclid's algorithm for the GCD of two numbers (300 BC) is still used in every modern computer's arithmetic library. Long division is an algorithm. A recipe is an algorithm. The question is always the same: how many steps does it take, and how does that grow as the input grows?

Alan Turing formalised the concept of a computable algorithm in 1936 with the Turing machine — a theoretical model that defines exactly what it means for a problem to be solvable by a mechanical process.

The Concept

Big-O Notation

Big-O notation describes how an algorithm's runtime (or memory usage) scales as the input size n grows. It describes the worst-case upper bound, ignoring constant factors.

Notation Name Example n=100 n=1,000 n=1,000,000
O(1) Constant Array index access 1 op 1 op 1 op
O(log n) Logarithmic Binary search 7 ops 10 ops 20 ops
O(n) Linear Linear scan 100 1,000 1,000,000
O(n log n) Linearithmic Merge sort 664 9,966 19,931,568
O(n²) Quadratic Bubble sort 10,000 1,000,000 10¹²
O(2ⁿ) Exponential Naive TSP 10³⁰ — —

The difference between O(n log n) and O(n²) is the difference between a sort that handles a million records in 1 second and one that takes 12 days.

Formal definition: f(n) = O(g(n)) if there exist constants c > 0 and n₀ such that f(n) ≤ c·g(n) for all n ≥ n₀. In practice: keep only the fastest-growing term, drop coefficients.

Analysing an Algorithm

def find_duplicates(lst):          # n = len(lst)
    for i in range(len(lst)):      # n iterations
        for j in range(len(lst)):  # n iterations (inner)
            if i != j and lst[i] == lst[j]:
                return True
    return False

Inner loop runs n times for each of n outer iterations: O(n²).

Better approach:

def find_duplicates_fast(lst):
    seen = set()                   # O(1) lookup
    for x in lst:                  # n iterations
        if x in seen:              # O(1) average
            return True
        seen.add(x)                # O(1) average
    return False

Single loop, O(1) operations per iteration: O(n). For n=1,000,000: the first version does 10¹² comparisons; the second does 1,000,000.

Space Complexity

Runtime is not the only resource that scales. Memory usage also has a Big-O:

def sum_list(lst):
    total = 0              # O(1) space — one variable
    for x in lst:
        total += x
    return total           # Total: O(1) space

def reverse_list(lst):
    result = []            # O(n) space — new list same size as input
    for i in range(len(lst) - 1, -1, -1):
        result.append(lst[i])
    return result          # Total: O(n) space

There is often a space-time tradeoff: use more memory to get faster runtime (hash tables, memoisation) or use less memory at the cost of more computation (in-place sorts).

Recursion and the Recurrence Relation

Many algorithms are naturally recursive. Their complexity is expressed as a recurrence relation:

def binary_search(arr, target, low, high):
    if low > high:
        return -1
    mid = (low + high) // 2
    if arr[mid] == target:
        return mid
    elif arr[mid] < target:
        return binary_search(arr, target, mid + 1, high)
    else:
        return binary_search(arr, target, low, mid - 1)

At each step, the problem size halves: T(n) = T(n/2) + O(1). Solving: T(n) = O(log n).

The Master Theorem gives a formula for recurrences of the form T(n) = aT(n/b) + O(n^d):

  • If d > log_b(a): T(n) = O(n^d)
  • If d = log_b(a): T(n) = O(n^d log n)
  • If d < log_b(a): T(n) = O(n^(log_b a))

Merge sort: T(n) = 2T(n/2) + O(n), so a=2, b=2, d=1. log_2(2)=1=d → T(n) = O(n log n).

Greedy, Divide-and-Conquer, Dynamic Programming

These three paradigms cover most algorithm design:

Greedy: at each step, make the locally optimal choice and never reconsider.

  • Coin change (specific denominations), activity selection, Dijkstra's shortest path
  • Fast, simple — but often does not produce the global optimum

Divide and Conquer: split the problem into independent sub-problems, solve each, combine.

  • Merge sort, binary search, quicksort, fast Fourier transform
  • Enables O(n log n) where naive approaches are O(n²)

Dynamic Programming: break into overlapping sub-problems; store results to avoid recomputation.

  • Fibonacci, longest common subsequence, shortest path (Bellman-Ford), knapsack
  • Turns exponential recursion into polynomial iteration

Going Deeper

NP-completeness: some problems have no known polynomial-time algorithm. The Travelling Salesman Problem (find the shortest route through n cities) can be solved in O(n!) by brute force or O(n² × 2ⁿ) with dynamic programming — still exponential. No one has found a polynomial algorithm, but no one has proven one doesn't exist. This is the famous P vs NP question — one of the Millennium Prize Problems. If P=NP were proven, essentially all cryptography would be broken.

Amortised analysis: some data structures (dynamic arrays, hash tables) occasionally do expensive operations (resizing). The cost averaged over a sequence of operations — the amortised cost — is much lower. Python lists use amortised O(1) for append(): the list doubles in capacity when full, so n appends cost O(n) total, or O(1) per append amortised.

﻿# Module 5.4 — Recursion: Functions That Call Themselves

The Problem

Some problems are defined in terms of themselves. The factorial of n is n times the factorial of n-1. The height of a tree is one plus the maximum height of its subtrees. The files in a folder include all the files in all its subfolders.

Writing loops to solve these problems forces you to manage explicit stacks, state variables, and awkward index arithmetic. The code obscures the problem's natural structure.

Recursion expresses these problems directly — the code mirrors the definition.

The Story

Recursive Thinking Before Computers

Long before programming languages, mathematicians defined functions recursively. Giuseppe Peano (1889) defined the natural numbers recursively: 0 is a number; if n is a number, then the successor of n is a number. Ackermann's function (1928) was one of the first examples of a function that is computable but not primitive recursive — it grows faster than any fixed power of n.

In programming, recursive functions became possible once CPUs had the call stack (Module 4.2). The ability to call a function from within itself, with each call getting its own stack frame, is precisely what makes recursion work. Early languages like FORTRAN (1957) did not support recursion — function calls used a fixed return address, so a function calling itself would overwrite its own return address. ALGOL 60 introduced proper recursion with a hardware-supported call stack.

The Concept

The Structure of a Recursive Function

Every correct recursive function has two parts:

Base case: the simplest input that can be answered directly, without further recursion. Without a base case, the function recurses forever → stack overflow.

Recursive case: the function calls itself with a smaller version of the problem, moving toward the base case.

def factorial(n):
    # Base case
    if n <= 1:
        return 1
    # Recursive case: n! = n × (n-1)!
    return n * factorial(n - 1)

Trace for factorial(4):

factorial(4)
  → 4 × factorial(3)
       → 3 × factorial(2)
            → 2 × factorial(1)
                 → 1          (base case returns)
            ← 2 × 1 = 2
       ← 3 × 2 = 6
  ← 4 × 6 = 24

Each call waits on the stack until its sub-call returns. The call stack holds 4 frames simultaneously for factorial(4).

Stack Frames and Depth

Every recursive call creates a new stack frame (as shown in Module 4.2). The maximum recursion depth is limited by the stack size. Python's default limit is 1,000 frames:

import sys
print(sys.getrecursionlimit())   # 1000

def infinite(n):
    return infinite(n + 1)

infinite(0)  # RecursionError: maximum recursion depth exceeded

For problems that require deep recursion (trees with depth 10,000, files nested 500 levels), you need either:

  • An iterative solution using an explicit stack data structure
  • Tail call optimisation (TCO) — the compiler reuses the stack frame when the recursive call is the very last thing done (Python does not do TCO; Scheme requires it)
  • Increasing the stack size (risky)

Fibonacci — The Classic Trap

def fib_naive(n):
    if n <= 1: return n
    return fib_naive(n-1) + fib_naive(n-2)

This is O(2ⁿ) — exponential time. fib(50) takes about 10¹⁰ operations. The problem: the same sub-problems are computed repeatedly:

fib(5)
├── fib(4)
│   ├── fib(3)        ← computed again below
│   │   ├── fib(2)
│   │   └── fib(1)
│   └── fib(2)
└── fib(3)            ← duplicate
    ├── fib(2)        ← duplicate
    └── fib(1)

Memoisation fixes this in one line:

from functools import lru_cache

@lru_cache(maxsize=None)
def fib(n):
    if n <= 1: return n
    return fib(n-1) + fib(n-2)

Now O(n) — each sub-problem computed once, result cached. This is the core idea of dynamic programming: cache sub-problem results.

Recursion on Data Structures

Recursion shines on naturally recursive structures — particularly trees (covered in Level 6):

class TreeNode:
    def __init__(self, val, left=None, right=None):
        self.val   = val
        self.left  = left
        self.right = right

def tree_height(node):
    if node is None:           # base case: empty tree has height 0
        return 0
    left_h  = tree_height(node.left)   # height of left subtree
    right_h = tree_height(node.right)  # height of right subtree
    return 1 + max(left_h, right_h)    # this node adds 1

def tree_sum(node):
    if node is None: return 0
    return node.val + tree_sum(node.left) + tree_sum(node.right)

An iterative tree traversal requires an explicit stack. The recursive version is identical in structure to the mathematical definition.

Mutual Recursion

Two or more functions can call each other:

def is_even(n):
    if n == 0: return True
    return is_odd(n - 1)

def is_odd(n):
    if n == 0: return False
    return is_even(n - 1)

This is elegant but not efficient — use n % 2 == 0 in practice. The concept matters: parsers for context-free grammars are often built as mutually recursive functions, where each function handles one grammar rule.

Tower of Hanoi

The canonical recursive problem: move n disks from peg A to peg C, using peg B as auxiliary, without placing a larger disk on a smaller one.

def hanoi(n, source, target, auxiliary):
    if n == 1:
        print(f"Move disk 1 from {source} to {target}")
        return
    hanoi(n-1, source, auxiliary, target)   # move n-1 disks out of the way
    print(f"Move disk {n} from {source} to {target}")
    hanoi(n-1, auxiliary, target, source)   # move n-1 disks to target

hanoi(3, 'A', 'C', 'B')

The solution requires exactly 2ⁿ − 1 moves. There is no simpler way — the recursion captures the entire problem structure. The Tower of Hanoi is also a model for the recursive nature of the call stack itself: each invocation contains smaller subproblems, just as each disk move enables the next.

Going Deeper

Continuation-passing style (CPS): a transform that makes all recursive calls tail calls. Every recursive function can be converted to CPS, making it TCO-compatible. ﻿# Module 5.5 — Sorting: Putting Things in Order

The Problem

A database table has 50 million rows. A search engine needs to rank 10 billion web pages. A hospital system needs to sort 100,000 patient records by urgency in real time.

Sorting is one of the most fundamental operations in computing. It is estimated that 25% of all CPU time in the world is spent sorting. And the difference between a bad sort algorithm and a good one is the difference between a program that works and one that never finishes.

The Story

The Sorting Problem Drove Algorithm Theory

In the 1950s and 60s, IBM's core business was data processing — payroll, census tabulation, inventory management. Sorting punched cards and magnetic tape records was the bottleneck. IBM researchers spent enormous effort on sort algorithms because a 2× speedup in sort performance would save millions of dollars in computing time.

John von Neumann wrote Mergesort in 1945 — the first O(n log n) sort algorithm. Tony Hoare invented Quicksort in 1959 while working on machine translation at Moscow State University. The sorting problem was so important that it drove major theoretical advances: the proof that no comparison-based sort can be faster than O(n log n) in the worst case (the information-theoretic lower bound), and the discovery of Radix sort which breaks this barrier by not using comparisons.

The standard sort algorithm in production today (Timsort, used in Python, Java, and Android) was invented in 2002 by Tim Peters specifically for Python. It exploits real-world patterns in data — partially sorted runs — to achieve near-linear performance on common inputs.

The Concept

The Sorting Problem

Input: an array of n elements with a total order (we can compare any two elements).
Output: the same elements in non-decreasing order.
Constraint: we count comparisons and swaps; we want to minimise them.

Bubble Sort — O(n²) — The Slow Baseline

def bubble_sort(arr):
    n = len(arr)
    for i in range(n):
        for j in range(0, n - i - 1):
            if arr[j] > arr[j + 1]:
                arr[j], arr[j + 1] = arr[j + 1], arr[j]

Each pass "bubbles" the largest unsorted element to its final position. n passes × n comparisons each = O(n²).

In practice: never use bubble sort. It is taught because it is simple to understand and implement, but its performance is catastrophically bad for n > 1,000.

Merge Sort — O(n log n) — Guaranteed

def merge_sort(arr):
    if len(arr) <= 1:
        return arr
    mid = len(arr) // 2
    left  = merge_sort(arr[:mid])    # sort left half
    right = merge_sort(arr[mid:])    # sort right half
    return merge(left, right)        # merge two sorted halves

def merge(left, right):
    result = []
    i = j = 0
    while i < len(left) and j < len(right):
        if left[i] <= right[j]:
            result.append(left[i]); i += 1
        else:
            result.append(right[j]); j += 1
    result.extend(left[i:])
    result.extend(right[j:])
    return result

Why O(n log n)?
Divide: log₂(n) levels of recursion. Each level merges total n elements. Total: n × log n comparisons.

Stable: elements with equal keys maintain their original relative order.
Not in-place: requires O(n) extra space for the merge step.
Predictable: always O(n log n), never worse. Preferred when worst-case matters (e.g., real-time systems).

Quick Sort — O(n log n) average, O(n²) worst

def quick_sort(arr, low=0, high=None):
    if high is None: high = len(arr) - 1
    if low < high:
        p = partition(arr, low, high)
        quick_sort(arr, low, p - 1)
        quick_sort(arr, p + 1, high)

def partition(arr, low, high):
    pivot = arr[high]    # choose last element as pivot
    i = low - 1
    for j in range(low, high):
        if arr[j] <= pivot:
            i += 1
            arr[i], arr[j] = arr[j], arr[i]
    arr[i+1], arr[high] = arr[high], arr[i+1]
    return i + 1

Pivot selection is everything. With a good pivot (median-of-three, random), the array splits roughly in half each time: O(n log n). With the worst pivot (always the smallest or largest element, e.g., sorted input with naive pivot choice): one partition gets n-1 elements → O(n²).

In-place: O(log n) stack space for recursion, O(1) extra space otherwise.
Cache-friendly: accesses memory sequentially — excellent real-world performance.
Not stable: equal elements may be reordered.

In practice, Quicksort with randomised or median-of-three pivot is faster than Mergesort on random data by a constant factor, despite the same O(n log n) asymptotics.

Heap Sort — O(n log n), in-place

Builds a max-heap from the array (O(n)), then repeatedly extracts the maximum (O(log n) each × n times).

  • Always O(n log n), in-place, not stable
  • Cache-unfriendly (heap accesses jump around memory)
  • Used when guaranteed in-place O(n log n) is required

Radix Sort — O(nk) — Beats the Lower Bound

The O(n log n) lower bound applies only to comparison-based sorts. Radix sort does not compare elements — it distributes them into buckets by individual digits.

def radix_sort(arr, base=10):
    max_val = max(arr)
    exp = 1
    while max_val // exp > 0:
        counting_sort_by_digit(arr, base, exp)
        exp *= base

For 32-bit integers with base 256: 4 passes, each O(n) → O(4n) = O(n). In practice, the constant factor is large, and Radix sort is only faster than comparison sorts for very large n with bounded key size (e.g., sorting IP addresses, DNA sequences).

Timsort — The Real-World Champion

Python's built-in sorted() and list.sort() use Timsort (Tim Peters, 2002):

  1. Find natural runs of already-sorted data in the input (forward or backward)
  2. Ensure each run is at least minrun elements (typically 32–64) using insertion sort
  3. Merge runs pairwise using a merge sort variant with "galloping" mode for runs with long sequential matches

Best case: O(n) on already-sorted data (just finds one run).
Average/worst case: O(n log n).
Stable and adaptive: exploits existing order in the data.
Used in: Python, Java (Arrays.sort for objects), Android, V8 (JavaScript engine).

The Lower Bound Proof

Theorem: any comparison-based sort requires Ω(n log n) comparisons in the worst case.

Proof sketch: think of all possible orderings of n elements — there are n! of them. Each comparison eliminates at most half the remaining possibilities (binary decision tree with n! leaves). The tree has height at least log₂(n!) ≈ n log n (Stirling's approximation). Therefore, at least n log n comparisons are needed in the worst case. □

No comparison sort can do better. Mergesort and Heapsort achieve this bound.

Going Deeper

External sorting: what if the data doesn't fit in RAM? Sorting 1 TB on a machine with 16 GB RAM requires a disk-based sort. ﻿# Module 5.6 — Searching: Finding What You Need

The Problem

A phone book has 5 million entries. Finding a name by scanning every entry takes minutes. Finding it by binary search takes microseconds.

Google's index has 100 billion web pages. Finding pages matching a query in under 100 milliseconds requires not just a fast search algorithm but an entirely different data structure designed for search from the ground up.

Searching is the inverse of sorting, and understanding how to find things efficiently — from a sorted array, an unsorted collection, a graph, or a text string — is foundational to almost every software system ever built.

The Story

From Card Catalogues to Search Engines

Before computers, librarians invented efficient search structures: alphabetical catalogues, Dewey Decimal classification, card indexes. These were manual implementations of data structures designed to reduce lookup time from O(n) (scan every card) to O(log n) (binary search through a sorted index).

Vannevar Bush (1945) described the Memex in his essay "As We May Think" — a hypothetical device that could store and rapidly retrieve vast amounts of information using associative links. This vision directly inspired hypertext and the web.

The first web search engine, Archie (1990), simply indexed FTP filenames. AltaVista (1995) indexed full page text. Google (1998) introduced PageRank — ranking by link structure rather than just keyword frequency — and transformed search from a text-matching problem into a graph analysis problem. Today, a Google search traverses an index of 100 billion pages in under 100ms on a cluster of thousands of machines.

The Concept

Linear Search — O(n)

The simplest possible search: check every element until you find the target or exhaust the collection.

def linear_search(arr, target):
    for i, x in enumerate(arr):
        if x == target:
            return i      # found at index i
    return -1             # not found

When to use: unsorted data, small collections (n < ~50), or when you need to find all occurrences.
When not to use: large sorted collections — binary search is orders of magnitude faster.

Binary Search — O(log n)

Requires the array to be sorted. At each step, compare the target to the middle element and eliminate half the remaining search space.

def binary_search(arr, target):
    low, high = 0, len(arr) - 1
    while low <= high:
        mid = (low + high) // 2
        if arr[mid] == target:
            return mid
        elif arr[mid] < target:
            low = mid + 1    # target is in the right half
        else:
            high = mid - 1   # target is in the left half
    return -1                 # not found

Why O(log n)? Each comparison halves the remaining search space. Starting with n elements, after k comparisons we have n/2^k elements left. When n/2^k = 1, k = log₂(n). For n = 1,000,000: at most 20 comparisons.

Invariant: at every iteration, if the target exists, it is in arr[low..high]. Maintaining this invariant is the key to getting the boundary conditions right.

Common mistakes:

  • Off-by-one in mid + 1 / mid - 1 — leads to infinite loops or missed elements
  • Integer overflow in (low + high) // 2 for very large arrays (use low + (high - low) // 2 in C)

Binary Search Variants

Binary search has many useful generalisations:

Find first occurrence of target (duplicates in array):

def first_occurrence(arr, target):
    low, high, result = 0, len(arr) - 1, -1
    while low <= high:
        mid = (low + high) // 2
        if arr[mid] == target:
            result = mid
            high = mid - 1   # keep searching left for earlier occurrence
        elif arr[mid] < target:
            low = mid + 1
        else:
            high = mid - 1
    return result

Find insertion point (like Python's bisect.bisect_left): Returns the index where target should be inserted to keep the array sorted.

Search on answer — a powerful technique: binary search on the answer space rather than the data. For example: "what is the minimum speed at which I can complete a task within T hours?" Binary search over possible speeds, using a feasibility function to check each candidate.

Hash Tables — O(1) Average

Binary search requires sorted data and gives O(log n). For O(1) average-case search, we use a hash table (covered in depth in Level 6):

d = {'alice': 30, 'bob': 25, 'carol': 28}
d['alice']        # O(1) average — hash lookup
'bob' in d        # O(1) average

The hash function maps the key to an array index. Lookup: hash the key, go directly to that index. No comparisons needed. The price: hash tables use more memory, and worst-case is O(n) if many keys hash to the same slot.

Graph Search — BFS and DFS

When data has relationships (not just linear order), we need graph search. Covered fully in Level 6 (Module 6.6), but the foundations are:

Breadth-First Search (BFS): explore level by level, using a queue.

  • Finds the shortest path (fewest edges) in an unweighted graph
  • O(V + E) where V = vertices, E = edges

Depth-First Search (DFS): go as deep as possible before backtracking, using a stack (or recursion).

  • Detects cycles, topological sort, connected components
  • O(V + E)

String Search — KMP Algorithm

Finding a pattern of length m within a text of length n. Naive: try every position → O(nm). The Knuth-Morris-Pratt (KMP) algorithm preprocesses the pattern to avoid redundant comparisons → O(n + m).

Text:     AAABAAABAAAC
Pattern:  AAABAAAC

Naive: would restart from scratch on each mismatch
KMP: uses a failure function to skip characters already matched

The core idea: when a mismatch occurs, the pattern's internal structure tells us how far to shift without losing already-matched characters. This makes substring search in a 1GB log file fast enough to be done in seconds.

Trie — O(m) Prefix Search

A trie (prefix tree) stores strings as paths in a tree where each node is a character:

Insert: "cat", "car", "card", "care", "bat"

         root
        /    \
       c      b
       |      |
       a      a
      / \     |
     t   r    t
         |
        d/e

Lookup: "care" → follow c→a→r→e. O(m) where m = string length, regardless of how many strings are stored. Tries enable prefix-based autocomplete: finding all words starting with "car" takes O(m + output size).

Bloom filters: a probabilistic data structure that can answer "is this element in the set?" with no false negatives and a configurable false positive rate, using a fraction of the memory of a hash table. The tradeoff: you cannot enumerate elements, and you cannot delete elements without a counting variant.

B-trees and database indices: database tables with millions of rows need search in O(log n) disk accesses. A B-tree keeps all data sorted in a balanced tree where each node holds many keys — a typical node fills one disk page (4–16 KB). This minimises disk reads. B-trees are the data structure behind almost every database index ever built. Level 9 covers them in detail.

import math
def min_speed(tasks, hours):
    def can_finish(speed):
        return sum(math.ceil(t/speed) for t in tasks) <= hours

    low, high = 1, max(tasks)
    while low < high:
        mid = (low+high)//2
        if can_finish(mid): high=mid
        else: low=mid+1
    return low

▸ Part E

Single search: linear O(n) < sort O(n log n) + binary O(log n). Linear wins.

k searches: sort cost O(n log n) is paid once. After that, k binary searches = O(k log n). Break-even: k log n < k×(n/2), roughly k > n log n / (n/2 - log n) ≈ 2 log n for large n. For n=1000: break-even at about k ≈ 20 searches.
