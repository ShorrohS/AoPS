﻿# Module 10.1 — HTML, CSS, and JavaScript from the Ground Up

The Problem

In 1991, Tim Berners-Lee needed a way to share documents between physicists at CERN. He invented three technologies that now power virtually all interactive software: a markup language to structure content (HTML), a styling language to control appearance (CSS), and a scripting language to add behaviour (JavaScript).

Every web page — from a simple blog to a complex trading platform — is built from these three technologies, working together. Understanding them from first principles reveals why the modern web is the way it is, warts and all.

The Story

HTML, CSS, JavaScript: Three Accidents of History

HTML was designed for documents, not applications. The tags (<h1>, <p>, <a>) were meant to describe content structure, not visual layout. The early <blink> and <marquee> tags for visual effects were embarrassments that browsers eventually stopped supporting.

CSS was designed by Håkon Wium Lie (1994) to separate presentation from content. Before CSS, HTML authors used <font> tags, <table> for layout, and bgcolor attributes everywhere — mixing content with presentation in ways that were impossible to maintain.

JavaScript was invented by Brendan Eich at Netscape in 10 days in 1995. The original goal: add simple interactivity to web pages. It was designed quickly, with deliberate Java-like syntax to appeal to Java programmers, but with dynamic typing and prototype-based objects — very different from Java. Every strange corner of JavaScript (type coercion, this binding, var hoisting) is a direct consequence of that 10-day timeline.

These three technologies were standardised by the W3C and ECMA, evolved separately, and are now deeply intertwined — the foundation of all web development.

The Concept

HTML — Structure

HTML (HyperText Markup Language) describes the semantic structure of content:

<!DOCTYPE html>
<html lang="en">
<head>
  <meta charset="UTF-8">
  <meta name="viewport" content="width=device-width, initial-scale=1.0">
  <title>My Page</title>
  <link rel="stylesheet" href="styles.css">
</head>
<body>
  <header>
    <h1>Welcome</h1>
    <nav>
      <a href="/">Home</a>
      <a href="/about">About</a>
    </nav>
  </header>
  <main>
    <article>
      <h2>Article Title</h2>
      <p>First paragraph. <strong>Important word.</strong></p>
      <p>Second paragraph.</p>
    </article>
  </main>
  <footer>
    <p>&copy; 2026</p>
  </footer>
</body>
</html>

Semantic HTML: use the right element for the right content. <article> for self-contained content. <nav> for navigation. <button> for buttons (not <div>). <input type="email"> for email fields. Semantic HTML improves:

  • Accessibility: screen readers use semantics to navigate
  • SEO: search engines weight headings and semantic elements
  • Maintainability: clear meaning for developers

The DOM (Document Object Model): the browser parses HTML and creates a tree of objects. JavaScript can read and modify this tree, dynamically updating the page.

CSS — Presentation

CSS (Cascading Style Sheets) controls visual appearance through selectors and declarations:

/* Selector: element */
h1 { color: #1C1C1C; font-size: 2rem; }

/* Selector: class */
.card { background: white; border-radius: 8px; padding: 16px; }

/* Selector: ID */
#main-nav { display: flex; gap: 24px; }

/* Selector: pseudo-class */
a:hover { text-decoration: underline; }

/* Selector: descendant */
.card p { color: #666; font-size: 0.9rem; }

The Box Model: every HTML element is a rectangular box:

┌─────────────────────────────────────────┐
│                 MARGIN                  │
│  ┌───────────────────────────────────┐  │
│  │             BORDER                │  │
│  │  ┌─────────────────────────────┐  │  │
│  │  │           PADDING           │  │  │
│  │  │  ┌────────────────────┐     │  │  │
│  │  │  │      CONTENT       │     │  │  │
│  │  │  └────────────────────┘     │  │  │
│  │  └─────────────────────────────┘  │  │
│  └───────────────────────────────────┘  │
└─────────────────────────────────────────┘

Flexbox — one-dimensional layout:

.container {
  display: flex;
  justify-content: space-between;  /* horizontal distribution */
  align-items: center;             /* vertical alignment */
  gap: 16px;
}

CSS Grid — two-dimensional layout:

.grid {
  display: grid;
  grid-template-columns: repeat(3, 1fr);  /* 3 equal columns */
  grid-template-rows: auto;
  gap: 24px;
}

Cascade and Specificity: when multiple rules target the same element, the most specific wins:

  • Inline style: style="color:red" (specificity: 1000)
  • ID selector: #id (specificity: 100)
  • Class selector: .class (specificity: 10)
  • Element selector: p (specificity: 1)
  • !important overrides everything (use sparingly)

JavaScript — Behaviour

JavaScript makes pages interactive. Core concepts:

// Variables
let count = 0;           // block-scoped, reassignable
const PI = 3.14159;      // block-scoped, not reassignable
var legacy = "avoid";    // function-scoped, hoisted (legacy)

// Functions
function add(a, b) { return a + b; }
const multiply = (a, b) => a * b;   // arrow function

// DOM manipulation
const btn = document.querySelector('#submit-btn');
btn.addEventListener('click', function(event) {
  event.preventDefault();             // stop form submission
  const input = document.querySelector('#name');
  const message = document.querySelector('#message');
  message.textContent = `Hello, ${input.value}!`;
  message.style.color = 'green';
});

// Fetch API — HTTP requests from JavaScript
async function fetchUser(id) {
  const response = await fetch(`/api/users/${id}`);
  if (!response.ok) throw new Error(`HTTP ${response.status}`);
  const data = await response.json();
  return data;
}

Event-driven model: JavaScript runs in an event loop. No blocking I/O. Events (clicks, timers, network responses) are queued and handled one at a time. This is the same model as Node.js on the server.

Promises and async/await:

// Old way: callback hell
fetchUser(1, function(user) {
  fetchOrders(user.id, function(orders) {
    renderPage(user, orders);
  });
});

// Modern way: async/await
async function loadPage() {
  try {
    const user   = await fetchUser(1);
    const orders = await fetchOrders(user.id);
    renderPage(user, orders);
  } catch (err) {
    showError(err.message);
  }
}

How the Three Work Together

<!-- HTML: structure -->
<button id="counter-btn" class="btn-primary">
  Clicked <span id="count">0</span> times
</button>

/* CSS: appearance */
.btn-primary {
  background: #1C2D42;
  color: white;
  padding: 12px 24px;
  border: none;
  border-radius: 4px;
  cursor: pointer;
  font-size: 1rem;
}
.btn-primary:hover { background: #2a3f5c; }

// JavaScript: behaviour
let count = 0;
const btn  = document.getElementById('counter-btn');
const span = document.getElementById('count');

btn.addEventListener('click', () => {
  count++;
  span.textContent = count;
});

Separation of concerns: HTML defines what is there, CSS defines how it looks, JavaScript defines what it does.

Going Deeper

Virtual DOM: React, Vue, and other frameworks don't directly modify the real DOM — they maintain a virtual representation in JavaScript objects, diff it when state changes, and apply only the minimal set of real DOM changes. This is faster because DOM operations are expensive (they trigger browser layout and paint). Understanding why the virtual DOM was invented requires experiencing the performance problems of naive DOM manipulation.

CSS preprocessors and modern tooling: writing raw CSS for large applications is painful — no variables (before CSS custom properties), no nesting, no modules. SASS and LESS added these features as preprocessors. Modern CSS has custom properties (--color: #1C2D42;), nesting (in newer browsers), and @layer for cascade management. PostCSS transforms future CSS syntax for current browsers. Understanding the gap between what developers write and what browsers receive is essential for modern frontend work.

let tasks = [];
let nextId = 1;

function addTask(text) {
    tasks.push({ id: nextId++, text, completed: false });
    saveToStorage();
    renderTasks(currentFilter);

function toggleTask(id) {
    const t = tasks.find(t => t.id === id);
    if (t) { t.completed = !t.completed; saveToStorage(); renderTasks(currentFilter); }

function deleteTask(id) {

function saveToStorage() { localStorage.setItem('tasks', JSON.stringify(tasks)); }
function loadFromStorage() {
    const raw = localStorage.getItem('tasks');
    tasks = raw ? JSON.parse(raw) : [];
    nextId = tasks.reduce((max, t) => Math.max(max, t.id), 0) + 1;
}

﻿# Module 10.2 — How Browsers Render Pages

The Problem

You type a URL. 0.5 seconds later, a fully-rendered web page appears. What happened?

Between the DNS lookup and the pixels on screen, the browser does an enormous amount of work: network requests, parsing, style calculation, layout, painting, and compositing. Understanding this pipeline explains why some pages feel instant and others feel sluggish — and how to make the difference.

The Story

Browsers as the World's Most Complex Applications

The first graphical web browser, NCSA Mosaic (1993), was revolutionary but simple. It downloaded an HTML file, parsed it sequentially, and drew text and images on screen.

Modern browsers — Chrome, Firefox, Safari, Edge — are among the most complex software systems ever built. Chrome has over 35 million lines of code. The rendering engine alone (Blink, forked from WebKit in 2013) handles HTML5, CSS3, JavaScript ES2022, WebGL, WebAssembly, WebRTC, service workers, and hundreds of other standards.

The performance of rendering directly affects user experience. Google's research showed a 100ms delay in search results caused a 0.2% reduction in searches. Amazon found every 100ms increase in page load time cost 1% in revenue. This commercial pressure drove massive investment in browser performance optimisation.

The Concept

The Critical Rendering Path

1. DNS lookup
2. TCP connection + TLS handshake
3. HTTP request/response
4. Receive HTML bytes
       ↓
5. Parse HTML → DOM tree
6. Parse CSS → CSSOM tree
       ↓
7. Combine → Render Tree
       ↓
8. Layout (Reflow) — calculate position and size
       ↓
9. Paint — draw pixels for each element
       ↓
10. Composite — layer pixels onto screen

Step 1–3: Network

The browser resolves the hostname via DNS, opens a TCP connection, performs a TLS handshake (for HTTPS), and sends an HTTP GET request. First byte arrives after 1–2 RTTs minimum.

Time to First Byte (TTFB): how long until the browser receives the first byte of the response. Optimised by CDNs (serve from geographically closer servers) and server-side caching.

Step 4–6: Parsing

HTML parsing → DOM: The browser parses HTML incrementally as bytes arrive — it does not wait for the entire document. Parsing is deliberately error-tolerant (browsers handle malformed HTML without crashing):

<html><body><h1>Title</h1><p>Text</p></body></html>

↓

Document
  └── html
        └── body
              ├── h1
              │    └── "Title"
              └── p
                   └── "Text"

CSS parsing → CSSOM: CSS is render-blocking: the browser cannot render any part of the page until all CSS is loaded and parsed. Why? Because any element might be affected by any CSS rule — the browser cannot start rendering until it knows the complete styles.

h1 { color: red; font-size: 2rem; }
p  { color: #333; margin: 16px 0; }

↓

CSSStyleSheet
  ├── Rule: h1 → {color:red, font-size:2rem}
  └── Rule: p  → {color:#333, margin:16px 0}

JavaScript is also render-blocking (unless marked async or defer): when the HTML parser encounters a <script> tag, it stops parsing HTML, downloads the script, executes it, then resumes. JavaScript can modify the DOM and CSSOM, so the browser must pause to maintain consistency.

<!-- Blocking: parser stops until script downloads and executes -->
<script src="app.js"></script>

<!-- async: download in parallel, execute immediately when ready -->
<script src="analytics.js" async></script>

<!-- defer: download in parallel, execute after HTML parsed -->
<script src="app.js" defer></script>

Step 7: Render Tree

The render tree combines DOM + CSSOM. It includes only visible elements:

  • display: none elements are excluded
  • visibility: hidden elements are included (space reserved, but invisible)
  • Pseudo-elements (::before, ::after) are added

Each node in the render tree knows its computed styles.

Step 8: Layout (Reflow)

The browser calculates the exact position and size of every element in the render tree. This involves:

  • Computing text flow (line breaking, word wrapping)
  • Resolving percentage widths relative to parent
  • Computing margins, paddings, borders
  • Handling flexbox/grid layout algorithms

Layout is expensive and cascading: changing the width of a parent may require re-laying out all its descendants. This is called reflow. Operations that trigger reflow include:

  • Changing any CSS property that affects size or position
  • Inserting or removing DOM elements
  • Reading offsetWidth, scrollTop, getBoundingClientRect() — forces synchronous layout ("layout thrashing")

Step 9: Paint

The browser creates drawing commands for each visible element — backgrounds, borders, text, shadows, images. This creates a list of painting operations but does not yet produce pixels.

Layers: elements that need to be painted independently (due to animations, will-change, position: fixed, overflow: scroll, etc.) are promoted to their own compositor layer — drawn once and cached as a texture.

Step 10: Composite

The GPU composites (combines) all layers into the final frame. Operations handled entirely by the compositor (no layout or paint triggered):

  • CSS transform: translate/rotate/scale
  • CSS opacity
  • CSS filter

This is why CSS animations of transform and opacity are smooth (60 fps) while animating top, left, or margin causes jank (triggers layout on every frame).

Performance: 60fps and the 16ms Budget

The human eye perceives motion as smooth at 60 frames per second. Each frame must be rendered in 16.67ms (1000ms ÷ 60). For a smooth animation:

  • JavaScript execution: < 10ms
  • Rendering pipeline: < 6ms

If JavaScript takes longer than ~50ms, users notice jank. Profile with Chrome DevTools → Performance tab.

Key optimisations:

  • Minimise reflows: batch DOM reads and writes, use requestAnimationFrame
  • Avoid layout thrashing: don't read and write layout properties in a loop
  • Use transform and opacity for animations (compositor only)
  • Use will-change: transform to promote elements to their own layer
  • Load JavaScript deferred or async; load CSS in <head>

Going Deeper

Service Workers: a script that runs in the background, separate from the web page, intercepting network requests. Can cache resources and serve them from cache even offline. The foundation of Progressive Web Apps (PWAs). A service worker acts as a proxy between the browser and the network — it can return cached responses, generate synthetic responses, or pass through to the real network.

WebAssembly (WASM): a binary instruction format that runs in browsers at near-native speed. C, C++, Rust, and Go programs can be compiled to WASM and run in browsers — enabling applications like Figma, Google Earth, and Doom to run in the browser without plugins. WASM does not replace JavaScript — they work together. WASM handles compute-intensive tasks; JavaScript handles DOM manipulation and web APIs.

Part B — Layout Thrashing

const boxes = document.querySelectorAll('.box');

﻿# Module 10.3 — REST APIs and JSON

The Problem

A mobile app, a web frontend, a desktop app, and a third-party service all need to share the same data and functionality.

You cannot share code — they run on different platforms. You cannot share a database — that would be a security nightmare.

You need a standard way for these different systems to communicate. A contract that says: send this request, get that response.

That contract is the API (Application Programming Interface), and for web services, the dominant style is REST using JSON.

The Story

REST: A Style, Not a Standard

Roy Fielding defined REST (Representational State Transfer) in his 2000 PhD dissertation at UC Irvine. Fielding was one of the primary authors of HTTP/1.1; REST was his architectural analysis of why the web worked so well and how to apply those same principles to designing APIs.

REST is not a protocol or a specification — it is a set of architectural constraints. An API that follows these constraints is called "RESTful."

Before REST, web services typically used SOAP (Simple Object Access Protocol) — XML-based, rigid, complex, with extensive tooling requirements. SOAP dominated enterprise software in the early 2000s. REST replaced it because it was simpler: use HTTP verbs and URLs you already understand, and JSON instead of XML.

JSON (JavaScript Object Notation) was popularised by Douglas Crockford around 2001. It was not invented — it was discovered as a subset of JavaScript that worked as a data interchange format. Simpler than XML (no closing tags), directly parseable by JavaScript, and human-readable.

The Concept

JSON — Data Format

{
  "id": 1,
  "name": "Alice Johnson",
  "email": "alice@example.com",
  "age": 30,
  "address": {
    "street": "123 Main St",
    "city": "New York",
    "country": "US"
  },
  "tags": ["developer", "python", "aws"],
  "active": true,
  "score": 98.5,
  "deleted_at": null
}

JSON data types: string (double quotes), number (int or float), boolean (true/false), null, object ({}), array ([]).

JSON in Python:

import json

# Parse JSON string → Python dict
data = json.loads('{"name": "Alice", "age": 30}')
print(data['name'])      # Alice

# Serialize Python → JSON string
obj = {'name': 'Bob', 'scores': [95, 87, 92]}
text = json.dumps(obj, indent=2)
# {
#   "name": "Bob",
#   "scores": [95, 87, 92]
# }

REST Architectural Constraints

  1. Client-Server: separate concerns — client handles UI, server handles data
  2. Stateless: each request contains all information needed; server stores no session state per client
  3. Cacheable: responses indicate whether they can be cached
  4. Uniform Interface: consistent URLs and HTTP methods (the key constraint)
  5. Layered System: client doesn't know if it's talking to the real server or a load balancer/cache
  6. Code on Demand (optional): server can send executable code (JavaScript)

RESTful API Design

Resources (nouns) map to URLs. HTTP methods (verbs) define the action:

GET    /users           → list all users
GET    /users/42        → get user 42
POST   /users           → create a new user
PUT    /users/42        → replace user 42 entirely
PATCH  /users/42        → partially update user 42
DELETE /users/42        → delete user 42

GET    /users/42/orders → list orders for user 42
POST   /users/42/orders → create an order for user 42
GET    /orders/7        → get a specific order (can also go here)

URL design rules:

  • Use nouns, not verbs: /users/42 not /getUser?id=42
  • Use plural nouns: /users not /user
  • Nest for relationships: /users/42/orders
  • Keep it flat when possible: /orders?user_id=42 is fine
  • Versioning: /api/v1/users or Accept: application/vnd.api+json;version=1

Request and Response Format

Creating a user (POST):

Request:

POST /api/v1/users HTTP/1.1

Content-Type: application/json
Authorization: Bearer eyJhbGciOiJIUzI1NiJ9...

}

Response:

{

  "name": "Alice Johnson",

Error response (validation failure):

HTTP/1.1 422 Unprocessable Entity
Content-Type: application/json

{
  "error": "validation_failed",
  "message": "Request validation failed",

    {"field": "name", "code": "too_short", "message": "Name must be at least 2 characters"}
  ]
}

Building a REST API with Python (Flask)

from flask import Flask, request, jsonify, abort

app = Flask(__name__)

# In-memory store (use a database in production)
users = {1: {'id':1,'name':'Alice','email':'alice@example.com'}}
next_id = 2

@app.route('/api/v1/users', methods=['GET'])
def list_users():
    return jsonify(list(users.values()))

@app.route('/api/v1/users/<int:user_id>', methods=['GET'])
def get_user(user_id):
    user = users.get(user_id)
    if not user: abort(404, description=f"User {user_id} not found")
    return jsonify(user)

@app.route('/api/v1/users', methods=['POST'])
def create_user():
    global next_id
    data = request.get_json()
    if not data or 'name' not in data or 'email' not in data:
        abort(400, description="name and email are required")
    user = {'id': next_id, 'name': data['name'], 'email': data['email']}
    users[next_id] = user
    next_id += 1
    return jsonify(user), 201

@app.route('/api/v1/users/<int:user_id>', methods=['DELETE'])
def delete_user(user_id):
    if user_id not in users: abort(404)
    del users[user_id]
    return '', 204

@app.errorhandler(404)
def not_found(e): return jsonify(error=str(e)), 404

@app.errorhandler(400)
def bad_request(e): return jsonify(error=str(e)), 400

Authentication

API Keys: simplest form. Include in header: Authorization: ApiKey abc123. No expiry, hard to revoke per-user.

JWT (JSON Web Token): a signed token containing claims (user ID, roles, expiry). The server can verify the token without database lookup — stateless authentication.

import jwt, datetime

SECRET = 'your-secret-key'

def create_token(user_id):
    return jwt.encode({
        'sub': user_id,
        'exp': datetime.datetime.utcnow() + datetime.timedelta(hours=24),
        'iat': datetime.datetime.utcnow()
    }, SECRET, algorithm='HS256')

def verify_token(token):
    return jwt.decode(token, SECRET, algorithms=['HS256'])

OAuth 2.0: industry standard for delegated authorisation. "Login with Google" — the user grants your app limited access to their Google data without sharing their password.

Going Deeper

GraphQL: an alternative to REST invented by Facebook (2015). Instead of multiple endpoints, there is one endpoint (/graphql) and you specify exactly what data you want in the request body. Benefits: no over-fetching (getting more data than needed) or under-fetching (needing multiple requests to get all needed data). Trade-offs: more complex server implementation, harder caching, N+1 query problems. Used heavily in modern frontend apps.

OpenAPI (Swagger): a specification format for describing REST APIs. An openapi.yaml file describes all endpoints, parameters, request/response schemas, and authentication. From this file: generate client SDKs in any language, generate interactive documentation (Swagger UI), validate requests and responses automatically. Most production REST APIs publish an OpenAPI spec.

﻿# Module 10.4 — Full-Stack Project

The Problem

You have learned:

  • HTML, CSS, JavaScript (frontend)
  • HTTP and REST APIs (communication layer)
  • Databases and SQL (data persistence)
  • Sockets and servers (networking)

But these skills in isolation do not make a working application. A real application is these layers working together: a user clicks a button in the browser → JavaScript sends an HTTP request → a server receives and validates it → queries a database → returns structured data → JavaScript renders the result on screen.

This module integrates everything by building a complete, working application from scratch.

The Story

The Full Stack Emerges

The term "full stack" was popularised around 2008–2012 as web applications became increasingly complex. The LAMP stack (Linux, Apache, MySQL, PHP) was an early full-stack: PHP generated HTML server-side, MySQL stored data.

AJAX (Asynchronous JavaScript and XML, named ~2005) changed the model: instead of the server rendering complete HTML pages, JavaScript would fetch data (via XMLHttpRequest) and update the page dynamically. Google Maps (2005) demonstrated this spectacularly — panning a map didn't reload the page.

Modern full-stack typically means: a JavaScript or TypeScript frontend (React, Vue, Angular), a backend API (Node.js, Python, Go, Java), and a database (PostgreSQL, MySQL, MongoDB). The frontend and backend communicate via JSON REST APIs or GraphQL.

The Concept

Application Architecture

A modern full-stack web application has three tiers:

┌─────────────────────────────────────────────────────┐
│   BROWSER (Client)                                  │
│   HTML/CSS/JavaScript                               │
│   React / Vue / plain JS                            │
│   Fetches data from API                             │
└──────────────────────────┬──────────────────────────┘
                           │ HTTP/REST (JSON)
┌──────────────────────────▼──────────────────────────┐
│   WEB SERVER (Backend)                              │
│   Python/Flask, Node.js/Express, etc.              │
│   Handles requests, applies business logic         │
│   Authentication, validation, authorisation        │
└──────────────────────────┬──────────────────────────┘
                           │ SQL / ORM
┌──────────────────────────▼──────────────────────────┐

The Project: A Task Manager

Build a simple but complete task manager app:

  • Mark tasks as complete

# app.py
from flask import Flask, request, jsonify
from flask_cors import CORS
import sqlite3, json
from datetime import datetime

app = Flask(__name__)
CORS(app)  # allow browser requests from different origin

DB = 'tasks.db'

def get_db():
    conn = sqlite3.connect(DB)
    conn.row_factory = sqlite3.Row  # rows as dicts
    return conn

def init_db():
    with get_db() as db:
        db.execute('''
            CREATE TABLE IF NOT EXISTS tasks (
                id          INTEGER PRIMARY KEY AUTOINCREMENT,
                title       TEXT NOT NULL,
                description TEXT,
                due_date    TEXT,
                completed   INTEGER DEFAULT 0,
                created_at  TEXT DEFAULT (datetime('now'))
            )
        ''')

@app.route('/api/tasks', methods=['GET'])
def list_tasks():
    status = request.args.get('status')   # ?status=pending or ?status=completed
    with get_db() as db:
        if status == 'pending':
            rows = db.execute('SELECT * FROM tasks WHERE completed=0 ORDER BY created_at DESC').fetchall()
        elif status == 'completed':
            rows = db.execute('SELECT * FROM tasks WHERE completed=1 ORDER BY created_at DESC').fetchall()
        else:
            rows = db.execute('SELECT * FROM tasks ORDER BY created_at DESC').fetchall()
    return jsonify([dict(r) for r in rows])

@app.route('/api/tasks', methods=['POST'])
def create_task():
    data = request.get_json()
    if not data or not data.get('title'):
        return jsonify(error='title is required'), 400
    with get_db() as db:
        cursor = db.execute(
            'INSERT INTO tasks (title, description, due_date) VALUES (?, ?, ?)',
            (data['title'], data.get('description'), data.get('due_date'))
        )
        task_id = cursor.lastrowid
        task = dict(db.execute('SELECT * FROM tasks WHERE id=?', (task_id,)).fetchone())
    return jsonify(task), 201

@app.route('/api/tasks/<int:task_id>', methods=['PATCH'])
def update_task(task_id):
    data = request.get_json()
    with get_db() as db:
        task = db.execute('SELECT * FROM tasks WHERE id=?', (task_id,)).fetchone()
        if not task: return jsonify(error='not found'), 404
        if 'completed' in data:
            db.execute('UPDATE tasks SET completed=? WHERE id=?', (int(data['completed']), task_id))
        if 'title' in data:
            db.execute('UPDATE tasks SET title=? WHERE id=?', (data['title'], task_id))
        updated = dict(db.execute('SELECT * FROM tasks WHERE id=?', (task_id,)).fetchone())
    return jsonify(updated)

@app.route('/api/tasks/<int:task_id>', methods=['DELETE'])
def delete_task(task_id):
    with get_db() as db:
        result = db.execute('DELETE FROM tasks WHERE id=?', (task_id,))
        if result.rowcount == 0: return jsonify(error='not found'), 404
    return '', 204

init_db()
if __name__ == '__main__':
    app.run(debug=True, port=5000)

React and component-based UIs: plain JavaScript for UIs becomes unmaintainable as complexity grows — you write endless document.getElementById() calls and lose track of what state is displayed. React's component model (function TaskItem({task}) { return <div>...</div>; }) makes UI logic modular and testable. The virtual DOM handles efficient DOM updates. Understanding why React was invented requires first experiencing the pain of vanilla JS UI code at scale.

Authentication and sessions: our app has no authentication. Adding it requires: login endpoint (POST /api/auth/login → JWT), protected endpoints (verify JWT on every request), logout (invalidate token), and refresh tokens (short-lived access tokens + long-lived refresh tokens). This is a non-trivial addition that most production apps need from day one.

▸ Part B.5 — JWT
import jwt, datetime

SECRET = 'your-secret-key'

def create_token(user_id):
    return jwt.encode({
        'sub': user_id,
        'exp': datetime.datetime.utcnow() + datetime.timedelta(hours=24),
        'iat': datetime.datetime.utcnow()
    }, SECRET, algorithm='HS256')

def verify_token(token):
    return jwt.decode(token, SECRET, algorithms=['HS256'])  # raises on invalid

def require_auth(fn):
    from functools import wraps
    from flask import request, jsonify
    @wraps(fn)
    def wrapper(*args, **kwargs):
        auth = request.headers.get('Authorization', '')
        if not auth.startswith('Bearer '):
            return jsonify(error='Unauthorized'), 401
        try:
            payload = verify_token(auth[7:])
            return fn(*args, user_id=payload['sub'], **kwargs)
        except jwt.InvalidTokenError:
            return jsonify(error='Invalid token'), 401
    return wrapper
▸ Part C.7–9
  1. /getTasks uses a verb in the URL — REST uses nouns. Correct: GET /tasks?user_id=42
  2. GET /deleteTask?id=99 uses GET for a destructive action — deletes should use DELETE method. Correct: DELETE /tasks/99
  3. /tasks/update/5 uses a verb "update" in the path. Correct: PUT /tasks/5 (the method expresses the action, not the URL)
▸ Part E.15 — full trace
  1. User clicks checkbox → JavaScript change event fires
  2. toggleTask(42, true) called
  3. fetch('/api/tasks/42', {method:'PATCH', body: JSON.stringify({completed:true})})
  4. HTTP request: PATCH /api/tasks/42\r\nContent-Type: application/json\r\n\r\n{"completed":true}
  5. Flask routes to update_task(42) → reads JSON body
  6. SQL: UPDATE tasks SET completed=1 WHERE id=42
  7. SQL: SELECT * FROM tasks WHERE id=42 (return updated task)
  8. Flask returns 200 JSON {"id":42,"completed":1,...}
  9. JavaScript receives response → calls loadTasks() → re-fetches entire list
