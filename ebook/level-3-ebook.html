﻿# Module 3.1 — Memory: How Machines Remember

The Problem

You have an ALU that can add, subtract, and perform logic operations. You have registers that hold values for a single clock cycle.

But here is the problem: where do the values come from before they reach the ALU? And where do results go after the ALU produces them?

The answer is memory — the system that lets a machine remember anything at all.

Without memory, a processor can only react to its current inputs. It cannot store a result, recall a previous value, or execute a program. Memory is what transforms a calculator into a computer.

The Story

The Human Analogy

A human performing arithmetic uses two types of memory simultaneously:

  • Working memory — the few numbers held in mind right now (small, fast, volatile)
  • Long-term memory — everything learned and stored (large, slow, persistent)

Computer memory works the same way, at every scale from a single chip to an entire data centre. The hierarchy exists because of a fundamental physical tradeoff: fast memory is expensive and small; slow memory is cheap and large.

Every computer architecture in history has navigated this tradeoff.

From Flip-Flops to Memory Arrays

In Module 2.5 you built a D flip-flop — a single bit of memory. One flip-flop stores one bit.

Eight flip-flops wired together store one byte. That is a register.

Now imagine 256 rows of 8 flip-flops each. That is 256 bytes of SRAM — Static Random Access Memory. Add an address decoder to select which row to read or write, and you have a functioning memory array.

This is literally how CPU cache memory works today, scaled to millions of cells.

SRAM vs DRAM

SRAM (Static RAM) — each bit stored in a flip-flop (6 transistors per bit)

  • Fast: access time ~1 nanosecond
  • Expensive: large die area
  • Used for: CPU registers, L1/L2/L3 cache

DRAM (Dynamic RAM) — each bit stored as charge on a capacitor (1 transistor + 1 capacitor per bit)

  • Slower: access time ~50–100 nanoseconds
  • Cheap: very small cell, high density
  • Problem: capacitors leak — must be refreshed every ~64 milliseconds
  • Used for: main system RAM (DDR4, DDR5)

The "dynamic" in DRAM refers to this need for constant refreshing. If the refresh circuit fails, all data is lost within milliseconds — even with power connected.

The Memory Hierarchy

Modern systems layer memory into a hierarchy based on speed and capacity:

Level Type Size Speed Location
L0 CPU Registers 16–32 × 64-bit 1 cycle (~0.3 ns) On-chip
L1 SRAM Cache 32–64 KB 4 cycles (~1 ns) On-chip
L2 SRAM Cache 256 KB–1 MB 12 cycles (~4 ns) On-chip
L3 SRAM Cache 4–32 MB 40 cycles (~12 ns) On-chip
RAM DRAM 4–64 GB ~200 cycles (~60 ns) Off-chip
SSD Flash 256 GB–4 TB ~100,000 ns Off-chip
HDD Magnetic 1–20 TB ~10,000,000 ns Off-chip

The CPU operates on data in registers. When it needs data not in registers, it looks in L1 cache. On a miss, it checks L2, then L3, then RAM, then disk. Each level is roughly 10–100× slower than the one above.

This is why cache locality matters so much in software performance: a program that accesses memory in sequential, predictable patterns keeps data in fast cache. A program that jumps around randomly keeps forcing expensive cache misses to main RAM.

Address Space and Addressability

Every byte in memory has a unique address — a number that identifies its location.

For a 32-bit address space: 2³² = 4,294,967,296 addresses = 4 GB maximum. For a 64-bit address space: 2⁶⁴ = 18,446,744,073,709,551,616 addresses = 16 exabytes.

Addressability refers to what unit each address points to. Most modern architectures are byte-addressable: each address identifies one byte. Some older or embedded systems are word-addressable (each address identifies 16 or 32 bits).

Memory map: not all addresses point to RAM. A typical x86-64 system uses its address space for:

  • RAM (the majority)
  • Memory-mapped I/O (peripherals that respond to memory read/write)
  • BIOS/UEFI ROM
  • Graphics framebuffer
  • Reserved regions

How a Read Operation Works

When the CPU issues a read:

  1. CPU places the address on the address bus
  2. CPU asserts the read control signal
  3. Memory decodes the address to select the correct row and column
  4. Memory places the data on the data bus
  5. CPU latches the data from the data bus into a register

For DRAM, step 3–4 involves:

  • Row address strobe (RAS): selects the row, copies it into a row buffer
  • Column address strobe (CAS): selects the column from the row buffer
  • CAS latency (CL) is the key DRAM timing spec (e.g., CL16 = 16 clock cycles)

How a Write Operation Works

When the CPU issues a write:

  1. CPU places the address on the address bus
  2. CPU places the data on the data bus
  3. CPU asserts the write control signal
  4. Memory decodes the address, stores data at that location

The Concept: Memory as an Addressed Array

Think of memory as a post office with numbered mailboxes. Each mailbox (address) holds a fixed-size value (1 byte for byte-addressable memory). The postmaster (address decoder) routes requests to the correct box. Reading opens the box and copies its contents. Writing replaces its contents.

The key abstractions:

  • Address: which location
  • Data: what value
  • Control: read or write

These three signals — address, data, control — form the memory bus interface. Everything from a 1980s microprocessor to a modern server uses this same abstraction.

Going Deeper

Write-through vs write-back caches: When the CPU writes to a cached address, does it immediately write to RAM (write-through) or only update the cache and write to RAM later (write-back)? Write-back is faster but more complex — the cache must track which lines are "dirty" (modified but not yet written back). Modern CPUs use write-back with sophisticated coherency protocols.

Virtual memory: Programs don't see physical RAM addresses. The CPU's Memory Management Unit (MMU) translates virtual addresses (what the program uses) to physical addresses (where the data actually lives in RAM). This allows isolation between processes, larger address spaces than physical RAM, and demand paging. Module 4.4 covers this in depth.

﻿# Module 3.2 — The Fetch-Decode-Execute Cycle

The Problem

You now have:

  • An ALU that performs arithmetic and logic
  • Memory that stores bytes at addresses
  • Registers that hold values temporarily

The missing piece: what makes the CPU actually do something?

What starts the process? What decides which operation to perform next? What keeps it going, instruction after instruction, without stopping?

The answer is the Fetch-Decode-Execute cycle — the three-step loop that has driven every program ever run on every computer ever built.

The Story

The Problem of Sequential Control

Imagine you have a list of instructions written on paper:

  1. Load the number at address 5 into Register A
  2. Load the number at address 6 into Register B
  3. Add Register A and Register B
  4. Store the result at address 7

A human can read this list and execute it. But how does a machine do it?

The machine needs:

  • A way to remember where it is in the instruction list (the Program Counter)
  • A way to read the next instruction from memory (the Fetch step)
  • A way to understand what the instruction means (the Decode step)
  • A way to carry out the instruction (the Execute step)
  • A way to automatically move to the next instruction (PC increment)

These five elements, working in a continuous loop, are the CPU.

The Three Registers You Cannot Live Without

Program Counter (PC) — holds the address of the next instruction to fetch. After each fetch, it automatically increments. A jump instruction sets it to a new value, breaking the sequential flow.

Instruction Register (IR) — holds the current instruction being decoded and executed. The fetched instruction is copied here and stays until the next fetch.

Memory Address Register (MAR) — holds the address being read from or written to memory. When the CPU needs to access memory, it first loads the address here.

Memory Data Register (MDR) also called the Memory Buffer Register (MBR) — holds the data traveling to or from memory. Reads store their result here; writes take their data from here.

The Cycle — Step by Step

FETCH:

  1. Copy PC → MAR (tell memory which address to read)
  2. Read memory[MAR] → MDR (get the instruction bytes)
  3. Copy MDR → IR (load instruction into the instruction register)
  4. Increment PC (point to the next instruction)

DECODE: 5. The control unit examines IR 6. It identifies the opcode (what operation to perform) 7. It identifies the operands (which registers, addresses, or immediate values to use) 8. It activates the correct control signals for the next phase

EXECUTE: 9. The identified operation is performed:

  • ALU operation: route operands to ALU, store result
  • Memory read: MAR ← address, MDR ← memory[MAR], register ← MDR
  • Memory write: MAR ← address, MDR ← register, memory[MAR] ← MDR
  • Jump: PC ← new address
  1. Return to FETCH.

The cycle repeats forever — or until the machine is powered off or halts.

Why This Is Profound

Every program ever written — every web browser, every game, every operating system — runs on this three-step loop. The loop does not know about Python or JavaScript or databases. It knows only: fetch an instruction, decode it, execute it, repeat.

The sophistication of modern software exists entirely in how instructions are sequenced and what they instruct the hardware to do. The hardware itself is doing nothing more than this ancient, simple cycle.

A Concrete Example — Tracing ADD

Suppose memory contains:

Address 0x00: 0x01  ← LOAD_A instruction (load next byte into Register A)
Address 0x01: 0x05  ← operand: value 5
Address 0x02: 0x02  ← LOAD_B instruction
Address 0x03: 0x03  ← operand: value 3
Address 0x04: 0x10  ← ADD instruction (A + B → A)
Address 0x05: 0x30  ← STORE instruction (store A at address 0x08)
Address 0x06: 0x08  ← operand: store address

PC starts at 0x00.

Cycle 1 — LOAD_A 5:

  • Fetch: IR ← 0x01, PC becomes 0x01
  • Decode: opcode 0x01 = LOAD_A; operand follows
  • Execute: fetch operand (0x05=5), load 5 into Register A; PC becomes 0x02

Cycle 2 — LOAD_B 3:

  • Fetch: IR ← 0x02, PC becomes 0x03
  • Decode: opcode 0x02 = LOAD_B; operand follows
  • Execute: fetch operand (0x03=3), load 3 into Register B; PC becomes 0x04

Cycle 3 — ADD:

  • Fetch: IR ← 0x10, PC becomes 0x05
  • Decode: opcode 0x10 = ADD; uses Reg A and Reg B
  • Execute: ALU computes A + B = 8; result stored in Register A

Cycle 4 — STORE:

  • Fetch: IR ← 0x30, PC becomes 0x06
  • Decode: opcode 0x30 = STORE; address follows
  • Execute: fetch address (0x08); write Register A (8) to memory[0x08]

After 4 cycles, memory[0x08] = 8. The computation 5 + 3 = 8 is complete.

The Role of the Control Unit

The Control Unit (CU) is the conductor of this orchestra. It:

  • Generates all timing and control signals
  • Tells the ALU which operation to perform
  • Opens and closes the gates that route data between registers and memory
  • Manages the PC increment and jump logic
  • Handles exceptions (invalid instruction, division by zero, memory fault)

The CU does not compute. It directs the components that do.

Two implementations: hardwired control (logic gates implementing the state machine — fast, inflexible) and microprogrammed control (a small internal ROM of microinstructions — slower, but easy to modify and extend).

Clock Speed and IPC

The FDE cycle is driven by a clock. Modern CPUs run at 3–6 GHz — 3 to 6 billion clock cycles per second. But a single instruction often takes multiple cycles (memory accesses are slow). The key performance metric is not just clock speed but IPC — Instructions Per Clock.

Modern superscalar CPUs execute multiple instructions per clock using pipelining: while one instruction is in the Execute stage, the next is in Decode, and the one after is being Fetched — simultaneously. A 4-stage pipeline theoretically achieves 4× throughput.

This is why modern CPUs have performance figures like "4.5 GHz × 6 IPC = 27 billion instruction-equivalents per second."

The Concept: State Drives Computation

The FDE cycle is a finite state machine. The state is:

  • The contents of all registers (PC, IR, MAR, MDR, general-purpose registers)
  • The contents of memory
  • The current phase (Fetch / Decode / Execute)

Given any state, the next state is completely determined by the current instruction and the control unit's logic. There is no randomness, no ambiguity — just deterministic state transitions at clock speed.

This determinism is what makes debugging possible, what makes programs reliable, and what makes the behaviour of software predictable from its source code.

Going Deeper

Exceptions and interrupts: What happens if an instruction is invalid, or a divide-by-zero occurs? The control unit detects the fault, saves the current PC, and jumps to a fault handler — a special piece of code that decides how to respond. This is how operating systems catch and handle program errors.

Branch prediction: Jump instructions are a problem for pipelining — the CPU doesn't know the next instruction until it executes the jump. Modern CPUs predict the branch direction and speculatively fetch instructions along the predicted path. If the prediction is wrong, the pipeline is flushed and the CPU restarts from the correct address. Good branch predictors achieve >99% accuracy.

﻿# Module 3.3 — Instruction Set Architecture (ISA)

The Problem

The ALU can add, subtract, AND, OR, XOR. The FDE cycle can fetch and execute instructions. Memory can store and retrieve bytes.

But how does the CPU know what to do with a byte like 0x83? How does it distinguish "add these two registers" from "load this value" from "jump to that address"?

The answer is the Instruction Set Architecture — the contract between hardware and software that defines every operation a CPU can perform.

The ISA is the most important design decision in computer architecture. It is the interface that software speaks and hardware implements. Every program ever compiled targets a specific ISA. Change the ISA and every program must be recompiled or rewritten.

The Story

The First ISAs

Early computers had no standard instruction set. Each machine had its own unique set of operations, wired directly into its control unit. Writing a program for one machine meant it ran on nothing else. Moving programs between machines meant rewriting them from scratch.

The IBM System/360 (1964) was the first family of computers to share a common ISA across machines of different speeds and prices. A program written for the cheapest System/360 would run unchanged on the most powerful one. This was revolutionary: software became an asset that outlasted hardware.

The System/360 ISA introduced concepts still present in x86-64 today.

What an ISA Defines

An ISA specifies:

  1. Registers — how many, how wide, which are special
  2. Data types — integers (8/16/32/64-bit), floats, vectors
  3. Instructions — every operation the CPU supports
  4. Addressing modes — how operands are located (immediate, register, memory, indirect)
  5. Instruction encoding — how instructions are represented as bits
  6. Memory model — byte order (endianness), alignment rules
  7. Privilege levels — which instructions only the OS can use
  8. Exception model — what happens on errors

RISC vs CISC

Two competing philosophies dominate ISA design:

CISC — Complex Instruction Set Computer

  • Many instructions, some very complex (string copy, matrix operations)
  • Instructions of variable length (1–15 bytes on x86)
  • Single instruction can do a memory read, an operation, and a memory write
  • Fewer instructions needed in programs → smaller code size
  • Complex decoder hardware needed
  • Examples: Intel x86-64, AMD64

RISC — Reduced Instruction Set Computer

  • Few, simple instructions — each does exactly one thing
  • Fixed instruction length (typically 32 bits)
  • Memory access only via explicit load/store instructions
  • More instructions needed for complex operations → larger programs
  • Simple decoder → easier to pipeline, easier to optimise
  • Examples: RISC-V, ARM (modern), MIPS, SPARC

The modern reality: ARM processors (RISC) run almost all smartphones and tablets. x86-64 (CISC) runs almost all desktop/laptop/server computing. Apple's M-series chips (ARM RISC) now run high-performance Macs, challenging x86-64 dominance. RISC-V is an open-source ISA gaining traction in embedded and research systems.

Interesting nuance: modern x86-64 CPUs internally translate CISC instructions into simpler micro-operations (μops) that look a lot like RISC. The CISC/RISC distinction has blurred at the implementation level, even if the ISA surface remains different.

Addressing Modes

How does an instruction specify where its data comes from? Addressing modes are the answer.

Immediate: the value is encoded directly in the instruction. LOAD A, 42 — loads the literal value 42 into register A.

Register: the value is in a register. ADD A, B — adds the value in register B to register A.

Direct (absolute): the value is at a specific memory address. LOAD A, [0x1000] — loads the byte at memory address 0x1000 into A.

Indirect: the address of the value is in a register. LOAD A, [B] — loads the byte from the address stored in register B.

Base + offset: address = register + constant. LOAD A, [B + 4] — loads from the address (B's value + 4). Used for array indexing and struct field access.

PC-relative: address = PC + offset. Used for branch instructions. JMP +8 — jump forward 8 bytes from the current PC. Produces position-independent code.

Instruction Encoding

Every instruction must be represented as a pattern of bits. Two main approaches:

Fixed-length (RISC): every instruction is exactly 32 bits.

RISC-V R-type (32-bit):
[31:25] funct7  [24:20] rs2  [19:15] rs1  [14:12] funct3  [11:7] rd  [6:0] opcode

Simple decoder: always knows exactly where each field is.

Variable-length (CISC): instructions range from 1 to 15 bytes.

x86-64 examples:
NOP:           0x90           (1 byte)
INC  eax:      0xFF 0xC0      (2 bytes)
MOV  rax, imm: 0x48 0xB8 + 8-byte immediate  (10 bytes)

Complex decoder: must figure out instruction length before it can decode it. One reason x86 decoders are expensive in silicon area.

Real ISA: x86-64 Subset

The actual instruction set your computer uses for every program you run:

; Load values
MOV rax, 5          ; rax = 5 (immediate)
MOV rbx, [0x1000]   ; rbx = memory[0x1000] (direct)
MOV rcx, [rax]      ; rcx = memory[rax] (indirect)
MOV rdx, [rax + 8]  ; rdx = memory[rax + 8] (base+offset)

; Arithmetic
ADD rax, rbx        ; rax = rax + rbx
SUB rax, 1          ; rax = rax - 1
IMUL rax, rbx       ; rax = rax * rbx (signed multiply)
IDIV rcx            ; rax = rax / rcx, rdx = rax mod rcx

; Comparison and control flow
CMP rax, 0          ; sets flags based on rax - 0 (doesn't modify rax)
JE  label           ; jump if equal (ZF=1)
JNE label           ; jump if not equal
JL  label           ; jump if less (signed)
JMP label           ; unconditional jump
CALL function       ; push PC, jump to function
RET                 ; pop PC (return from function)

Every C/C++/Rust/Go program you compile becomes sequences of these instructions.

The Concept: The ISA as Contract

The ISA is the most stable interface in computing. Intel has maintained backward compatibility with the 8086 ISA (1978) through every generation of x86 processor to this day. A program compiled in 1985 for DOS can still run on a 2024 Core i9 (in compatibility mode). This backward compatibility is both a massive commercial advantage (all old software keeps working) and an engineering burden (carrying 46 years of design decisions forward).

ARM's decision to design a clean, simple RISC ISA in the 1980s is why ARM cores are so efficient — they don't carry the weight of 40 years of complexity.

RISC-V represents a third path: a completely open, free ISA designed with modern knowledge, with no legacy baggage. Its adoption in research, embedded systems, and potentially data centres is growing rapidly.

Going Deeper

The ABI (Application Binary Interface): Beyond the ISA, software needs conventions for how programs interact. Which register holds the first function argument? How is the stack organised? ﻿# Module 3.4 — Input/Output: Connecting to the World

The Problem

You have a CPU that fetches, decodes, and executes instructions. You have memory that stores programs and data.

But a computer that can only read from and write to its own memory is useless. How does it accept input from a keyboard? How does it send output to a screen? How does it read a file from disk?

The answer is Input/Output (I/O) — the mechanisms by which a CPU communicates with the world outside its own chip.

Without I/O, a computer is a sealed box performing calculations no one can see and responding to nothing. I/O is what connects the silicon to the world.

The Story

The First I/O: Punch Cards and Lights

The earliest computers had no keyboard, no screen. Programs were loaded via punched cards fed into a card reader — a mechanical device that detected holes and converted them to electrical signals. Output was printed on paper or displayed as patterns of lights on a front panel.

The operator's interaction with the computer was entirely through these physical media. A program could take minutes to load and hours to run. Output was not real-time — it was retrieved after the job completed.

The concept of interactive computing — where a human types and the computer responds immediately — did not exist until the 1960s. The development of time-sharing operating systems and terminals made it possible. This was considered revolutionary.

Three I/O Methods

Method 1 — Programmed I/O (Polling)

The CPU directly controls the I/O device by reading and writing specific addresses. To check if a key has been pressed, the CPU reads a "status register" address and tests a bit. If not ready, it reads it again. And again. And again.

loop:
  READ status_register → A
  AND A, 0x01          ; test the "data ready" bit
  JZ loop              ; if not ready, keep polling
  READ data_register → B  ; now read the actual data

This is called polling or busy-waiting. It works, but the CPU wastes 100% of its time checking — it can do nothing else while waiting for I/O.

Analogy: standing at the front door staring at the letterbox, checking every second if a letter has arrived.

Method 2 — Interrupts

The CPU continues executing its program normally. When an I/O device has data ready, it sends an interrupt signal to the CPU.

The CPU:

  1. Finishes the current instruction
  2. Saves the current PC and registers to the stack
  3. Jumps to an Interrupt Service Routine (ISR) — a special function that handles the event
  4. The ISR reads the data from the I/O device
  5. The ISR restores registers and returns to the interrupted program

The CPU can do useful work between I/O events. The keyboard only interrupts when a key is actually pressed — perhaps 10 times per second, consuming a tiny fraction of CPU time.

Analogy: put a doorbell on the front door. You do your work. The doorbell rings when a letter arrives.

Method 3 — Direct Memory Access (DMA)

For high-bandwidth I/O (disk, network, video), even interrupt-driven I/O is too slow — the CPU would spend all its time copying bytes from the I/O device into memory.

DMA gives the I/O device direct access to memory without involving the CPU:

  1. CPU programs the DMA controller: "copy 4096 bytes from disk to address 0x8000"
  2. CPU continues executing other code
  3. DMA controller handles all the data transfer autonomously
  4. When done, DMA controller interrupts the CPU
  5. CPU reads the data at 0x8000 — already there

Modern SSDs, GPUs, and network cards all use DMA. Without it, a CPU reading a 1 GB file would spend nearly all its time doing memory copies instead of useful computation.

Memory-Mapped I/O

How does the CPU "talk to" an I/O device? There are two approaches:

Port-mapped I/O: separate IN/OUT instructions with a separate I/O address space (x86 uses this historically).

IN  al, 0x60   ; read from keyboard port 0x60
OUT 0x61, al   ; write to speaker port 0x61

Memory-mapped I/O (MMIO): I/O devices appear at specific memory addresses. Reading from or writing to those addresses communicates with the device — no special instructions needed.

Address 0xFFFF0000: keyboard status register
Address 0xFFFF0001: keyboard data register
Address 0xFFFF0010: screen framebuffer start

When the CPU writes to 0xFFFF0010, the value doesn't go to RAM — it goes to the video controller, which displays it on screen.

Modern practice: almost all modern systems use MMIO. ARM processors use MMIO exclusively. Memory-mapped I/O makes device drivers simpler — they just use regular memory read/write operations.

The Journey of a Keystroke

Let's trace what happens when you press the 'A' key:

  1. Physical: the key closes a circuit, sending a voltage signal
  2. Keyboard controller: detects the closed circuit, generates a scancode (0x1C for 'A' on a standard layout)
  3. Keyboard buffer: stores the scancode in a small internal buffer
  4. Hardware interrupt: keyboard controller asserts the IRQ1 interrupt line
  5. CPU: finishes current instruction, saves state, jumps to keyboard ISR
  6. ISR: reads the scancode from the keyboard data port, translates to ASCII ('A' = 0x41), stores in OS keyboard buffer
  7. ISR return: CPU restores state, continues previous program
  8. Application: calls read() system call, OS returns 'A' from the keyboard buffer
  9. Terminal/shell: receives 'A', echoes it to screen, adds to input line

This entire chain — from key press to character appearing on screen — takes approximately 1–10 milliseconds. Most of that time is in the OS and display pipeline. The hardware interrupt itself is handled in microseconds.

From Punch Cards to USB

Punch cards (1890s–1970s): data encoded as holes; mechanical reader converts holes to signals; output via line printer
Serial terminals (1960s–1980s): RS-232 serial connection; text only; 110–9600 baud
Parallel port (1970s–2000s): 8 data lines + control lines; used for printers; up to 1 MB/s
PS/2 (1987–present): dedicated keyboard/mouse port; synchronous serial protocol
USB (1996–present): Universal Serial Bus; hot-pluggable; 1.5 Mb/s to 40 Gb/s (USB4); handles keyboard, mouse, storage, audio, video, charging
PCIe (2003–present): high-speed bus for GPUs, NVMe SSDs, network cards; PCIe 5.0 = 128 GB/s (×16 slot)

Every peripheral you connect to a computer uses one of these protocols to convert physical signals into data the CPU can read.

The Concept: Every Peripheral is a Memory Address

The elegance of MMIO is the reduction: every I/O operation becomes a memory read or write. The CPU doesn't need to know whether it's talking to RAM or a GPU or a network card. It just reads and writes addresses. The hardware behind those addresses handles the rest.

This abstraction is what makes device drivers possible. A driver is a program that knows the memory-mapped register layout of a specific device and uses regular memory operations to control it.

Going Deeper

Interrupt priorities and nested interrupts: Not all interrupts are equally urgent. A system timer interrupt can wait; a hardware fault cannot. CPUs implement an interrupt priority scheme (IRQ levels). A high-priority interrupt can interrupt the ISR of a low-priority interrupt — creating nested interrupt handling. Real-time operating systems (RTOS) depend on this for guaranteed response times.

I/O schedulers: When many processes are reading from disk simultaneously, the OS I/O scheduler decides the order. The classic "elevator algorithm" minimises disk head movement by servicing requests in sweep order (like an elevator going up then down). Modern SSDs don't have a mechanical head, so SSDs use different scheduling strategies optimised for parallelism.

﻿# Module 3.5 — The Bus: Moving Data Around

The Problem

The CPU computes. Memory stores. I/O devices communicate.

But how do these components actually talk to each other? The CPU is a chip on a motherboard. Memory is another chip. The GPU is a third.

They cannot communicate by thought. They need a shared pathway — a physical medium, a protocol, and a set of rules for who talks when.

That pathway is the bus.

A bus is a shared communication channel — a set of wires connecting multiple components, plus the protocol that governs who uses those wires and when.

The Story

The Early Bus: Everything Shared One Wire

The earliest computers wired components point-to-point: the CPU had a dedicated wire to memory, another to the printer, another to the card reader. Every new device required new wires and new control logic. Adding a device to a computer was a hardware engineering project.

The invention of the shared bus — a common set of wires that all components connect to — was transformative. Now adding a device meant plugging it into the existing bus. The protocol managed who could talk and when.

The Intel 8086 (1978) used a 16-bit data bus and 20-bit address bus. The IBM PC (1981) standardised the ISA bus (not to be confused with Instruction Set Architecture — the same acronym used for different purposes). PCI (1992) replaced ISA. PCIe (2003) replaced PCI with a point-to-point switched fabric that looks like a bus to software but is physically very different.

The Three Sub-Buses

A classical system bus consists of three logically separate groups of signals:

Address Bus

  • Carries the address of the memory location or I/O device being accessed
  • Unidirectional: CPU → memory/devices
  • Width determines addressable space: 32-bit → 4 GB, 64-bit → 16 EB
  • Example: CPU places 0x0000_1000 on address bus → selects address 4096

Data Bus

  • Carries the actual data being read or written
  • Bidirectional: CPU ↔ memory/devices
  • Width determines how much data moves per transfer: 8, 16, 32, or 64 bits
  • A 64-bit data bus moves 8 bytes per bus cycle

Control Bus

  • Carries control signals that coordinate the operation
  • Signals include:
    • READ / WRITE — direction of transfer
    • MEMORY_SELECT / IO_SELECT — is this a memory or I/O access?
    • CLOCK — timing signal
    • INTERRUPT_REQUEST — device requests CPU attention
    • BUS_GRANT / BUS_REQUEST — bus arbitration
    • RESET — system reset

All three buses operate simultaneously, coordinated by the clock.

Bus Arbitration

A bus is a shared resource. Only one device can use it at a time. When multiple components want to use the bus simultaneously, someone must decide who goes first. This is bus arbitration.

Daisy-chain arbitration: devices are chained in priority order. A bus grant signal passes down the chain — the first device in the chain that wants the bus takes it. Simple but unfair to low-priority devices.

Centralised arbitration: a dedicated bus arbiter receives requests from all devices and grants access based on a scheduling policy (round-robin, priority, etc.). Fairer but requires extra hardware.

Distributed arbitration: devices use a shared wire and a collision-detection protocol (similar to early Ethernet). Each device can "bid" for the bus simultaneously; the highest-priority wins based on wire-OR logic.

Modern systems like PCIe avoid shared-bus arbitration entirely by using point-to-point switched connections — each device has its own dedicated link to a switch (like Ethernet vs a hub). But the software model still looks like a bus.

Von Neumann vs Harvard Architecture

Von Neumann architecture: instructions and data share the same memory and the same bus. The CPU fetches an instruction, then fetches data — both using the same path. This creates the Von Neumann bottleneck: the bus bandwidth limits performance because the same resource is contended for both code and data.

Almost all general-purpose computers (x86, ARM application cores) use Von Neumann architecture.

Harvard architecture: separate memory and separate buses for instructions and data. The CPU can fetch an instruction and read data simultaneously — no contention. Simpler to implement but more expensive (two separate memory systems).

Used in: microcontrollers (PIC, AVR), DSPs, many embedded systems.

Modified Harvard: use separate L1 instruction cache and L1 data cache (effectively separate buses at the cache level), but share memory at L2 and beyond. This gives most of Harvard's performance benefit while keeping one unified address space. Used by: modern x86-64, ARM Cortex-A. This is why L1 is listed as "L1i" (instruction) and "L1d" (data) in CPU specs.

Bus Bandwidth and Latency

Bandwidth: how much data can flow per second.

Bandwidth = (bus width in bytes) × (bus clock frequency)
Example: 64-bit bus at 100 MHz = 8 bytes × 100 MHz = 800 MB/s
DDR4-3200: 64-bit × 1,600 MHz (double-pumped) × 2 channels = 51.2 GB/s

Latency: how long until the first data byte arrives after a request.

Latency = (bus request overhead) + (memory access time)
Typical DRAM latency: 60–80 ns regardless of bus bandwidth

Bandwidth and latency are independent. A high-bandwidth bus can still have high latency. Latency dominates for small random accesses; bandwidth dominates for large sequential transfers.

Bus width vs bus speed: doubling bus width doubles bandwidth but requires more pins/wires (expensive). Doubling clock speed doubles bandwidth but increases power and electromagnetic interference. Real systems balance both.

PCIe: The Modern "Bus"

PCIe (Peripheral Component Interconnect Express) is the dominant high-speed interconnect in modern PCs. Technically it is not a shared bus — it is a switched point-to-point serial fabric.

  • Each device has a dedicated serial link (lane) to the PCIe root complex (in the CPU or chipset)
  • Each lane is 2 differential pairs: one transmit, one receive
  • ×1, ×4, ×8, ×16 slot configurations (1, 4, 8, or 16 lanes)
  • PCIe 5.0: 4 GB/s per lane → ×16 = 64 GB/s bidirectional

But from the software perspective, PCIe devices appear in the system address space, are configured via memory-mapped registers, and use the same read/write semantics as any bus. The abstraction holds.

The Concept: The Bus as Shared Protocol

The bus is the physical embodiment of the computing contract: any component that implements the protocol can participate in the system. This is why standards matter. The PCI bus standard let any manufacturer build cards that worked in any PCI motherboard. USB lets any peripheral connect to any host. PCIe lets any GPU or NVMe drive work in any compatible system.

Without standardised bus protocols, the computer industry would be a fragmented ecosystem of incompatible proprietary interfaces — which is exactly what it was before the IBM PC standardised the ISA bus in 1981.

Going Deeper

Cache coherency: when multiple CPU cores share memory, each has its own L1/L2 cache. If Core 0 writes to address X and Core 1 has X cached, Core 1's cache is now stale (incoherent). The MESI protocol (Modified, Exclusive, Shared, Invalid) maintains coherency: cache lines carry state tags, and bus transactions notify other caches when a write occurs. Without coherency, multiprocessor programs would produce incorrect results silently.

Memory-mapped I/O vs port-mapped I/O revisited: on x86, both exist. The CPU has separate IN/OUT instructions for port-mapped I/O (64K I/O ports) and uses regular MOV for MMIO. Linux drivers almost exclusively use MMIO via ioremap(). Port I/O is relegated to legacy devices (PS/2 keyboard, COM ports, legacy DMA).
