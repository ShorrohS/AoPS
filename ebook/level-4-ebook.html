﻿# Module 4.1 — Machine Code and Assembly Language

The Problem

You can now build a CPU and execute instructions from memory. The CPU understands binary — 0x01 0x05 means "load the value 5 into register A."

But nobody writes programs in hex bytes.

How did programmers get from "a CPU that reads binary" to "a Python script you can write in plain English"?

The first step up from raw binary is assembly language — and the tool that bridges them is the assembler.

Every high-level program you will ever write sits atop a chain of translations. Understanding the first link in that chain — from human-readable mnemonics to machine binary — is essential for understanding everything above it.

The Story

The First Programmers Had No Language

ENIAC (1945) was programmed by physically rewiring the machine. There were no instructions in memory — the circuit topology was the program. Changing the program meant changing the hardware.

The stored-program computer (1948–1949) was the breakthrough: programs could be loaded into memory as data. But the first stored programs were still written as raw binary numbers. Programmers kept notebooks mapping opcodes to numbers. A single typo in a binary string produced a program that crashed silently or produced wrong results with no indication of where.

Kathleen Booth (1947) and David Wheeler (1949) at Cambridge are among the earliest people credited with writing what we would today recognise as assembly language — symbolic mnemonics like ADD and JMP that a secondary program (the assembler) would translate into binary.

The insight was simple but profound: let the computer do the translation. Write in symbols; let a program convert them to numbers.

The Compilation Pipeline

Modern programs go through multiple translation stages before the CPU can execute them:

Source code (.c, .py, .rs)
       ↓  Preprocessor
Preprocessed source
       ↓  Compiler
Assembly code (.s / .asm)
       ↓  Assembler
Object code (.o / .obj)  ← machine code + relocation metadata
       ↓  Linker
Executable (.exe / ELF binary)  ← ready to load
       ↓  Loader (OS)
Process in memory  ← CPU executes this

Preprocessor — expands macros, includes header files, strips comments
Compiler — translates high-level code to assembly (register allocation, optimisation)
Assembler — translates assembly mnemonics to binary machine code
Linker — combines multiple object files, resolves symbol references, produces one executable
Loader — the OS reads the executable, allocates memory, copies segments into place, sets PC to entry point

What Machine Code Looks Like

x86-64 machine code is variable-length. Here is the same simple computation in three representations:

// C source
int x = 5;
int y = 3;
int z = x + y;

; x86-64 Assembly (AT&T syntax)
movl  $5, -4(%rbp)      ; x = 5  (store 5 at stack slot)
movl  $3, -8(%rbp)      ; y = 3
movl  -4(%rbp), %eax    ; load x into eax
addl  -8(%rbp), %eax    ; eax = eax + y
movl  %eax, -12(%rbp)   ; z = eax

; Machine code (hex bytes)
C7 45 FC 05 00 00 00    ; movl $5, -4(%rbp)
C7 45 F8 03 00 00 00    ; movl $3, -8(%rbp)
8B 45 FC                ; movl -4(%rbp), %eax
03 45 F8                ; addl -8(%rbp), %eax
89 45 F4                ; movl %eax, -12(%rbp)

The CPU executes the bottom representation. The middle is what a human can read. The top is what an application programmer writes.

Anatomy of an Assembly Instruction

label:    mnemonic    operand1, operand2    ; comment

Label — optional name for this address. Used as jump targets and function names.
Mnemonic — the instruction name: MOV, ADD, SUB, JMP, CALL, RET, etc.
Operands — what the instruction operates on:

  • Immediate: $5 (literal value)
  • Register: %rax, %rbx (CPU register)
  • Memory: -4(%rbp) (address = rbp − 4)

Two syntax flavours:

  • Intel syntax (Windows, NASM): mov rax, 5 — destination first
  • AT&T syntax (Linux, GAS): movq $5, %rax — source first, register prefixed with %

Real x86-64 Registers

Register 64-bit 32-bit Purpose
Accumulator rax eax Return values, arithmetic
Base rbx ebx General purpose
Counter rcx ecx Loop counter
Data rdx edx I/O, multiply/divide
Stack Pointer rsp esp Top of stack
Base Pointer rbp ebp Stack frame base
Instruction Pointer rip eip Current instruction address
Source Index rsi esi String source
Dest Index rdi edi String dest, arg 1 (Linux ABI)
R8–R15 — — General purpose (64-bit only)

Hello World in Assembly (x86-64 Linux)

; hello.asm — NASM syntax, x86-64 Linux
section .data
    msg db "Hello, World!", 10   ; 10 = newline character
    len equ $ - msg              ; length = current position minus msg label

section .text
    global _start

_start:
    ; write(1, msg, len)  — syscall number 1 = write
    mov rax, 1          ; syscall: write
    mov rdi, 1          ; fd: stdout (1)
    mov rsi, msg        ; pointer to message
    mov rdx, len        ; length of message
    syscall             ; invoke kernel

    ; exit(0)  — syscall number 60 = exit
    mov rax, 60         ; syscall: exit
    mov rdi, 0          ; exit code: 0 (success)
    syscall

This is the bedrock. Every print("Hello") in Python eventually produces a sequence of operations equivalent to this — layers of abstraction translate the readable to the executable.

The Assembler's Job

An assembler makes two passes through the source:

Pass 1 — Symbol table construction:

  • Record the address of every label
  • Compute the size of every instruction
  • Build a table: {label → address}

Pass 2 — Code generation:

  • For each instruction, look up the opcode encoding
  • Substitute label references with actual addresses
  • Emit the binary bytes

The output is an object file — machine code with relocation entries: placeholders that the linker will fill in when it knows the final layout of all combined object files.

The Concept: Every High-Level Construct Has an Assembly Equivalent

// if statement
if (x > 0) { y = 1; }

; Assembly equivalent
cmp   eax, 0          ; compare x (in eax) with 0
jle   skip            ; jump if x ≤ 0 (skip the body)
mov   [y], 1          ; y = 1
skip:

// for loop
for (int i = 0; i < 10; i++) { sum += i; }

; Assembly equivalent
mov   ecx, 0          ; i = 0
loop_start:
cmp   ecx, 10         ; i < 10?
jge   loop_end        ; if not, exit
add   eax, ecx        ; sum += i
inc   ecx             ; i++
jmp   loop_start
loop_end:

Every if, for, while, function call, and return in every language compiles to this style of pattern. The patterns are universal; only the syntax differs between architectures.

Going Deeper

Calling conventions and the ABI: Assembly doesn't enforce any rules about how functions pass arguments or return values. The Application Binary Interface (ABI) is the platform convention that everyone agrees to follow. On Linux x86-64: first 6 integer arguments go in rdi, rsi, rdx, rcx, r8, r9. Return value in rax. Stack 16-byte aligned at CALL. These rules let code compiled by different compilers (and different languages) call each other. Module 4.2 covers this in depth.

Inline assembly in C: Sometimes a programmer needs to write assembly inside a C program — for hardware-specific operations, maximum performance, or features the compiler can't generate. In GCC: asm("instruction" : outputs : inputs : clobbers);. Widely used in OS kernels.

▸ Part B answers

  1. MOV eax, 5: B8 05 00 00 00 (opcode 0xB8+0=0xB8, then 5 in 4 bytes LE = 05 00 00 00)

  2. RET NOP NOP: C3 90 90

  3. JMP +3: EB 03 (offset = 3, jumps 3 bytes past the byte after JMP)

  4. Little-endian stores the least significant byte first. MOV eax, 5 = B8 05 00 00 00 — the 05 (value 5) is at the lowest address. This matches x86's memory byte ordering. A big-endian encoding would be B8 00 00 00 05.

▸ Part C — two-pass trace

Pass 1 — symbol table:

start → 0x00  (LOAD A,10 starts at 0)
        0x03  (LOAD B,3)
        0x06  (SUB A,B)
loop  → 0x09  (ADD A,1)
        0x0C  (JMP done) ← 2 bytes
        0x0E  (ADD A,99)
done  → 0x11  (HALT)

  1. Offset = 0x11 − (0x0C + 2) = 0x11 − 0x0E = 0x03. The JMP encodes as JMP 0x03 meaning "jump 3 bytes forward from the next instruction."

  2. A forward reference is a label used before it is defined (e.g., jumping to done before the assembler has seen done:). Two-pass: Pass 1 records all labels and their addresses. Pass 2 can resolve all references because the symbol table is complete.

  3. Backpatching: in a single pass, the assembler emits a placeholder (e.g., 0x00) for unknown forward references, records the location, and patches it after the whole file is processed. Functionally equivalent to two-pass but more complex to implement correctly.

▸ Part D — linker

  1. add_two is at math.o local 0x00, placed at 0x2000 → final address: 0x2000

  2. CALL at linked 0x1010. Offset = target − (call_site + 5) = 0x2000 − (0x1010 + 5) = 0x2000 − 0x1015 = 0x0FEB. Linker patches the 4-byte placeholder with 0xEB 0x0F 0x00 0x00 (little-endian).

  3. Symbol table: maps exported names to their local addresses in the object file. Relocation table: lists locations in the code that contain addresses needing adjustment when the file is placed at its final linked address. During linking: the linker places all object files at their final addresses, then uses each relocation entry to patch the corresponding address in the code with the correct final value.

▸ Part E

  1. B8 07 00 00 00 → MOV eax, 7 → eax = 7. B9 03 00 00 00 → MOV ecx, 3 → ecx = 3.

  2. MOV ebx, 7: ebx is register 3. Opcode = 0xB8 + 3 = 0xBB. Full: BB 07 00 00 00.

Multiple C programs can compile to identical machine code. Disassembly is lossless in structure; decompilation is not.

﻿# Module 4.2 — The Stack and Calling Conventions

The Problem

You can write assembly instructions. You know how to jump to a label.

But how do functions work at the machine level? How does a function receive its arguments? How does it return a value? How does it return to exactly where it was called from — even when functions call other functions?

The answer is the stack — and the rules that govern its use are the calling convention.

Without the stack, you cannot have functions. Without functions, you cannot have programs longer than a few dozen lines. The stack is the structural foundation on which all procedural programming rests.

The Story

The Problem of Return Addresses

Suppose function A calls function B, which calls function C. Each call must eventually return to exactly the right place. How?

The naive solution: store the return address in a fixed register. But if B calls C, B's return address gets overwritten. The solution to nested calls is a stack — a last-in, first-out structure that grows as calls nest and shrinks as they return.

The stack was invented independently by several people in the early 1950s. Friedrich Bauer and Klaus Samelson in Germany, Charles Leonard Hamblin in Australia, and others all recognised that a pushdown automaton could solve the nested-call problem elegantly. By the late 1950s, the call stack was universal.

The Stack in Hardware

The x86-64 stack is a region of memory that grows downward (toward lower addresses). Two registers manage it:

RSP (Stack Pointer) — always points to the current top of the stack (the most recently pushed value). Lower RSP = more stack used.

RBP (Base Pointer / Frame Pointer) — points to the base of the current stack frame. Fixed while a function executes, allowing stable access to local variables and parameters regardless of what RSP does.

PUSH instruction:

push rax     ; RSP -= 8; memory[RSP] = rax

POP instruction:

pop rbx      ; rbx = memory[RSP]; RSP += 8

The stack is not a special hardware structure — it is ordinary memory, accessed through a convention. Any memory region could be a stack if you use it this way.

The CALL and RET Instructions

CALL target:

; equivalent to:
push rip + instruction_size   ; save return address (next instruction)
jmp target                    ; jump to function

RET:

; equivalent to:
pop rip       ; restore return address
; (CPU resumes execution at the saved address)

This is how nested calls work. Each CALL pushes a return address. Each RET pops and jumps to it. They interleave correctly because of LIFO order:

main calls A    → stack: [main_ret]
A    calls B    → stack: [main_ret, A_ret]
B    calls C    → stack: [main_ret, A_ret, B_ret]
C    returns    → pops B_ret, resumes in B
B    returns    → pops A_ret, resumes in A
A    returns    → pops main_ret, resumes in main

The Stack Frame

When a function is called, it creates a stack frame — a region of the stack containing:

  1. The saved return address (pushed by CALL)
  2. The saved RBP (pushed by the function prologue)
  3. Local variables (allocated by subtracting from RSP)
  4. Saved registers (if the function uses callee-saved registers)

Standard function prologue (x86-64):

push rbp          ; save caller's frame pointer
mov  rbp, rsp     ; set frame pointer to current stack top
sub  rsp, N       ; allocate N bytes for locals

Standard function epilogue:

mov  rsp, rbp     ; restore stack pointer (deallocate locals)
pop  rbp          ; restore caller's frame pointer
ret               ; pop return address and jump

After the prologue, local variables live at negative offsets from RBP:

[rbp - 4]  → local int a
[rbp - 8]  → local int b
[rbp - 12] → local int c

And the saved return address and caller's RBP live above RBP:

[rbp + 8]  → return address (pushed by CALL)
[rbp + 0]  → saved RBP (pushed by prologue)
[rbp - 4]  → first local variable

Calling Conventions — The Rules Everyone Agrees On

A calling convention is the agreement between caller and callee about:

  • Which registers hold function arguments
  • Which register holds the return value
  • Which registers the callee must preserve (callee-saved)
  • Which registers the callee may destroy (caller-saved)
  • How the stack must be aligned

Linux x86-64 (System V AMD64 ABI):

Purpose Registers
Integer arguments 1–6 rdi, rsi, rdx, rcx, r8, r9
Floating-point args 1–8 xmm0–xmm7
Return value rax (integer), xmm0 (float)
Callee-saved rbx, rbp, r12–r15 (must restore)
Caller-saved rax, rcx, rdx, rsi, rdi, r8–r11 (may be destroyed)
Stack alignment RSP must be 16-byte aligned at CALL site

Windows x64 ABI (different!):

  • First 4 integer args: rcx, rdx, r8, r9
  • 32-byte "shadow space" on stack required by callee
  • Different callee/caller-saved register split

This is why Windows DLLs and Linux shared libraries are binary-incompatible even on the same CPU.

A Complete Function Call Example

// C
int add(int a, int b) {
    return a + b;
}

int main() {
    int result = add(3, 4);
    return 0;
}

; Linux x86-64 — what the compiler generates

add:
    push rbp
    mov  rbp, rsp
    ; a is in edi (first arg), b is in esi (second arg)
    mov  eax, edi       ; eax = a
    add  eax, esi       ; eax = a + b
    pop  rbp
    ret                 ; return value is in eax

main:
    push rbp
    mov  rbp, rsp
    sub  rsp, 16        ; allocate space for local 'result'
    mov  edi, 3         ; first arg = 3
    mov  esi, 4         ; second arg = 4
    call add            ; call add(3, 4)
    mov  [rbp-4], eax   ; result = return value
    mov  eax, 0         ; return 0
    pop  rbp
    ret

Stack Overflow and Buffer Overflows

Stack overflow: when recursive function calls nest so deeply that RSP runs out of stack space and crashes into other memory. Default stack size is typically 1–8 MB. An infinite recursive function will always stack overflow.

Buffer overflow: when a local array on the stack is written past its end, corrupting adjacent stack data — potentially overwriting the saved return address. If an attacker controls what the return address is overwritten with, they can redirect execution to arbitrary code. This is one of the oldest and most dangerous classes of security vulnerabilities. Modern defences: stack canaries, ASLR, non-executable stack (NX bit).

The Concept: The Stack Enforces Scope

The stack's LIFO property naturally enforces the nesting of function calls. A function's local variables appear when it is called and disappear when it returns — exactly corresponding to lexical scope in high-level languages.

This is why local variables in C are "on the stack" and go away when the function returns. It is not a design decision — it is a direct consequence of how the call stack works.

Going Deeper

Tail call optimisation (TCO): if a function's last action is a call to another function, the compiler can reuse the current stack frame instead of creating a new one. This makes certain recursive algorithms (tail-recursive) use O(1) stack space instead of O(n). Functional languages (Scheme, Haskell) rely on TCO for their looping idioms.

This is the "stack trace" or "backtrace" you see in error messages. Frame pointers (RBP) are essential for reliable stack unwinding — which is why performance-sensitive code that omits them (-fomit-frame-pointer) makes debugging harder.

﻿# Module 4.3 — Operating System Concepts

The Problem

You have a CPU that can execute programs. You have memory that stores them. You have I/O devices to communicate with the world.

Now run two programs at once.

How do you prevent program A from reading program B's memory? Who decides which program gets the CPU, and for how long? What happens when a program wants to write to disk — does it get direct access to the hardware?

These are the problems the operating system exists to solve.

An OS is not magic. It is a program — but a privileged one, with exclusive access to hardware, that manages resources on behalf of all other programs and enforces the boundaries between them.

The Story

Early Computers Had No OS

On early computers, one program ran at a time. The programmer submitted a job (usually a deck of punch cards), the operator loaded it, it ran, and the output was collected. If the program crashed or ran forever, the operator killed it manually.

The batch OS (late 1950s) automated job sequencing: when one program finished, the OS automatically loaded the next. Still one program at a time, but no human required between jobs.

Time-sharing (1960s) was the revolution: multiple users sharing one computer simultaneously. The OS rapidly switched between programs, giving each a short burst of CPU time. Each user felt they had a dedicated machine. CTSS (MIT, 1961), Multics (1965–1969), and Unix (1969–1973) emerged from this era.

Unix's influence dominates to this day. Linux, macOS, Android, iOS, and BSD are all Unix-descended systems. Even Windows NT borrowed heavily from Unix/VMS concepts.

Kernel vs User Space

The operating system enforces a hardware-enforced boundary between two privilege levels:

Kernel space: where the OS kernel runs. Direct access to hardware, memory, all CPU instructions. A bug here crashes the entire system.

User space: where all applications run. Cannot directly access hardware. Cannot access another process's memory. Cannot execute privileged CPU instructions. A crash here only kills that one process.

The CPU enforces this via privilege rings (or protection levels). x86 has 4 rings (0–3); modern OSes use only ring 0 (kernel) and ring 3 (user). ARM uses EL0 (user) through EL3 (firmware).

The boundary exists for security and stability: a buggy or malicious user program cannot crash the system or access another program's data. Without this boundary, every program crash would bring down the whole machine — which is exactly what happened on early unprotected systems.

System Calls — The Bridge

User programs cannot access hardware directly. But they need to — to read files, write to screen, open network connections, allocate memory. The mechanism is the system call (syscall).

A system call is a controlled transition from user space to kernel space:

  1. User program places syscall number in rax and arguments in rdi, rsi, rdx, ...
  2. User program executes the syscall instruction
  3. CPU switches to ring 0, jumps to the kernel's syscall handler
  4. Kernel validates arguments, performs the requested operation
  5. Kernel places result in rax, returns to user space (ring 3)
; Linux x86-64 — write "hello" to stdout
mov rax, 1          ; syscall #1 = write
mov rdi, 1          ; fd = 1 (stdout)
mov rsi, msg_ptr    ; pointer to message
mov rdx, 5          ; length = 5
syscall             ; enter kernel
; rax now holds number of bytes written (or negative error code)

Common Linux syscalls:

Number Name Description
0 read Read from file descriptor
1 write Write to file descriptor
2 open Open a file
3 close Close a file descriptor
9 mmap Map memory
11 munmap Unmap memory
12 brk Adjust heap break
60 exit Terminate process
57 fork Create child process
59 execve Execute new program

The C standard library (libc) wraps syscalls in convenient functions: printf() calls write(), malloc() calls brk() or mmap(), fopen() calls open(). You use these every day without thinking about the syscall layer beneath.

Processes and Context Switching

A process is an instance of a running program. It consists of:

  • A virtual address space (more on this in Module 4.4)
  • A set of open file descriptors
  • A process ID (PID)
  • A program counter and register state
  • A stack and heap

The OS gives the illusion that multiple processes run simultaneously. In reality (on a single core), only one runs at a time. The OS uses a timer interrupt to periodically preempt the running process and switch to another.

Context switch:

  1. Timer interrupt fires — CPU jumps to kernel
  2. Kernel saves all registers of the running process to its Process Control Block (PCB)
  3. Kernel scheduler selects the next process to run
  4. Kernel restores the registers of the new process from its PCB
  5. Kernel returns to user space — the new process resumes exactly where it left off

A context switch takes ~1–10 microseconds. A modern system performs thousands per second. This is why time-sharing feels instantaneous to humans, whose perception latency is ~10 milliseconds.

The Scheduler

The scheduler decides which process runs next. Key policies:

Round Robin: each process gets a fixed time quantum (e.g., 10 ms). Fair but ignores priority.

Priority scheduling: higher-priority processes preempt lower-priority ones. Risk: starvation — a low-priority process may never run if high-priority ones keep arriving.

Completely Fair Scheduler (CFS) — used by Linux: tracks each process's "virtual runtime" (time actually executed, normalised by priority). Always runs the process with the smallest virtual runtime. Achieves fairness without explicit time quanta.

Real-time scheduling: hard deadlines. A process must run within a guaranteed time window. Used in embedded systems, audio drivers, industrial control.

Files, Processes, and Everything as Files

Unix's most elegant abstraction: everything is a file. A regular file, a directory, a terminal, a network socket, a hardware device — all accessed via the same system calls: open, read, write, close.

This uniformity means: a program that reads from stdin (fd = 0) can be redirected to read from a file, a network socket, or another program's stdout — without changing a line of the program. This is the foundation of Unix pipes and redirection.

ls -la | grep ".c" | sort > output.txt

Each | creates a pipe: a kernel buffer where the stdout of one process is connected to the stdin of the next. Three processes, running concurrently, communicating through the kernel.

The Concept: The OS as a Resource Manager

The OS does three things:

  1. Isolation: each process believes it owns the whole computer. Hardware enforces this illusion.
  2. Multiplexing: one CPU, many processes; one disk, many files; one network, many connections.
  3. Abstraction: expose clean interfaces (files, sockets, processes) that hide messy hardware realities.

Every program you have ever used benefits from all three simultaneously.

Going Deeper

fork() and exec(): Unix process creation uses two syscalls. fork() creates an exact copy of the current process (child). exec() replaces the current process's memory with a new program. The shell uses this pattern constantly: fork a child, exec the requested command in the child, parent waits for the child to finish. Signals: asynchronous notifications sent to a process. SIGTERM asks it to terminate gracefully. SIGKILL kills it immediately (cannot be caught). SIGSEGV fires when a process accesses invalid memory (segfault). SIGINT is sent when you press Ctrl+C. Signal handlers are registered with the kernel and called asynchronously.

﻿# Module 4.4 — Memory Management

The Problem

A 64-bit CPU can address 16 exabytes of memory. A typical machine has 16 gigabytes of RAM.

Every program believes it has its own private address space starting at 0x0000. Two different programs can both have a variable at address 0x4000 — and they never interfere.

How?

And how does a 4 GB program run on a machine with only 8 GB of RAM when other programs are also running?

These two mysteries have the same answer: virtual memory — one of the most elegant engineering solutions in the history of computing.

The Story

The Problem of Running Multiple Programs

On early computers, programs ran at fixed physical addresses. Loading two programs simultaneously was impossible — they would overwrite each other. The programmer had to know exactly where in physical RAM the program would be placed and write addresses accordingly.

Relocation (1950s) was the first solution: a hardware register held the base address of the current program. Every memory access added this base. Programs could move anywhere in RAM without being rewritten. But they still shared the same physical address space — a bug in one program could corrupt another's memory.

Segmentation (1960s, Multics) added boundaries: each program had a base and a limit. Hardware enforced that no access exceeded the limit. But segments were variable-size, leading to fragmentation.

Paging (late 1960s) solved fragmentation: divide all memory into fixed-size pages (typically 4 KB). Give each process its own mapping from virtual pages to physical pages. This is the system used today in every general-purpose OS.

Virtual vs Physical Addresses

Every user-space program uses virtual addresses. These are what the program sees — addresses starting at 0x0000_0000_0000_0000 and extending to 0xFFFF_FFFF_FFFF_FFFF (on 64-bit, though only 48 bits are used in practice).

Physical addresses are the actual locations in RAM chips. The CPU's Memory Management Unit (MMU) translates every virtual address into a physical address on the fly, for every memory access.

Virtual address  →  [MMU / Page Table Walk]  →  Physical address
0x00007FFF_1000          translation              0x0000_1A40_3000

Two processes can both use virtual address 0x401000 — they map to different physical addresses. Neither can see the other's memory. The OS controls the mapping.

Pages, Frames, and Page Tables

Page: a fixed-size block of virtual memory. Typically 4 KB (4096 bytes).
Frame: a fixed-size block of physical memory. Same size as a page.
Page table: a data structure mapping virtual page numbers to physical frame numbers.

For a 32-bit address space with 4 KB pages:

  • Virtual address = 20-bit page number + 12-bit page offset
  • 2²⁰ = 1,048,576 possible virtual pages
  • Each page table entry (PTE) = 4 bytes → 4 MB page table per process!

That is too large. The solution: multi-level page tables.

A 2-level page table for 32-bit systems:

Virtual address: [10 bits dir] [10 bits table] [12 bits offset]
                     ↓                ↓               ↓
               Page Directory → Page Table → Physical Frame + Offset

x86-64 uses a 4-level page table:

Virtual address: [9 bits PML4] [9 bits PDP] [9 bits PD] [9 bits PT] [12 bits offset]

Only page directories that are actually in use need to exist. A sparse address space uses very little memory for its page table.

Page Table Entries (PTEs)

Each PTE contains:

  • Physical frame number — which RAM frame this page maps to
  • Present bit (P) — 1 = this mapping exists; 0 = page not in memory (triggers page fault)
  • Writable bit (W) — 0 = read-only; 1 = writable. Enforces code section immutability.
  • User bit (U) — 0 = kernel only; 1 = user space accessible
  • Accessed bit (A) — set by hardware when the page is read. Used by page replacement algorithms.
  • Dirty bit (D) — set by hardware when the page is written. Used to know if a page needs to be written back to disk before reclaiming.
  • NX bit (No-Execute) — prevents code execution from this page. Makes data pages non-executable — critical for stack/heap security.

The TLB — Translation Lookaside Buffer

A page table walk requires up to 4 memory accesses (on x86-64). That would make every memory access 5× slower. The solution: the TLB — a small, fast cache of recent virtual→physical translations.

  • Capacity: 64–4096 entries (tiny)
  • Speed: 1 cycle (same as L1 cache)
  • Hit rate: >99% for well-behaved programs (due to temporal and spatial locality)

TLB miss: the hardware page table walker reads the page table hierarchy, loads the translation into the TLB, and retries. On x86, this is done entirely by hardware (hardware page table walker). On ARM, software can handle TLB misses.

TLB shootdown: when the OS modifies a process's page table (e.g., unmaps a page), it must invalidate the corresponding TLB entries on all CPU cores. On a multiprocessor system, this requires an inter-processor interrupt (IPI) to each core. TLB shootdowns are expensive and a significant performance cost of shared-memory multiprocessors.

Demand Paging and the Page Fault

A process does not need all its pages in physical RAM simultaneously. The OS uses demand paging: pages are loaded into RAM only when first accessed.

When a process accesses a virtual address whose PTE has Present=0:

  1. The CPU raises a page fault exception
  2. The kernel's page fault handler runs
  3. It checks: is this a valid virtual address for this process?
    • Yes: load the page from disk (swap space / file), update PTE, return
    • No: invalid access → send SIGSEGV to the process (segmentation fault)
  4. The process resumes, unaware that it paused

Copy-on-Write (CoW): when fork() creates a child process, the OS does not immediately copy the parent's memory. Instead, both parent and child share the same physical pages, marked read-only. When either process writes to a shared page, a page fault fires, the kernel copies just that page, and the write proceeds. This makes fork() nearly free even for large processes.

Swap Space

When RAM is full and a new page must be loaded, the OS must evict an existing page. If the page is dirty (modified), it is written to swap space on disk before eviction. If clean (matches the disk copy), it can be silently discarded.

Page replacement algorithms:

  • LRU (Least Recently Used): evict the page accessed longest ago. Optimal in practice but expensive to implement precisely.
  • Clock algorithm (Second Chance): approximates LRU using the Accessed bit. Scan pages in circular order; if A=1, clear it and give a second chance; if A=0, evict.
  • LFU (Least Frequently Used): evict the page accessed fewest times. Suffers from outdated frequency counts.

Modern Linux uses variants of the clock algorithm plus separate active/inactive page lists.

Process Memory Layout

A typical Linux process's virtual address space (64-bit):

0xFFFFFFFF_FFFFFFFF  ┐
                     │  Kernel space (user cannot access)
0xFFFF8000_00000000  ┘
        ...
0x00007FFF_FFFFFFFF  ┐
                     │  Stack (grows downward)
0x00007FFE_XXXXXXXX  ┘  ← RSP here
        ...
        [random ASLR gap]
        ...
                        Heap (grows upward) ← sbrk/mmap
                     ┐
                     │  .bss (uninitialised globals, zeroed)
                     │  .data (initialised globals)
0x00000000_00401000  │  .text (code, read+execute, not writable)
0x00000000_00400000  ┘  ← ELF header

The Concept: The MMU Makes Every Process Think It Owns All of Memory

This is the central illusion of modern operating systems. Each process has a complete, private virtual address space. The physical RAM is shared invisibly. The OS and MMU cooperate to maintain the illusion seamlessly — except when debugging, when the illusion's mechanics become visible and useful.

Going Deeper

Huge pages: using 4 KB pages for large memory workloads (databases, JVMs, ML models) generates enormous TLB pressure. Huge pages (2 MB on x86) reduce TLB misses by 512× for the same memory coverage. Linux supports transparent huge pages (THP), which tries to merge small pages automatically.

This is how database files, executable files, and shared libraries are loaded — the dynamic linker mmap's the ELF file sections into the process's address space.

﻿# Module 4.5 — File Systems

The Problem

You can read and write bytes at memory addresses. But when the power goes off, RAM forgets everything.

How do you give data a name that persists across power cycles? How do you organise billions of bytes on a disk into something human-navigable? How does the OS know where one file ends and another begins?

The answer is the file system — the layer that imposes order on the chaos of raw storage.

A file system solves three problems simultaneously: naming (how to find data by name), organisation (how to structure data into directories), and persistence (how to survive power loss without corruption).

The Story

Files Before File Systems

Early computers had no persistent storage. Programs and data were loaded from punch cards each run. The concept of a "file" — data with a name that persists — did not exist.

Magnetic tape (1950s) introduced persistence but no random access. Data was stored sequentially; to find record 1000, you had to scan past records 1–999. The concept of a "directory" had no meaning.

Magnetic disk (IBM RAMAC, 1956) introduced random access: the read/write head could seek to any location in milliseconds. Now you could have many files — but you needed a way to find them. The first file system concepts emerged: a table mapping names to disk locations.

Unix (1969) introduced the inode-based file system. This design — with refinements — is still used in ext4 (Linux) and HFS+ (macOS) today.

Disks and Blocks

A magnetic hard disk is divided into fixed-size blocks (also called sectors or clusters). Typical block size: 4096 bytes (4 KB).

A file system works entirely in terms of blocks, not bytes:

  • A 1-byte file occupies one full block (4 KB wasted internally — called internal fragmentation)
  • A 5000-byte file occupies two blocks (8 KB on disk, 3 KB wasted)

The block is the smallest unit of allocation. The file system maintains a data structure tracking which blocks are free and which are in use.

Inodes — The Heart of Unix File Systems

An inode (index node) is a data structure that stores all metadata about a file except its name:

inode {
  mode:      permissions (rwxrwxrwx) + file type
  uid, gid:  owner user and group IDs
  size:      file size in bytes
  atime:     last access time
  mtime:     last modification time
  ctime:     last metadata change time
  nlinks:    number of hard links to this inode
  blocks[]:  array of block addresses where data lives
             [direct blocks: 12 entries]
             [single indirect block pointer]
             [double indirect block pointer]
             [triple indirect block pointer]
}

Direct blocks: the first 12 entries point directly to data blocks. Supports files up to 12 × 4 KB = 48 KB with no indirection.

Single indirect: one block used as an array of block pointers. 4 KB / 4 bytes = 1024 pointers → 1024 × 4 KB = 4 MB additional data.

Double indirect: pointer → block of pointers → data. 1024 × 1024 × 4 KB = 4 GB.

Triple indirect: 1024³ × 4 KB = 4 TB.

This structure allows small files to be accessed very efficiently (direct blocks) while still supporting large files.

Directories — Files About Files

A directory is simply a file whose data is a table of (name → inode_number) pairs:

Directory /home/user:
.    → inode 2  (this directory)
..   → inode 1  (parent directory)
hello.c → inode 417
notes.txt → inode 821
src  → inode 1024  (subdirectory inode)

When you access /home/user/hello.c:

  1. Start at root inode (inode 2 on most systems)
  2. Read root's directory data → find "home" → get its inode number
  3. Read "home"'s directory data → find "user" → get inode number
  4. Read "user"'s directory data → find "hello.c" → get inode 417
  5. Read inode 417 → get list of data blocks
  6. Read data blocks → file contents

This is why deep directory nesting (100 levels) is slow: each level requires at least one disk read.

Hard Links and Soft Links

Hard link: a second directory entry pointing to the same inode. The inode's nlinks counter increments. The file has two names. Deleting one name decrements nlinks; data is only freed when nlinks reaches 0.

ln file.txt link.txt    # hard link: same inode, two names

Symbolic link (symlink): a file whose data is a path string. Following a symlink reads its data (the path) and redirects the lookup. Symlinks can point to directories, span file systems, and point to things that don't exist.

ln -s /path/to/target link.txt   # symlink

Hard links: same inode, same file, multiple names. Symlinks: separate inode, data = path string, like a shortcut.

The Free Space Bitmap

The file system tracks which blocks are free using a bitmap: one bit per block. Bit = 0 means free; bit = 1 means in use. Allocating a block: find a 0 bit, flip it to 1. Freeing a block: find the bit, flip it to 0.

For a 1 TB disk with 4 KB blocks: 1 TB / 4 KB = 2²⁸ blocks → bitmap = 2²⁸ bits = 32 MB. A very compact structure that fits easily in memory.

Journaling — Surviving Power Loss

Suppose the system loses power halfway through creating a file:

  • The directory was updated (points to a new inode)
  • But the inode was never written
  • Or the data blocks were written but the inode size was not updated

Without protection, the file system is now inconsistent — internal data structures contradict each other. fsck (file system check) was the traditional solution: scan the entire disk on every boot after an unclean shutdown. For a 1 TB disk this takes minutes.

Journaling (ext3, ext4, NTFS, HFS+): before making changes, write a journal entry describing what changes are about to be made. After all changes are safely written, mark the journal entry as committed.

On recovery after a crash: replay the journal. Any committed entries not yet applied are re-applied. The file system is always in a consistent state — recovery takes seconds instead of minutes.

Three modes:

  • Journal (safest): journal both metadata and data. Slowest.
  • Ordered (default ext4): journal metadata only; data flushed before metadata. Good balance.
  • Writeback (fastest): journal metadata only; no ordering guarantee for data.

FAT32 remains valuable for its universal compatibility — every device (cameras, USB drives, consoles) understands it. Everything else is better for primary storage.

The Concept: A File System is a Structured Lie

Raw storage is just blocks numbered 0 to N. The file system imposes a hierarchical namespace, persistent naming, and metadata on top of these anonymous blocks. The "file" you edit in a text editor does not physically exist as a contiguous sequence of bytes on the disk — it is an abstraction maintained by the inode and block pointer structures.

Understanding this is essential for: diagnosing disk corruption, recovering deleted files, building databases (which often bypass the file system entirely for performance), and understanding why "formatting" a disk doesn't actually erase data.

Going Deeper

Log-structured file systems (LFS): instead of updating files in place, LFS writes everything sequentially to the end of the log. Updates are always appends — no seeks, no fragmentation. Garbage collection reclaims space from old versions. Modern SSDs with their inherent sequential-write performance advantage make LFS attractive again.

B-trees in file systems: large directories with thousands of files cannot use a flat array — binary search would be needed. Modern file systems (NTFS, HFS+, btrfs, XFS) store directory contents in B-trees for O(log n) lookup. The B-tree appears at every layer of systems programming: databases (Module 9.2) also use it for the same reason.

  2. After deleting /home/alice/notes.txt (assuming nlinks drops to 0, data freed): cat shortcut.txt fails with "No such file or directory". The symlink still exists but its target path no longer resolves. Hard links avoid this because they reference the inode directly, not the path.

  3. rm bigfile.txt removes the directory entry and decrements nlinks to 0 in the inode — essentially instant (one metadata write). The inode and block bitmap bits are cleared, marking the space as available. The data bytes are NOT overwritten. The space becomes available immediately for new allocations. The old data physically remains until new files overwrite those blocks.

  4. Recovery is possible because the data bytes remain until overwritten. To make recovery impossible: overwrite the data blocks with zeros (or random data) before freeing them — the shred command does this. Secure deletion tools and full-disk encryption make forensic recovery infeasible.

▸ Part E

  1. Without journaling: inode not updated → inode points to no data blocks but bitmap says data blocks are allocated → "orphaned" blocks (allocated but not referenced). fsck must: scan all inodes, compare against block bitmap, find discrepancies, mark orphaned blocks as free. Time = proportional to disk size.

  2. In ordered mode: data blocks written first, then journal entry written with metadata changes (inode + directory). After crash: data is on disk (step 2 done), journal entry for steps 3+4 may or may not exist. Recovery: if journal entry present, replay it (write inode and directory). If not, the file doesn't exist in the directory and inode isn't updated — no inconsistency, just the file is not created. No fsck needed.

  3. Writeback: journal protects metadata consistency but data and metadata order is not guaranteed. After recovery, the file might exist (metadata written) but contain garbage data from old blocks that happened to be allocated. The journal ensures you won't have an inconsistent inode structure, but the file's content may be corrupt.

  4. Incorrect. Journaling protects file system metadata consistency — inode structures, directory entries, block allocations. It does NOT guarantee that application data written to a file reaches durable storage. Without fsync(), data may still be in the kernel's page cache (not yet on disk). A power loss drops the cached but unsynced data. fsync() forces the OS to flush all pending writes for that file to disk before returning.
