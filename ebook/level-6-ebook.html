﻿# Module 6.1 — Arrays and Linked Lists

The Problem

You need to store a collection of items. You will add items, remove items, and access them by position or by searching.

The obvious choice: just put them all in a row. But "in a row" has hidden costs. Inserting in the middle means moving everything else. Not knowing the size in advance means either wasting space or copying everything.

The first decision in every data structure course is the most fundamental: contiguous or linked?

The Story

Arrays — The First Data Structure

The array is as old as stored-program computing. A memory address is a number; an array is just a block of memory at a base address, with each element at base + index × element_size. The CPU can compute any element's address in one multiplication and one addition — O(1) access.

FORTRAN (1957), the first widely-used programming language, was built around arrays. Matrix arithmetic in FORTRAN was the entire point: scientific computing required fast access to elements by index. The array's O(1) access is why cache memory (Level 3) was designed the way it was — sequential memory access patterns fill cache lines efficiently.

Linked lists were invented slightly later, when programmers needed to handle collections whose size wasn't known at compile time. John McCarthy's Lisp (1958) was the first language built around linked lists — in Lisp, everything is a list. The language's name stands for "LISt Processing."

The Concept

Arrays

An array stores elements in contiguous memory. For an array of int (4 bytes each) starting at address A:

Element:  arr[0]   arr[1]   arr[2]   arr[3]
Address:  A+0      A+4      A+8      A+12

Random access: arr[i] → address A + i * sizeof(element) → one instruction. O(1).

Insertion at end: if capacity remains, write at arr[length] and increment length. O(1) amortised (Python lists, C++ vector double capacity when full).

Insertion at middle: must shift all elements after the insertion point right. O(n).

Deletion at middle: shift all elements after the deletion point left. O(n).

Search (unsorted): scan from index 0 until found. O(n).

Search (sorted): binary search. O(log n).

Memory: no overhead per element — just the data itself.

Dynamic Arrays

Static C arrays have fixed size declared at compile time. Dynamic arrays (Python list, C++ vector, Java ArrayList) grow automatically:

lst = []           # empty, capacity 0
lst.append(1)      # allocates initial capacity (e.g., 4 slots)
lst.append(2)      # fits in existing capacity
# ... append until capacity full
lst.append(x)      # RESIZE: allocate new array (2× capacity),
                   # copy all elements, free old array

The resize is O(n) work, but it happens rarely. Amortised analysis: n appends on a fresh list do at most O(2n) total work (geometric series: n + n/2 + n/4 + ...) → O(1) amortised per append.

Linked Lists

A linked list stores elements in nodes scattered anywhere in memory. Each node contains the data and a pointer to the next node:

[data:1 | next:→] → [data:2 | next:→] → [data:3 | next:None]
  head                                     tail

In Python:

class Node:
    def __init__(self, data, next_node=None):
        self.data = data
        self.next = next_node

class LinkedList:
    def __init__(self):
        self.head = None

    def prepend(self, data):
        self.head = Node(data, self.head)   # O(1)

    def append(self, data):                  # O(n) — must traverse to tail
        if not self.head:
            self.head = Node(data); return
        curr = self.head
        while curr.next:
            curr = curr.next
        curr.next = Node(data)

    def delete(self, data):                  # O(n) — must find node
        if not self.head: return
        if self.head.data == data:
            self.head = self.head.next; return
        curr = self.head
        while curr.next:
            if curr.next.data == data:
                curr.next = curr.next.next; return
            curr = curr.next

Insert at head: update head pointer only. O(1).
Insert at tail (without tail pointer): traverse to last node. O(n).
Insert at tail (with tail pointer maintained): O(1).
Delete given node pointer: update previous node's next. O(1) if you have the previous node, O(n) if you must find it.
Random access (list[5]): must traverse from head. O(n) — no index formula exists.
Memory: each node stores a pointer (8 bytes on 64-bit) plus the data. More overhead than arrays.

Doubly Linked Lists

Each node has both a next and prev pointer:

None ← [1] ↔ [2] ↔ [3] → None

Enables O(1) deletion when you have a pointer to the node (update both neighbours without traversing). Python's collections.deque is implemented as a doubly linked list — O(1) append and pop from both ends.

When to Use Each

Operation Array (dynamic) Linked List
Access by index O(1) O(n)
Insert at end O(1) amortised O(1) with tail ptr
Insert at start O(n) O(1)
Insert at middle O(n) O(1) with node ptr
Delete at middle O(n) O(1) with node ptr
Memory per element Low High (pointer overhead)
Cache friendliness Excellent Poor (nodes scattered)

In practice: dynamic arrays (Python lists, C++ vectors) are used for almost everything. Their cache friendliness makes them faster than linked lists even for operations where linked lists have better asymptotic complexity. Linked lists are used when: insertions/deletions in the middle are extremely frequent and you already have node pointers, or when elements must not be moved in memory (e.g., intrusive linked lists in the Linux kernel, where struct members point to each other directly).

Going Deeper

Intrusive linked lists: the Linux kernel uses a linked list where the next/prev pointers live inside the struct being managed, rather than in a separate node wrapper. This eliminates one allocation per element and one pointer dereference. The entire kernel's scheduler, file system, and network stack use list_head — a two-line struct. Understanding this requires understanding pointer arithmetic, struct layout, and container_of macros.

Skip lists: a probabilistic data structure that adds multiple levels of linked lists, each skipping more elements. Supports O(log n) search, insert, and delete — competitive with balanced BSTs but much simpler to implement. Used in Redis as the backing data structure for sorted sets.

﻿# Module 6.2 — Stacks and Queues

The Problem

Two fundamental questions about collections:

  1. When you take something out, should it be the most recently added item (Last In, First Out)? → A stack of plates, the call stack, the browser back button.

  2. Or should it be the least recently added item (First In, First Out)? → A print queue, a line at a ticket counter, CPU job scheduling.

Stacks and queues are not clever data structures. They are principled restrictions on how a collection is accessed — and those restrictions turn out to match the natural structure of dozens of important problems.

The Story

The Call Stack and the History of Stacks

The concept of a stack in computing is inseparable from the call stack — the hardware mechanism for function calls described in Module 4.2. Every time you call a function, the return address is pushed; every time you return, it is popped. This is a stack in its purest form.

Alan Turing described stack-like mechanisms in 1946 for his ACE computer design. Friedrich Bauer and Klaus Samelson in Germany, and Charles Hamblin in Australia, independently formalised the push-down stack in the late 1950s.

The calculator application of stacks came from Hamblin: Reverse Polish Notation (RPN) — write 3 4 + instead of 3 + 4. RPN evaluates perfectly with a stack and requires no parentheses, no operator precedence rules, no parse tree. HP's engineering calculators used RPN through the 1970s–80s. Understanding why RPN works is the clearest introduction to stack-based computation.

Queues formalise the fair waiting structure that humans already understood intuitively — but computers needed an explicit data structure to implement scheduling, buffering, and breadth-first search.

The Concept

Stacks — LIFO

A stack supports two operations:

  • push(item): add item to the top
  • pop(): remove and return the top item
  • peek(): look at the top item without removing it
  • is_empty(): return True if no items
class Stack:
    def __init__(self):
        self._data = []

    def push(self, item):
        self._data.append(item)       # O(1) amortised

    def pop(self):
        if self.is_empty():
            raise IndexError("pop from empty stack")
        return self._data.pop()       # O(1) amortised

    def peek(self):
        return self._data[-1]         # O(1)

    def is_empty(self):
        return len(self._data) == 0

All operations O(1) amortised using a dynamic array as backing store.

Key applications:

Expression evaluation (RPN):

def eval_rpn(tokens):
    stack = Stack()
    for t in tokens:
        if t in '+-*/':
            b, a = stack.pop(), stack.pop()
            result = {'+':a+b, '-':a-b, '*':a*b, '/':a/b}[t]
            stack.push(result)
        else:
            stack.push(float(t))
    return stack.pop()

eval_rpn(['3','4','+','2','*'])   # (3+4)*2 = 14

Balanced parentheses check:

def is_balanced(s):
    stack = Stack()
    pairs = {')':'(', ']':'[', '}':'{'}
    for c in s:
        if c in '([{':
            stack.push(c)
        elif c in ')]}':
            if stack.is_empty() or stack.pop() != pairs[c]:
                return False
    return stack.is_empty()

is_balanced("({[]})")   # True
is_balanced("({[}])")   # False

Undo/redo: push each action onto the undo stack. Ctrl+Z pops from the undo stack and pushes onto the redo stack.

DFS without recursion:

def dfs(graph, start):
    stack = Stack()
    visited = set()
    stack.push(start)
    while not stack.is_empty():
        node = stack.pop()
        if node not in visited:
            visited.add(node)
            for neighbour in graph[node]:
                stack.push(neighbour)

Queues — FIFO

A queue supports:

  • enqueue(item): add item to the back
  • dequeue(): remove and return the front item
  • peek(): look at the front item
  • is_empty()

Implementing a queue with a Python list is inefficient: list.pop(0) is O(n) because it shifts every element. Use Python's collections.deque (doubly linked list):

from collections import deque

class Queue:
    def __init__(self):
        self._data = deque()

    def enqueue(self, item):
        self._data.append(item)         # O(1)

    def dequeue(self):
        if self.is_empty():
            raise IndexError("dequeue from empty queue")
        return self._data.popleft()     # O(1)

    def is_empty(self):
        return len(self._data) == 0

Key applications:

BFS (Breadth-First Search):

def bfs(graph, start):
    queue = Queue()
    visited = set([start])
    queue.enqueue(start)
    while not queue.is_empty():
        node = queue.dequeue()
        for neighbour in graph[node]:
            if neighbour not in visited:
                visited.add(neighbour)
                queue.enqueue(neighbour)

Process scheduling: the OS maintains a run queue of processes waiting for CPU time. Round Robin scheduling enqueues a process when its turn ends and dequeues the next one.

Printer spooler: jobs arrive and are enqueued. The printer dequeues and prints one at a time.

Circular Buffer (Ring Buffer)

A fixed-size queue implemented as an array with two pointers (head and tail). When they reach the end of the array, they wrap around. No dynamic resizing needed:

Array: [_, _, 3, 4, 5, _, _]   (size 7)
            ↑           ↑
           head         tail (next write position)

Used in: audio buffers (steady stream of samples), network packet buffers, producer-consumer queues in embedded systems. O(1) enqueue and dequeue with a fixed, pre-allocated memory footprint.

Monotonic Stack

A stack where elements are always in sorted order (either monotonically increasing or decreasing). Used to solve problems like "next greater element" in O(n):

def next_greater_element(arr):
    result = [-1] * len(arr)
    stack = []                    # stores indices
    for i, x in enumerate(arr):
        while stack and arr[stack[-1]] < x:
            idx = stack.pop()
            result[idx] = x       # x is the next greater for arr[idx]
        stack.append(i)
    return result

next_greater_element([4, 1, 2, 3])   # [-1, 2, 3, -1]

The naïve nested loop approach is O(n²). The monotonic stack approach is O(n) — each element is pushed and popped at most once.

Going Deeper

Priority queues: a generalisation of the queue where each item has a priority, and dequeue() always returns the highest-priority item. Implemented with a heap (Module 6.5). Used in: Dijkstra's shortest path, A* search, OS task scheduling, Huffman coding, event-driven simulation.

Lock-free queues: in multi-threaded systems, locking a queue for every enqueue/dequeue creates a bottleneck. Lock-free queues use CPU atomic compare-and-swap (CAS) instructions to safely update head/tail pointers without locks. Michael and Scott's lock-free queue (1996) is the standard algorithm — it uses a sentinel node and a pair of atomic pointer updates. Used in high-performance message queues, garbage collectors, and OS schedulers.

﻿# Module 6.3 — Hash Tables

The Problem

You have 10 million user records. For each web request, you need to look up a user by username. A sorted array gives O(log n) — about 23 comparisons per lookup. A linear scan gives O(n) — up to 10 million comparisons.

Can we do better than O(log n)? Can we achieve O(1) — constant time regardless of how many users exist?

Yes. The answer is a hash table — one of the most important data structures ever invented, used in every database, every caching layer, every programming language's built-in dictionary type.

The Story

The Birth of Hashing

The concept of hash functions appeared in the early 1950s as a way to accelerate data retrieval on magnetic tape systems, where random access was impossible. Hans Peter Luhn of IBM described a hashing technique in 1953 for chained overflow buckets — essentially the same as what we use today.

The first thorough theoretical treatment came from Arnold Dumey (1956), who coined the term "hash" and analysed collision resolution strategies. By the 1960s, every major database system used hash indexes for O(1) lookup.

The insight: instead of storing elements in order (requiring log n steps to find), store each element at the index determined by a function of its key. Finding it later requires only recomputing that function — one step, regardless of table size.

The Concept

The Core Idea

A hash table uses an array of fixed size M (the "buckets") and a hash function h(key) → [0, M-1] to map keys to array indices.

Insert: compute h(key), store the key-value pair at table[h(key)].
Lookup: compute h(key), return table[h(key)].
Delete: compute h(key), remove from table[h(key)].

If the hash function maps different keys to different indices, all operations are O(1).

# Extremely simplified — no collision handling
class TinyHashTable:
    def __init__(self, size=16):
        self.size = size
        self.table = [None] * size

    def _hash(self, key):
        return hash(key) % self.size   # Python's built-in hash function

    def set(self, key, value):
        self.table[self._hash(key)] = value

    def get(self, key):
        return self.table[self._hash(key)]

The Collision Problem

A collision occurs when two different keys hash to the same index. This is inevitable: if you store 1 million keys in a table of 1 million slots, by the Birthday Paradox, collisions start happening after only ~1,000 insertions. Two strategies:

1. Chaining (Separate Chaining)

Each bucket holds a linked list of all key-value pairs that hash there:

Table:
index 0: → [(alice, 30)] → None
index 1: → None
index 2: → [(bob, 25)] → [(carol, 28)] → None   ← collision
index 3: → [(dave, 22)] → None
...

Lookup: hash key → find bucket → scan linked list for matching key.

  • Average case: O(1) if the load factor (n/M) is bounded by a constant
  • Worst case: O(n) if all keys hash to the same bucket
  • Space: extra pointer per element

Python's dict uses a variant of open addressing (below), but conceptually, chaining is the cleaner mental model.

2. Open Addressing (Linear Probing)

No linked lists — all entries stored in the array itself. On collision, probe for the next empty slot:

def _insert(self, key, value):
    idx = self._hash(key)
    while self.table[idx] is not None:
        if self.table[idx][0] == key:    # update existing
            self.table[idx] = (key, value); return
        idx = (idx + 1) % self.size      # linear probe: try next slot
    self.table[idx] = (key, value)
  • Better cache performance than chaining (no pointer chasing, everything in one array)
  • Clustering problem: long runs of occupied slots form, making probing slow
  • Load factor must stay below ~0.7 — resize when exceeded
  • Deletion is tricky: cannot just clear a slot (breaks the probe chain). Use a "tombstone" marker.

Quadratic probing (idx = (idx + c₁i + c₂i²) % M) and double hashing (idx = (h1(key) + i × h2(key)) % M) spread keys more evenly and reduce clustering.

The Hash Function

A good hash function:

  • Is deterministic: h(k) = h(k) always
  • Is fast to compute: ideally O(1) for fixed-size keys
  • Distributes keys uniformly across buckets
  • Minimises collisions for real-world key distributions

For integers: simple approaches include modular hashing h(k) = k mod M. But if M is a power of 2, only the low bits matter — if keys cluster in low bits, so do their hashes. Better: use a prime M, or multiply by a large constant and take the high bits.

For strings: sum character values mod M is poor (anagrams collide). Better:

def hash_string(s, M):
    h = 0
    for c in s:
        h = (h * 31 + ord(c)) % M   # Horner's method, prime multiplier
    return h

Python's hash() for strings uses SipHash-1-3, a cryptographic-strength hash function, specifically to prevent hash flooding attacks — an adversary who knows the hash function can craft inputs that all map to the same bucket, turning O(1) lookup into O(n). SipHash uses a secret seed randomised per process startup.

Load Factor and Resizing

The load factor α = n / M (number of stored items / table size).

With chaining: expected O(1 + α) per lookup. Keep α < 1.
With open addressing: performance degrades rapidly above α ≈ 0.7. Keep α < 0.7.

When α exceeds the threshold, resize: allocate a new table of size ~2M, rehash all existing entries into the new table. This is O(n) work but happens infrequently.

Python's dict resizes when 2/3 full. Java's HashMap resizes at load factor 0.75.

Python's dict Implementation

Python dict uses open addressing with pseudo-random probing:

  1. Initial size: 8 slots
  2. Hash function: hash(key) % size for initial index
  3. On collision: use a probe sequence based on the full hash value (not linear) to reduce clustering
  4. Load factor threshold: 2/3 → resize to ~2× size, rehash all entries
  5. Since Python 3.7: dicts preserve insertion order — achieved by maintaining a separate compact array of entry indices

The CPython dict implementation is one of the most carefully optimised data structures in existence. It has been tuned over 30 years to be fast for the most common Python use cases.

Going Deeper

Consistent hashing: used in distributed databases and content delivery networks. When you add or remove a server, consistent hashing reassigns only n/m keys (where n = total keys, m = number of servers) rather than all keys. This is why DynamoDB, Cassandra, and Memcached can add/remove nodes without a full data reshuffle.

Used in Rust's HashMap and several modern hash table implementations. Achieves better worst-case performance than standard linear probing.

﻿# Module 6.4 — Trees: BST, AVL, Red-Black

The Problem

A sorted array gives O(log n) search via binary search. But inserting into a sorted array is O(n) — you must shift elements.

A linked list gives O(1) insert (given the right position). But search is O(n) — no binary search without random access.

Can we have both O(log n) search AND O(log n) insert?

Yes. The answer is the balanced binary search tree — a data structure that maintains sorted order dynamically, giving O(log n) for search, insert, and delete simultaneously.

The Story

Binary Search Trees — The Concept

A binary search tree (BST) stores keys in a tree structure such that for any node with key k:

  • All keys in the left subtree < k
  • All keys in the right subtree > k

This property enables binary-search-style lookups: at each node, compare the target to k and go left (smaller) or right (larger). With a balanced tree of n nodes, height ≈ log₂ n, so search takes O(log n) steps.

George Boole's logical algebra (1854) and Leonhard Euler's graph theory (1736) laid mathematical groundwork, but BSTs as a data structure were formalised in the early 1960s in connection with symbol tables for compilers. Compilers needed to look up variable names rapidly — a BST on variable names gave O(log n) lookup vs O(n) for a linear scan.

The problem came quickly: trees go wrong. Insert keys in sorted order (1, 2, 3, 4, 5...) and the BST degenerates into a linked list — O(n) for everything. The solution: self-balancing trees.

G.M. Adelson-Velsky and E.M. Landis (1962) invented the AVL tree — the first self-balancing BST, named after their initials. Rudolf Bayer and Ed McCreight (1972) invented the B-tree (used in databases, Module 9.2). Leonidas Guibas and Robert Sedgewick (1978) invented the red-black tree, now used in Linux's scheduler, C++ std::map, Java TreeMap, and virtually every language's sorted map.

The Concept

Binary Search Tree (BST)

class BSTNode:
    def __init__(self, key, val=None):
        self.key   = key
        self.val   = val
        self.left  = None
        self.right = None

class BST:
    def search(self, node, key):
        if node is None or node.key == key:
            return node
        if key < node.key:
            return self.search(node.left, key)
        return self.search(node.right, key)

    def insert(self, node, key, val=None):
        if node is None:
            return BSTNode(key, val)
        if key < node.key:
            node.left  = self.insert(node.left, key, val)
        elif key > node.key:
            node.right = self.insert(node.right, key, val)
        else:
            node.val = val   # update existing
        return node

In-order traversal (left → root → right) produces keys in sorted order — this is the fundamental property:

def inorder(node):
    if node:
        inorder(node.left)
        print(node.key)
        inorder(node.right)

Delete: three cases:

  1. Node has no children → remove it
  2. Node has one child → replace node with child
  3. Node has two children → replace node's key with in-order successor (smallest key in right subtree), then delete the successor

Complexity (balanced tree): O(log n) search, insert, delete.
Complexity (worst case — degenerate): O(n) for all operations.

AVL Trees — Height-Balanced

An AVL tree maintains the balance factor for every node: height(left) - height(right) ∈ {-1, 0, 1}. After every insert or delete, the tree rotates nodes to restore balance.

Rotations (O(1) operations):

Right rotation at node y:

    y              x
   / \            / \
  x   C    →    A   y
 / \                / \
A   B              B   C

Left rotation at node x:

  x                y
 / \              / \
A   y    →      x   C
   / \          / \
  B   C        A   B

Four cases after insertion:

  • Left-Left: single right rotation at unbalanced node
  • Right-Right: single left rotation
  • Left-Right: left rotation on left child, then right rotation on node
  • Right-Left: right rotation on right child, then left rotation on node

AVL trees guarantee height ≤ 1.44 × log₂(n+2). All operations strictly O(log n).

Red-Black Trees — Practically Faster

A red-black tree uses node colours (red/black) and a simpler set of invariants to maintain approximate balance:

  1. Every node is red or black
  2. The root is black
  3. Every leaf (null sentinel) is black
  4. If a node is red, both children are black (no two consecutive reds)
  5. All paths from any node to its descendant leaves contain the same number of black nodes

These rules guarantee height ≤ 2 × log₂(n+1). Red-black trees perform fewer rotations than AVL trees on average (AVL is more strictly balanced), making them faster in practice for workloads with many insertions and deletions.

Used in: Linux kernel (CFS scheduler, memory management), C++ std::map/std::set, Java TreeMap/TreeSet, Rust BTreeMap, most language standard library sorted containers.

from collections import deque
def level_order(root):
    q = deque([root])
    while q:
        node = q.popleft()
        print(node.key)
        if node.left:  q.append(node.left)
        if node.right: q.append(node.right)

BST as a Sorted Map

A balanced BST implements the sorted map (or ordered dictionary) ADT:

  • search(key) → O(log n)
  • insert(key, value) → O(log n)
  • delete(key) → O(log n)
  • min() / max() → O(log n)
  • successor(key) / predecessor(key) → O(log n)
  • range_query(lo, hi) → O(log n + k) where k = number of results

This range query capability is what makes BSTs superior to hash tables when you need ordered queries (e.g., "find all users with age between 20 and 30").

Post-order iterative: use two stacks, or push root; while stack: pop to result_stack, push left then right; then reverse result_stack.

﻿# Module 6.5 — Heaps and Priority Queues

The Problem

You are managing a hospital emergency room. Patients arrive continuously, each with a severity score. At any moment, the next patient to be treated should be the one with the highest severity — not the one who arrived first, and not a random one.

This is the priority queue problem: a collection where we always want efficient access to the minimum (or maximum) element.

An unsorted array gives O(n) for "find the minimum" — too slow. A sorted array gives O(1) for "find the minimum" but O(n) for insert — still too slow. A heap gives O(log n) for both insert and extract-min, with O(1) find-min.

The Story

Heapsort and Priority Queues

The heap data structure was invented by J. W. J. Williams in 1964, in the same paper that introduced Heapsort. Williams needed a data structure that could both maintain a partially-sorted order and allow efficient extraction of the maximum element — essentially a priority queue. The key insight was to store the structure as a binary tree implicitly in an array, using index arithmetic instead of pointers.

Robert Floyd (1964) improved the heap construction algorithm from O(n log n) to O(n) in the same year — a beautiful result showing that you can build a heap from an arbitrary array in linear time by "heapifying" from the bottom up rather than inserting elements one by one.

Heaps are used pervasively in systems software: Linux's Completely Fair Scheduler uses a red-black tree (a tree with heap-like properties) to manage processes. Dijkstra's algorithm, first described in 1959, uses a priority queue (typically a heap) to always expand the nearest unvisited node.

The Concept

The Heap Property

A binary heap is a complete binary tree (every level filled except possibly the last, filled left to right) satisfying the heap property:

Max-heap: every node's value ≥ its children's values. The maximum is always at the root.
Min-heap: every node's value ≤ its children's values. The minimum is always at the root.

Max-heap example:
        90
       /  \
      80   70
     / \  / \
    50  60 40 30
   / \
  20  10

Array Representation — No Pointers Needed

A complete binary tree maps to an array without any pointers:

Index:   0   1   2   3   4   5   6   7   8
Value:  [90, 80, 70, 50, 60, 40, 30, 20, 10]

For node at index i:
  Parent:       (i - 1) // 2
  Left child:   2*i + 1
  Right child:  2*i + 2

This is elegant: the heap is just an array, and all navigation is index arithmetic. Cache-friendly, zero pointer overhead.

Core Operations

peek_max() / peek_min(): return heap[0]. O(1).

insert(x) — "sift up" (also called "bubble up"):

  1. Append x to end of array (at position n)
  2. While x is greater than its parent and we're not at root:
    • Swap x with parent
    • Move up (i = parent index)
  3. Heap property restored. O(log n) — tree height.
def insert(heap, x):
    heap.append(x)
    i = len(heap) - 1
    while i > 0:
        parent = (i - 1) // 2
        if heap[i] > heap[parent]:      # max-heap condition
            heap[i], heap[parent] = heap[parent], heap[i]
            i = parent
        else:
            break

extract_max() — "sift down" (also called "heapify down"):

  1. Root (maximum) is the answer to return
  2. Move last element to root (to fill the gap)
  3. While root is less than either child:
    • Swap with the larger child
    • Move down
  4. Return the original root. O(log n).
def extract_max(heap):
    if not heap: raise IndexError
    max_val = heap[0]
    heap[0] = heap.pop()    # move last to root
    # sift down
    i = 0
    n = len(heap)
    while True:
        left, right = 2*i+1, 2*i+2
        largest = i
        if left < n and heap[left] > heap[largest]:   largest = left
        if right < n and heap[right] > heap[largest]: largest = right
        if largest == i: break
        heap[i], heap[largest] = heap[largest], heap[i]
        i = largest
    return max_val

build_heap(arr) — Floyd's algorithm, O(n):

Rather than inserting n elements one by one (O(n log n)), start from the last non-leaf and sift down every internal node:

def build_heap(arr):
    n = len(arr)
    for i in range((n-2)//2, -1, -1):    # start from last non-leaf
        sift_down(arr, i, n)
    return arr

The O(n) analysis: most nodes are near the bottom of the tree and need to sift down very few levels. The total work is bounded by the sum of heights, which is O(n) (geometric series).

Python's heapq Module

Python provides a min-heap implementation:

import heapq

heap = []
heapq.heappush(heap, 5)
heapq.heappush(heap, 3)
heapq.heappush(heap, 8)
heapq.heappush(heap, 1)

print(heapq.heappop(heap))   # 1 (minimum)
print(heapq.heappop(heap))   # 3

# Build heap in O(n):
data = [5, 3, 8, 1, 9, 2]
heapq.heapify(data)          # in-place, O(n)

# nlargest and nsmallest:
heapq.nlargest(3, data)      # [9, 8, 5]
heapq.nsmallest(2, data)     # [1, 2]

For a max-heap in Python, negate values: push -x and negate on pop.

Heapsort — O(n log n) In-Place

def heapsort(arr):
    # Step 1: build max-heap O(n)
    n = len(arr)
    for i in range((n-2)//2, -1, -1):
        sift_down(arr, i, n)
    # Step 2: extract max n times O(n log n)
    for i in range(n-1, 0, -1):
        arr[0], arr[i] = arr[i], arr[0]   # swap max to end
        sift_down(arr, 0, i)               # restore heap on remaining

Heapsort is in-place (O(1) extra space) and always O(n log n). In practice it is slower than Quicksort due to poor cache behaviour — elements are accessed in a tree pattern rather than sequentially.

The Priority Queue as an Interface

The heap implements the priority queue abstract data type (ADT):

  • insert(item, priority) — add item with given priority
  • extract_min() / extract_max() — remove and return highest-priority item
  • decrease_key(item, new_priority) — lower the priority of an existing item (needed for Dijkstra's)

Applications:

  • Dijkstra's shortest path: priority queue of (distance, node) — always expand the nearest unvisited node
  • A* search: priority queue of (f-score, node) — expand most promising node first
  • Huffman coding: extract the two smallest-frequency symbols to merge
  • k-way merge: merge k sorted lists using a min-heap of (current_element, list_index)
  • Event simulation: process events in time order using a min-heap of (time, event)

Going Deeper

Fibonacci heaps: a more complex heap structure that achieves O(1) amortised insert and decrease-key (vs O(log n) for binary heaps). This reduces Dijkstra's complexity from O((V+E) log V) to O(E + V log V) — significant for dense graphs. In practice, Fibonacci heaps have high constant factors and are rarely used in real implementations.

d-ary heaps: a heap where each node has d children (instead of 2). Larger d means faster decrease-key (fewer levels to sift) but slower extract-min (more children to compare). For Dijkstra's on graphs with many edge relaxations, a 4-heap or 8-heap often outperforms a binary heap.

﻿# Module 6.6 — Graphs: BFS, DFS, Dijkstra, A*

The Problem

A road network. A social network. The internet. A circuit board. A gene regulatory network. All of these are the same mathematical object: a graph.

How do you find the shortest route from A to B in a city with 10,000 intersections? How does Google find the shortest degree of separation between two people? How does a GPS recalculate a route in real time?

These all reduce to graph search problems — and understanding them means understanding the structure of almost every networked system ever built.

The Story

Leonhard Euler and the Bridges of Königsberg

In 1736, Leonhard Euler solved the first graph theory problem: is it possible to walk through Königsberg (now Kaliningrad, Russia) crossing each of its seven bridges exactly once? He proved it was impossible by abstraction: replace land masses with nodes, bridges with edges. The problem reduces to whether an Eulerian path exists — which requires at most two nodes of odd degree. Königsberg had four nodes of odd degree: impossible.

This was the birth of graph theory, 200 years before computers.

Edsger Dijkstra invented his shortest-path algorithm in 1956, reportedly in 20 minutes while sitting in a café in Amsterdam, without pen and paper. He was designing software for the first Dutch computer (ARMAC) and needed a test program. The algorithm he invented became one of the most widely used in computer science.

Peter Hart, Nils Nilsson, and Bertram Raphael invented A* at Stanford Research Institute in 1968, as part of the Shakey robot project — a robot that needed to navigate a room. A* added a heuristic to Dijkstra's algorithm to guide the search toward the goal, dramatically reducing unnecessary exploration.

The Concept

Graph Representation

Adjacency List (preferred for sparse graphs):

graph = {
    'A': ['B', 'C'],
    'B': ['A', 'D', 'E'],
    'C': ['A', 'F'],
    'D': ['B'],
    'E': ['B', 'F'],
    'F': ['C', 'E']
}

Space: O(V + E). Checking if edge (u,v) exists: O(degree(u)).

Adjacency Matrix (preferred for dense graphs):

# n×n matrix where matrix[i][j] = 1 if edge exists
matrix = [
    [0, 1, 1, 0, 0, 0],  # A
    [1, 0, 0, 1, 1, 0],  # B
    ...
]

Space: O(V²). Checking edge existence: O(1).

Breadth-First Search (BFS)

Explores all neighbours of a node before moving to their neighbours. Uses a queue. Finds the shortest path (fewest edges) in an unweighted graph.

from collections import deque

def bfs(graph, start):
    visited = {start: None}    # node → parent (for path reconstruction)
    queue   = deque([start])
    while queue:
        node = queue.popleft()
        for neighbour in graph[node]:
            if neighbour not in visited:
                visited[neighbour] = node
                queue.append(neighbour)
    return visited

def shortest_path(graph, start, end):
    visited = bfs(graph, start)
    if end not in visited: return None
    path = []
    node = end
    while node is not None:
        path.append(node)
        node = visited[node]
    return list(reversed(path))

Time: O(V + E). Space: O(V). Guarantees shortest path in unweighted graphs.

Depth-First Search (DFS)

Goes as deep as possible before backtracking. Uses a stack (or recursion). Finds connected components, detects cycles, produces topological orderings.

def dfs_recursive(graph, node, visited=None):
    if visited is None: visited = set()
    visited.add(node)
    for neighbour in graph[node]:
        if neighbour not in visited:
            dfs_recursive(graph, neighbour, visited)
    return visited

def dfs_iterative(graph, start):
    visited = set()
    stack = [start]
    while stack:
        node = stack.pop()
        if node not in visited:
            visited.add(node)
            for neighbour in graph[node]:
                if neighbour not in visited:
                    stack.append(neighbour)
    return visited

Applications of DFS:

  • Cycle detection: if DFS encounters a grey (in-progress) node, there's a cycle
  • Topological sort: DFS-based, used in build systems (make, Gradle)
  • Connected components: run DFS from each unvisited node
  • Maze solving: DFS finds a path (not necessarily shortest)

Dijkstra's Shortest Path

For weighted graphs (each edge has a cost/distance). Generalises BFS using a priority queue instead of a plain queue — always expand the unvisited node with the smallest known distance.

import heapq

def dijkstra(graph_weighted, start):
    # graph_weighted: {node: [(neighbour, weight), ...]}
    dist = {start: 0}
    pq   = [(0, start)]        # (distance, node)
    while pq:
        d, node = heapq.heappop(pq)
        if d > dist.get(node, float('inf')):
            continue           # stale entry
        for neighbour, weight in graph_weighted[node]:
            new_dist = dist[node] + weight
            if new_dist < dist.get(neighbour, float('inf')):
                dist[neighbour] = new_dist
                heapq.heappush(pq, (new_dist, neighbour))
    return dist

Time: O((V + E) log V) with a binary heap.
Correctness: only works on graphs with non-negative edge weights. Negative weights require Bellman-Ford.

A* Search

Dijkstra explores in all directions equally — expanding the cheapest frontier node regardless of direction. A* adds a heuristic h(n) estimating the cost from n to the goal:

f(n) = g(n) + h(n)

where g(n) = actual cost from start to n, h(n) = estimated cost from n to goal.

If h(n) is admissible (never overestimates the true cost), A* always finds the optimal path while exploring fewer nodes than Dijkstra.

def astar(graph, start, goal, heuristic):
    pq = [(heuristic(start, goal), 0, start)]
    g  = {start: 0}
    while pq:
        f, cost, node = heapq.heappop(pq)
        if node == goal:
            return cost
        if cost > g.get(node, float('inf')):
            continue
        for neighbour, weight in graph[node]:
            new_g = g[node] + weight
            if new_g < g.get(neighbour, float('inf')):
                g[neighbour] = new_g
                f_score = new_g + heuristic(neighbour, goal)
                heapq.heappush(pq, (f_score, new_g, neighbour))
    return float('inf')   # no path found

GPS navigation: heuristic = straight-line distance to destination (Euclidean or haversine). Nodes = road intersections. Edges = road segments with travel time as weight.

﻿# Module 6.7 — Sorting: Merge, Quick, Radix

The Problem

Module 5.5 introduced sorting and Big-O complexity. Now we go deeper: not just what these algorithms do, but why they work, what guarantees they provide, how to implement them correctly at the code level, and when to choose each one for a real problem.

Three algorithms dominate practical sorting: Merge Sort for guaranteed O(n log n), Quick Sort for real-world speed, and Radix Sort for when you can beat the comparison lower bound.

The Story

The Race for Practical Sorting

By the 1960s, sorting was known to have an O(n log n) lower bound for comparison-based methods. Merge Sort (von Neumann, 1945) achieved this but required O(n) extra memory. Shell Sort (1959) was faster in practice but its worst case was unclear. Tony Hoare's Quicksort (1962) was average-case O(n log n) and in-place — a stunning combination.

For decades, the battle between Merge Sort and Quicksort dominated practical computing. IBM's OS/360 used Merge Sort for stability and predictability. Unix's qsort used Quicksort for speed. Java's Arrays.sort for primitives uses Dual-Pivot Quicksort (Yaroslavskiy, 2009). Python's list.sort() uses Timsort (Peters, 2002) — a hybrid Merge Sort that exploits real-world patterns.

The key insight that drove modern sort implementations: theoretical worst cases matter less than average-case performance on real data. Real data is often partially sorted, has repeated elements, or exhibits patterns. Good sorts exploit these patterns.

The Concept

Merge Sort — Full Implementation

def merge_sort(arr):
    if len(arr) <= 1:
        return arr
    mid = len(arr) // 2
    left  = merge_sort(arr[:mid])
    right = merge_sort(arr[mid:])
    return merge(left, right)

def merge(left, right):
    result = []
    i = j  = 0
    while i < len(left) and j < len(right):
        if left[i] <= right[j]:     # <= for stability
            result.append(left[i]); i += 1
        else:
            result.append(right[j]); j += 1
    result.extend(left[i:])
    result.extend(right[j:])
    return result

Bottom-up Merge Sort (iterative, avoids recursion overhead):

def merge_sort_iterative(arr):
    n = len(arr)
    width = 1
    while width < n:
        for i in range(0, n, 2 * width):
            left  = arr[i : i + width]
            right = arr[i + width : i + 2 * width]
            arr[i : i + len(left) + len(right)] = merge(left, right)
        width *= 2
    return arr

Bottom-up avoids the O(log n) recursion stack — useful when stack space is limited.

Correctness proof by induction: base case (len ≤ 1 is sorted), inductive step (merge of two sorted arrays is sorted), merge is correct (takes the smaller of two heads at each step). Merging two arrays of total size m takes exactly m-1 comparisons at most.

Quicksort — Correct and Efficient Implementation

The key to correct Quicksort is the partition function. The most common bug: incorrect boundary conditions.

import random

def quicksort(arr, lo=0, hi=None):
    if hi is None: hi = len(arr) - 1
    if lo >= hi: return
    pivot_idx = partition(arr, lo, hi)
    quicksort(arr, lo, pivot_idx - 1)
    quicksort(arr, pivot_idx + 1, hi)

def partition(arr, lo, hi):
    # Randomise pivot to avoid worst case on sorted input
    rand_idx = random.randint(lo, hi)
    arr[rand_idx], arr[hi] = arr[hi], arr[rand_idx]
    pivot = arr[hi]
    i = lo - 1
    for j in range(lo, hi):
        if arr[j] <= pivot:
            i += 1
            arr[i], arr[j] = arr[j], arr[i]
    arr[i+1], arr[hi] = arr[hi], arr[i+1]
    return i + 1

Three-way partition (Dutch National Flag, Dijkstra 1976) — handles duplicates efficiently:

def quicksort_3way(arr, lo, hi):
    if lo >= hi: return
    lt, gt = lo, hi
    pivot  = arr[lo]
    i = lo + 1
    while i <= gt:
        if   arr[i] < pivot: arr[lt], arr[i] = arr[i], arr[lt]; lt += 1; i += 1
        elif arr[i] > pivot: arr[gt], arr[i] = arr[i], arr[gt]; gt -= 1
        else:                i += 1
    quicksort_3way(arr, lo, lt - 1)
    quicksort_3way(arr, gt + 1, hi)

With three-way partitioning, an array of all identical elements sorts in O(n) — each element is compared exactly once and placed in the "equal" region.

Introsort (David Musser, 1997): Quicksort with a fallback to Heapsort when recursion depth exceeds 2·log₂(n). Guarantees O(n log n) worst case while keeping Quicksort's average-case speed. Used in C++ std::sort.

Counting Sort and Radix Sort

When keys are integers in a bounded range [0, k], we can sort in O(n + k) — faster than O(n log n).

Counting Sort:

def counting_sort(arr, k):
    count = [0] * (k + 1)
    for x in arr:
        count[x] += 1
    # Cumulative counts (for stable positioning)
    for i in range(1, k+1):
        count[i] += count[i-1]
    output = [0] * len(arr)
    for x in reversed(arr):    # reversed for stability
        count[x] -= 1
        output[count[x]] = x
    return output

O(n + k) time and space. Optimal when k = O(n) — e.g., sorting ages (k=150), test scores (k=100), ASCII characters (k=128).

Radix Sort — sort digit by digit, least significant to most significant:

def radix_sort(arr):
    if not arr: return arr
    max_val = max(arr)
    exp = 1
    while max_val // exp > 0:
        arr = counting_sort_by_digit(arr, exp)
        exp *= 10
    return arr

def counting_sort_by_digit(arr, exp):
    n = len(arr)
    count  = [0] * 10
    output = [0] * n
    for x in arr:
        digit = (x // exp) % 10
        count[digit] += 1
    for i in range(1, 10):
        count[i] += count[i-1]
    for x in reversed(arr):
        digit = (x // exp) % 10
        count[digit] -= 1
        output[count[digit]] = x
    return output

For 32-bit integers with base 256: 4 passes, each O(n) → O(4n) = O(n) total.

Why does it work? Sorting by LSD (Least Significant Digit) first, then MSD last, with a stable sort at each step, produces a correctly sorted array. Stability is critical: elements equal on the current digit must retain their relative order from previous digit sorts.

The Lower Bound and When to Break It

Comparison-based lower bound theorem: any sort that only uses comparisons (a < b?) requires Ω(n log n) comparisons in the worst case. Proof: the decision tree has n! leaves (all possible orderings), height ≥ log₂(n!) = Θ(n log n).

Radix sort breaks this bound because it doesn't compare — it uses the key's digits as array indices. It operates outside the comparison model. But the price: it only works on integer (or integer-encoded) keys and requires O(n) extra space.

Going Deeper

Timsort in detail: Python's Timsort finds natural "runs" of already-sorted data. If a run is shorter than minrun (≈32), it extends it with binary insertion sort. Runs are merged using a careful strategy that maintains a stack of runs satisfying size invariants — ensuring no merge is much larger than its neighbours. This is why sorted([1,2,3,4,5,6,7,8]) is nearly instant in Python even though Mergesort is O(n log n): Timsort detects the single ascending run in O(n) and returns immediately.

Parallel sorting: modern CPUs have many cores. Merge Sort parallelises naturally — sort left and right halves on separate threads, then merge. The parallel time complexity is O(n/p + n) where p = number of processors. GPU-based radix sort can sort 100 million integers per second on modern hardware.

﻿# Module 6.8 — Dynamic Programming

The Problem

Naive recursion for Fibonacci: each call to fib(n) spawns two more. fib(50) requires 2⁵⁰ ≈ 10¹⁵ calls — impossible.

But fib(50) only has 50 distinct sub-problems: fib(0), fib(1), ..., fib(49). If we compute each one once and store the result, we need exactly 50 operations.

This is dynamic programming in its essence: identify overlapping sub-problems, solve each once, store the result, and build the final answer from stored sub-results.

Dynamic programming (DP) transforms exponential-time recursive algorithms into polynomial-time ones — one of the most powerful algorithmic techniques in computer science.

The Story

Richard Bellman and the Name

Richard Bellman coined the term "dynamic programming" in 1953 while working at RAND Corporation on optimal control problems. The name was deliberately chosen to sound impressive and avoid scrutiny — Bellman was working under a Secretary of Defense who disliked mathematics research, so he named it to be vague and unchallengeable.

The actual technique — breaking problems into sub-problems and storing results — had been used informally for centuries. But Bellman formalised it as a general principle and developed the principle of optimality: an optimal solution to the whole problem contains optimal solutions to its sub-problems.

DP is fundamental to: sequence alignment in bioinformatics (finding how similar two DNA sequences are), compiler optimisation (code generation), network routing (Bellman-Ford), speech recognition (Viterbi algorithm), machine translation, and game playing (minimax with memoisation).

The Concept

Two Approaches: Top-Down and Bottom-Up

Top-Down (Memoisation): write the natural recursion, cache results in a dictionary.

from functools import lru_cache

@lru_cache(maxsize=None)
def fib(n):
    if n <= 1: return n
    return fib(n-1) + fib(n-2)

# Or manually:
memo = {}
def fib_memo(n):
    if n in memo: return memo[n]
    if n <= 1: return n
    memo[n] = fib_memo(n-1) + fib_memo(n-2)
    return memo[n]

Bottom-Up (Tabulation): fill a table from smallest sub-problems upward.

def fib_dp(n):
    if n <= 1: return n
    dp = [0] * (n + 1)
    dp[1] = 1
    for i in range(2, n + 1):
        dp[i] = dp[i-1] + dp[i-2]
    return dp[n]

# Space optimised (only need last two):
def fib_optimal(n):
    a, b = 0, 1
    for _ in range(n):
        a, b = b, a + b
    return a

When to use top-down vs bottom-up:

  • Top-down is easier to write (follow the recursion), handles sparse sub-problem spaces
  • Bottom-up is often faster (no recursion overhead, better cache behaviour), more space-efficient

Identifying a DP Problem

Two properties make a problem solvable with DP:

  1. Optimal substructure: an optimal solution contains optimal solutions to sub-problems
  2. Overlapping sub-problems: the same sub-problems are solved repeatedly in naive recursion

If a problem has both, DP applies.

Canonical DP Problems

Longest Common Subsequence (LCS):

Given two strings, find the length of their longest common subsequence (characters in order, not necessarily contiguous).

def lcs(s1, s2):
    m, n = len(s1), len(s2)
    dp = [[0] * (n+1) for _ in range(m+1)]
    for i in range(1, m+1):
        for j in range(1, n+1):
            if s1[i-1] == s2[j-1]:
                dp[i][j] = dp[i-1][j-1] + 1
            else:
                dp[i][j] = max(dp[i-1][j], dp[i][j-1])
    return dp[m][n]

lcs("ABCBDAB", "BDCAB")   # 4 (BCAB or BDAB)

Time: O(mn). Used in: diff (finding differences between files), DNA sequence alignment, version control systems.

0/1 Knapsack:

n items, each with weight w[i] and value v[i]. A bag with capacity W. Maximise total value without exceeding capacity. Each item used at most once.

def knapsack(weights, values, W):
    n = len(weights)
    dp = [[0] * (W+1) for _ in range(n+1)]
    for i in range(1, n+1):
        for w in range(W+1):
            dp[i][w] = dp[i-1][w]    # don't take item i
            if weights[i-1] <= w:
                take = dp[i-1][w - weights[i-1]] + values[i-1]
                dp[i][w] = max(dp[i][w], take)   # take item i
    return dp[n][W]

Time: O(nW) — pseudo-polynomial (polynomial in W, but W can be exponentially large).

Coin Change:

Given coin denominations and a target amount, find the minimum number of coins.

def coin_change(coins, amount):
    dp = [float('inf')] * (amount + 1)
    dp[0] = 0
    for amt in range(1, amount + 1):
        for coin in coins:
            if coin <= amt:
                dp[amt] = min(dp[amt], dp[amt - coin] + 1)
    return dp[amount] if dp[amount] != float('inf') else -1

coin_change([1, 5, 10, 25], 36)   # 3 coins: 25+10+1

Longest Increasing Subsequence (LIS):

def lis(arr):
    if not arr: return 0
    n = len(arr)
    dp = [1] * n             # each element alone is an LIS of length 1
    for i in range(1, n):
        for j in range(i):
            if arr[j] < arr[i]:
                dp[i] = max(dp[i], dp[j] + 1)
    return max(dp)

lis([10, 9, 2, 5, 3, 7, 101, 18])   # 4 (2,3,7,101 or 2,5,7,101)

O(n²) DP. There is an O(n log n) solution using binary search and patience sorting.

The DP Design Process

Step 1 — Define the sub-problem: what does dp[i] or dp[i][j] represent?

Step 2 — Write the recurrence: how does dp[i] depend on smaller sub-problems?

Step 3 — Identify base cases: what are the smallest sub-problems with known answers?

Step 4 — Determine computation order: which sub-problems must be solved before others?

Step 5 — Extract the answer: which cell(s) of the table contain the final answer?

Step 6 — Optimise space: often only the last row (or last two values) of the DP table is needed.
