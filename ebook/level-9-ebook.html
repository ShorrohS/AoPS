﻿# Module 9.1 — The Relational Model and SQL

The Problem

A company stores customer data in one file, orders in another, products in a third. To find all orders placed by customers in New York for products that are currently out of stock, you write a custom program that opens all three files, reads every line, and applies filters.

Every new question requires a new program. When the file format changes, every program breaks.

In 1970, Edgar Codd published a paper that solved all of these problems at once. The solution: a relational model — data organised as tables, accessed through a declarative language that describes what you want, not how to get it.

The Story

E.F. Codd and the Relational Revolution

Edgar Codd was a computer scientist at IBM's San Jose Research Lab. In 1970, he published "A Relational Model of Data for Large Shared Data Banks" — one of the most influential papers in computer science history.

Codd's insight: store data in relations (tables), and access it using relational algebra — a mathematical framework with operations like selection, projection, and join. The query language would be declarative: describe what data you want, let the database figure out how to retrieve it.

IBM built System R (1974–1979) to prove the concept, developing the SEQUEL query language (later renamed SQL). Don Chamberlin and Ray Boyce designed SQL to be readable by non-programmers — like English with structure.

Oracle Corporation (founded 1977 by Larry Ellison) shipped the first commercial SQL database in 1979. PostgreSQL (1986, open source), MySQL (1995, open source), SQLite (2000, embedded) followed. Today, relational databases power virtually every financial system, e-commerce platform, and enterprise application in the world.

The Concept

Tables, Rows, Columns

A relation is a table with:

  • Schema: column names and types (defined once)
  • Rows (tuples): individual records
  • Primary key: one or more columns that uniquely identify each row
CREATE TABLE users (
    id          INTEGER PRIMARY KEY,
    name        VARCHAR(100) NOT NULL,
    email       VARCHAR(255) UNIQUE NOT NULL,
    city        VARCHAR(100),
    created_at  TIMESTAMP DEFAULT NOW()
);

CREATE TABLE orders (
    id          INTEGER PRIMARY KEY,
    user_id     INTEGER REFERENCES users(id),
    amount      DECIMAL(10,2) NOT NULL,
    status      VARCHAR(20) DEFAULT 'pending',
    created_at  TIMESTAMP DEFAULT NOW()
);

A foreign key (user_id REFERENCES users(id)) enforces referential integrity: you cannot create an order for a non-existent user, and you cannot delete a user who has orders.

SQL — The Four Core Operations

SELECT — Query data:

-- Basic selection and projection
SELECT name, email FROM users WHERE city = 'New York';

-- Aggregate functions
SELECT city, COUNT(*) as user_count, AVG(amount) as avg_order
FROM users u
JOIN orders o ON u.id = o.user_id
WHERE o.status = 'completed'
GROUP BY city
HAVING COUNT(*) > 10
ORDER BY user_count DESC
LIMIT 5;

INSERT — Add data:

INSERT INTO users (name, email, city) VALUES ('Alice', 'alice@example.com', 'NYC');
INSERT INTO orders (user_id, amount) SELECT id, 99.99 FROM users WHERE city = 'NYC';

UPDATE — Modify data:

UPDATE orders SET status = 'shipped' WHERE id = 1234;
UPDATE users SET city = 'New York' WHERE city = 'NYC';  -- normalise data

DELETE — Remove data:

DELETE FROM orders WHERE created_at < NOW() - INTERVAL '1 year' AND status = 'cancelled';

JOINs — Combining Tables

The JOIN operation is the heart of relational databases:

-- INNER JOIN: only rows where condition matches in both tables
SELECT u.name, o.amount, o.status
FROM users u
INNER JOIN orders o ON u.id = o.user_id;

-- LEFT JOIN: all users, even those with no orders
SELECT u.name, COUNT(o.id) as order_count
FROM users u
LEFT JOIN orders o ON u.id = o.user_id
GROUP BY u.id, u.name;

-- Self-join: find users who share a city
SELECT a.name, b.name, a.city
FROM users a
JOIN users b ON a.city = b.city AND a.id < b.id;

Types of joins:

  • INNER JOIN: intersection — rows matching in both tables
  • LEFT JOIN: all from left table + matching from right (NULLs where no match)
  • RIGHT JOIN: all from right + matching from left
  • FULL OUTER JOIN: all rows from both tables
  • CROSS JOIN: Cartesian product — every combination (rarely used)

Normalisation — Eliminating Redundancy

First Normal Form (1NF): every column holds atomic values (no lists, no nested tables). Each row is unique.

Second Normal Form (2NF): in addition to 1NF, every non-key attribute depends on the whole primary key (no partial dependencies). Relevant when the key is composite.

Third Normal Form (3NF): in addition to 2NF, no transitive dependencies — non-key attributes do not depend on other non-key attributes.

Example — violation and fix:

-- BAD: city depends on zip, not on customer_id + order_id
orders(customer_id, order_id, customer_name, customer_zip, customer_city, product_name, quantity)

-- GOOD: separate tables, each fact stored once
customers(customer_id, name, zip, city)       -- city depends only on zip → 3NF issue
zip_codes(zip, city, state)                   -- extract the dependency
customers(customer_id, name, zip)             -- zip is FK to zip_codes
orders(order_id, customer_id, product_id, quantity)
products(product_id, name, price)

Denormalisation is sometimes done intentionally for read performance: store redundant data to avoid joins.

Indexes — Making Queries Fast

Without an index, every query scans every row (O(n)). With an index (B+tree, Module 9.2):

-- Slow: full table scan
SELECT * FROM orders WHERE user_id = 12345;

-- Add index: O(log n) lookup
CREATE INDEX idx_orders_user_id ON orders(user_id);

-- Composite index: useful for queries filtering on both columns
CREATE INDEX idx_orders_user_status ON orders(user_id, status);

-- Covering index: all queried columns in the index → no table lookup
CREATE INDEX idx_orders_covering ON orders(user_id, status, amount, created_at);

-- Check if index is being used:
EXPLAIN SELECT * FROM orders WHERE user_id = 12345;

When indexes help: equality lookups, range queries, ORDER BY, GROUP BY on indexed columns, JOINs on indexed foreign keys.

When indexes hurt: INSERT, UPDATE, DELETE are slower (must maintain all indexes), full table scans on small tables (index lookup overhead exceeds full scan cost).

Going Deeper

Query optimiser: SQL is declarative — the database engine decides how to execute it. The query optimiser generates multiple execution plans, estimates their cost (using table statistics), and chooses the cheapest. A JOIN between two tables could be executed as a nested loop (O(n×m)), hash join (O(n+m)), or sort-merge join (O(n log n + m log m)). The optimiser picks based on table sizes, available indexes, and selectivity estimates. Understanding the optimiser explains why EXPLAIN ANALYZE output is a core DBA skill.

Window functions: a powerful SQL feature for analytical queries — compute running totals, rank rows within groups, calculate moving averages, all without subqueries:

SELECT name, salary,
       RANK() OVER (PARTITION BY department ORDER BY salary DESC) as dept_rank,
       SUM(salary) OVER (PARTITION BY department) as dept_total
FROM employees;

﻿# Module 9.2 — B-Trees and Why Databases Use Them

The Problem

A database table has 100 million rows. You need to find the row where user_id = 7,482,991 in under a millisecond.

A BST (Module 6.4) gives O(log n) — about 27 comparisons. That sounds fast. But each comparison may require a disk read. A disk read takes ~10 ms. 27 disk reads × 10 ms = 270 ms per query. For 100 concurrent users: 27 seconds of disk I/O per second.

The problem is not the number of comparisons — it's the number of disk accesses. The B-tree was designed to minimise disk accesses.

The Story

Designed for Disk

Rudolf Bayer and Ed McCreight invented the B-tree at Boeing Research Labs in 1972. Their paper title: "Organization and Maintenance of Large Ordered Indexes." The context was clear: they needed a data structure for storing and searching indexes on disk, not in RAM.

The key insight: disk I/O is the bottleneck, not CPU operations. A disk read fetches an entire block (typically 4–16 KB) at once, regardless of how much data you actually need. The B-tree exploits this by storing many keys in each node — the node fills exactly one disk block. One disk read retrieves a node with hundreds of keys; binary search within that node is pure CPU work (cheap).

IBM's IMS database (1968, pre-B-tree) used VSAM (Virtual Storage Access Method) with similar ideas. Oracle, IBM DB2, PostgreSQL, MySQL/InnoDB — every major relational database uses B-trees (or the closely related B+tree variant) for their primary storage.

The Concept

B-Tree Properties

A B-tree of order t (minimum degree):

  • Every node except root has at least t-1 keys
  • Every node has at most 2t-1 keys
  • A node with k keys has k+1 children
  • All leaves are at the same depth
  • Keys within a node are sorted

For t = 100 (typical for a disk-based B-tree with 4 KB blocks):

  • Each node holds 99–199 keys
  • Each internal node has 100–200 child pointers
  • Height of a tree with 1 billion keys: log₁₀₀(10⁹) ≈ 4.5 levels → 5 disk reads maximum

Compare: a BST with 1 billion nodes has height ~30, requiring 30 disk reads.

B-Tree vs B+Tree

Almost all databases use the B+tree variant:

B-tree: keys and data records stored in all nodes (internal and leaf).

B+tree:

  • Internal nodes store only keys and child pointers (routing keys)
  • All actual data (records or record pointers) stored in leaf nodes
  • Leaf nodes are linked in a doubly-linked list

Benefits of B+tree:

  1. Internal nodes can hold more keys (no data overhead) → shorter tree → fewer disk reads
  2. Leaf linked list enables efficient range scans: WHERE age BETWEEN 25 AND 35 traverses leaf nodes sequentially
  3. All queries touch leaf nodes → more predictable access patterns

Search

def btree_search(node, key):
    # Binary search for key in node.keys
    i = bisect_left(node.keys, key)

    if i < len(node.keys) and node.keys[i] == key:
        return node.vals[i]          # found in this node

    if node.is_leaf:
        return None                  # not found

    # Recurse into appropriate child
    return btree_search(node.children[i], key)

One disk read per level traversed. For a 4-level B+tree with t=100: maximum 4 disk reads to find any record among 200 million rows.

Insertion

  1. Search to find the correct leaf node
  2. Insert the key in sorted position in the leaf
  3. If the leaf is not full (< 2t-1 keys): done
  4. If the leaf is full: split it:
    • Create two nodes, each with ~half the keys
    • Promote the middle key to the parent
    • If parent is also full, split the parent recursively
    • If root splits, create a new root → tree height increases by 1

The only way a B-tree grows taller is when the root splits. All leaves remain at the same depth — the tree is always balanced.

Deletion

More complex:

  1. Find the key to delete
  2. If in a leaf: remove it
  3. If in an internal node: replace with in-order successor (from leaf), delete from leaf
  4. If deletion causes underflow (< t-1 keys):
    • Try to borrow from a sibling (redistribute keys via parent)
    • If sibling is at minimum too: merge with sibling + pull down parent key
    • Merging may propagate up to the root; if root becomes empty, tree shrinks

Database Index Implementation

In PostgreSQL, MySQL's InnoDB, and SQLite:

Clustered index (InnoDB's primary key): the actual table data is stored in the B+tree leaf nodes, ordered by the primary key. One disk read at leaf level = the actual row data.

Secondary index: leaf nodes store the primary key value (not the row data). To retrieve the full row: look up the secondary index B+tree to get the primary key, then look up the clustered B+tree. Two B+tree lookups per secondary index query (unless using a covering index).

-- This uses the name index (secondary index B+tree)
-- then the primary key B+tree to get the full row
SELECT * FROM users WHERE name = 'Alice';

-- This uses only the name index (covering index)
-- All needed columns are in the leaf nodes
SELECT id, name FROM users WHERE name = 'Alice';

Why Not Hash Tables for Databases?

Hash tables give O(1) lookup — faster than B+trees O(log n). So why do databases use B+trees?

  1. Range queries: WHERE price BETWEEN 10 AND 50 — hash tables are useless for ranges; B+trees handle them in O(log n + k)
  2. Ordering: ORDER BY name — B+tree traversal produces sorted order; hash tables don't
  3. Prefix queries: WHERE name LIKE 'Ali%' — B+trees handle prefix scans; hash tables don't
  4. Predictable worst case: hash tables have O(n) worst case; B+trees are always O(log n)

Databases do use hash indexes for equality-only lookups where ranges aren't needed (PostgreSQL has hash indexes). But the B+tree is the universal default because it supports everything.

Going Deeper

Write amplification: database writes to B-trees cause significant write amplification — a single row insert may require reading and rewriting multiple B-tree nodes. LSM-trees (Log-Structured Merge-trees), used in RocksDB, Cassandra, and LevelDB, trade write amplification for read amplification: writes are always sequential appends (fast on SSDs), reads merge multiple sorted runs. Understanding B-tree vs LSM-tree is fundamental to database internals.

Fractional cascading: a technique to speed up searches in multiple sorted lists by maintaining links between lists at matching keys. Reduces multi-list search from O(k log n) to O(log n + k). Used in range trees and priority search trees for multi-dimensional spatial queries.

﻿# Module 9.3 — Transactions, ACID, and Isolation

The Problem

Two people simultaneously book the last seat on a flight. Both checks show the seat is available. Both bookings succeed. Two passengers arrive, one seat exists.

A bank transfers £100 from account A to account B. The system crashes after deducting from A but before adding to B. £100 vanishes.

These are concurrency and durability problems in databases. Transactions and ACID properties exist specifically to prevent them.

The Story

The Problem of Bank Transfers

The canonical example of why transactions exist: a funds transfer. Conceptually: UPDATE accounts SET balance = balance - 100 WHERE id = 1 followed by UPDATE accounts SET balance = balance + 100 WHERE id = 2. These are two separate operations. Without transactions, a crash between them leaves the database in an inconsistent state — money lost.

Jim Gray formalised transaction processing in the 1970s while at IBM working on System R. His 1981 paper "The Transaction Concept: Virtues and Limitations" defined the ACID properties. Gray received the Turing Award in 1998 for his work on transaction processing and database systems.

The ideas from Gray's work are now universal: every relational database, most NoSQL databases, and many distributed systems implement some form of transactional guarantees.

The Concept

ACID Properties

Atomicity: a transaction either completes entirely or has no effect. No partial execution. "All or nothing."

BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;   -- both updates persist
-- If crash occurs before COMMIT: neither update persists (rollback)

Consistency: a transaction takes the database from one valid state to another. All integrity constraints (foreign keys, check constraints, unique constraints) hold after every committed transaction.

Isolation: concurrent transactions behave as if they executed serially. One transaction's intermediate state is invisible to others.

Durability: once committed, a transaction's effects survive crashes. Achieved via write-ahead logging (WAL): changes are written to a durable log before being applied to data pages.

The Write-Ahead Log (WAL)

Before any data page is modified, the change is recorded in the WAL (also called redo log in MySQL, journal in SQLite):

LSN 1001: BEGIN TRANSACTION txn#42
LSN 1002: UPDATE accounts SET balance=900 WHERE id=1  [old=1000, new=900]
LSN 1003: UPDATE accounts SET balance=200 WHERE id=2  [old=100,  new=200]
LSN 1004: COMMIT txn#42

On crash recovery:

  • WAL entries with COMMIT are replayed (redo): any changes not yet on disk are re-applied
  • WAL entries without COMMIT are rolled back (undo): any partial changes are reversed

The WAL is append-only — the fastest possible write pattern on both HDDs and SSDs.

Isolation Levels and Concurrency Anomalies

Perfect isolation is expensive — it requires full serialisation. Most databases offer weaker isolation levels for better performance:

Read Uncommitted: a transaction can read uncommitted changes from other transactions. → Allows dirty reads: read data that another transaction will roll back.

Read Committed (PostgreSQL default): only committed data is visible. → Prevents dirty reads. Allows non-repeatable reads: re-reading the same row yields different results if another transaction committed between reads.

Repeatable Read (MySQL InnoDB default): all reads within a transaction see a consistent snapshot from transaction start. → Prevents dirty reads and non-repeatable reads. Allows phantom reads: a range query executed twice may return different rows if another transaction inserted rows matching the range.

Serializable: full isolation — transactions execute as if sequential. → Prevents all anomalies. Most expensive. Uses locks or MVCC + predicate locking.

MVCC — Multi-Version Concurrency Control

Most modern databases (PostgreSQL, Oracle, MySQL InnoDB) use MVCC rather than locks for read isolation:

  • Each row has a transaction ID range indicating which transactions can see it
  • When a transaction starts, it gets a snapshot timestamp
  • Reads see the latest version of each row committed before the transaction's snapshot
  • Writes create a new version of the row rather than modifying in-place
  • Old versions are cleaned up by a background process (VACUUM in PostgreSQL)

Benefits:

  • Readers never block writers, writers never block readers
  • Long-running queries don't stall updates

Costs:

  • Extra storage for multiple versions
  • Vacuum/cleanup overhead

Deadlocks in Databases

-- Session 1                  -- Session 2
BEGIN;                         BEGIN;
UPDATE accounts                UPDATE accounts
  SET bal=bal-100              SET bal=bal-100
  WHERE id=1;                  WHERE id=2;   -- acquires lock on row 2
                               UPDATE accounts
                                 SET bal=bal+100
                                 WHERE id=1; -- waits for lock on row 1
UPDATE accounts
  SET bal=bal+100
  WHERE id=2;  -- waits for    -- DEADLOCK
  lock on row 2

The database detects deadlocks (cycle in the wait-for graph) and aborts one transaction with an error. The application should retry the aborted transaction.

Lock ordering prevents deadlocks: always acquire locks in the same order. Many applications implement this by sorting the rows to update by primary key before executing.

Two-Phase Commit (2PC)

For distributed transactions spanning multiple databases:

Phase 1 (Prepare): coordinator asks all participants "are you ready to commit?" Each participant flushes its changes to WAL and responds "yes/no."

Phase 2 (Commit/Abort): if all said yes, coordinator sends COMMIT to all. If any said no, sends ROLLBACK to all.

2PC provides distributed ACID but is blocking: if the coordinator crashes after phase 1, participants hold locks indefinitely. Modern distributed databases (Google Spanner, CockroachDB) use Paxos/Raft for fault-tolerant distributed transactions.

Going Deeper

Serializable Snapshot Isolation (SSI): PostgreSQL's serializable isolation uses SSI — detecting serialisation conflicts at commit time rather than blocking immediately. This allows much higher concurrency than traditional 2PL (two-phase locking) while still guaranteeing full serializability. The key insight: track read-write conflicts between transactions and abort any that could produce a non-serializable outcome.

BASE vs ACID: many NoSQL databases (Cassandra, DynamoDB, MongoDB) relax ACID for higher availability and performance. BASE (Basically Available, Soft state, Eventually consistent) allows replicas to temporarily diverge — reads may return stale data, but the system converges to consistency eventually. Understanding the CAP theorem (Consistency, Availability, Partition tolerance: choose two) is essential for distributed database design.

﻿# Module 9.4 — Building a Toy SQL Engine

The Problem

SQL is a declarative language: you describe what you want. Someone has to figure out how to get it.

That someone is the SQL engine — the software that takes your query, parses it, plans an execution strategy, and retrieves the data.

Building a minimal SQL engine from scratch is one of the most educational programming projects in computer science. It requires understanding: parsing, query planning, B-tree indexes, join algorithms, aggregation, and storage formats.

The Story

SQLite — The World's Most Deployed Database

D. Richard Hipp wrote SQLite in 2000 for use on US Navy destroyers — embedded systems that needed a database without a server. SQLite is serverless, zero-configuration, and self-contained in a single ~750 KB C file.

Today, SQLite is embedded in: every Android device, every iOS device, every Mac and Windows machine, every Firefox browser, every Chrome browser. Over one trillion SQLite databases are in active use. It is almost certainly the most widely deployed software library in history.

SQLite's source code is public domain and is one of the best-documented database implementations ever written. Reading it is a masterclass in systems programming.

Our toy engine will be a fraction of SQLite's complexity but will hit the same fundamental concepts: parsing SQL text, executing against an in-memory table store, and producing results.

The Concept

The SQL Engine Pipeline

      ↓ Tokeniser (Lexer)

      ↓ Parser

Step 1: Tokeniser

import re

def tokenise(sql):
    token_patterns = [
        ('KEYWORD',  r'\b(SELECT|FROM|WHERE|INSERT|INTO|VALUES|UPDATE|SET|DELETE|AND|OR|NOT|CREATE|TABLE|INT|TEXT|PRIMARY|KEY|JOIN|ON|AS)\b'),
        ('NUMBER',   r'\d+(\.\d+)?'),
        ('STRING',   r"'[^']*'"),
        ('IDENT',    r'[a-zA-Z_][a-zA-Z0-9_]*'),
        ('OP',       r'[=<>!]+|[,;()*]'),
        ('WHITESPACE', r'\s+'),
    ]
    combined = '|'.join(f'(?P<{name}>{pattern})' for name, pattern in token_patterns)
    tokens = []
    for m in re.finditer(combined, sql, re.IGNORECASE):
        if m.lastgroup != 'WHITESPACE':
            tokens.append((m.lastgroup, m.group()))
    return tokens

tokenise("SELECT name, age FROM users WHERE id = 5")
# [('KEYWORD','SELECT'), ('IDENT','name'), ('OP',','), ('IDENT','age'),
#  ('KEYWORD','FROM'), ('IDENT','users'), ('KEYWORD','WHERE'),
#  ('IDENT','id'), ('OP','='), ('NUMBER','5')]

Step 2: Parser — Building an AST

class Parser:
    def __init__(self, tokens):
        self.tokens = tokens
        self.pos    = 0

    def peek(self): return self.tokens[self.pos] if self.pos < len(self.tokens) else None
    def consume(self): t = self.tokens[self.pos]; self.pos += 1; return t
    def expect(self, kind, val=None):
        t = self.consume()
        if t[0] != kind or (val and t[1].upper() != val.upper()):
            raise SyntaxError(f"Expected {kind} {val}, got {t}")
        return t

    def parse_select(self):
        self.expect('KEYWORD', 'SELECT')
        columns = self.parse_column_list()
        self.expect('KEYWORD', 'FROM')
        table = self.consume()[1]
        where  = None
        if self.peek() and self.peek()[1].upper() == 'WHERE':
            self.consume()
            where = self.parse_condition()
        return {'type': 'SELECT', 'columns': columns, 'table': table, 'where': where}

    def parse_column_list(self):
        cols = []
        t = self.peek()
        if t and t[1] == '*': self.consume(); return ['*']
        cols.append(self.consume()[1])
        while self.peek() and self.peek()[1] == ',':
            self.consume(); cols.append(self.consume()[1])
        return cols

    def parse_condition(self):
        left  = self.consume()[1]
        op    = self.consume()[1]
        right = self.consume()[1].strip("'")
        return {'left': left, 'op': op, 'right': right}

Step 3: In-Memory Storage Engine

class Table:
    def __init__(self, name, schema):
        # schema: [(col_name, col_type), ...]
        self.name   = name
        self.schema = schema
        self.rows   = []       # list of dicts
        self.next_id = 1

    def insert(self, row_dict):
        if 'id' not in row_dict:
            row_dict['id'] = self.next_id; self.next_id += 1
        self.rows.append(row_dict)

    def scan(self):
        return iter(self.rows)

class Database:
    def __init__(self):
        self.tables = {}

    def create_table(self, name, schema):
        self.tables[name] = Table(name, schema)

    def get_table(self, name):
        if name not in self.tables:
            raise NameError(f"Table '{name}' not found")
        return self.tables[name]

Step 4: Executor

def evaluate_condition(row, cond):
    if cond is None: return True
    left_val  = row.get(cond['left'])
    right_val = cond['right']
    # Try numeric comparison
    try: left_val = float(left_val); right_val = float(right_val)
    except (TypeError, ValueError): pass
    ops = {'=': lambda a,b: a==b, '!=': lambda a,b: a!=b,
           '<': lambda a,b: a<b,  '>': lambda a,b: a>b,
           '<=':lambda a,b: a<=b, '>=':lambda a,b: a>=b}
    return ops[cond['op']](left_val, right_val)

def execute(db, ast):
    if ast['type'] == 'SELECT':
        table = db.get_table(ast['table'])
        results = []
        for row in table.scan():
            if evaluate_condition(row, ast['where']):
                if ast['columns'] == ['*']:
                    results.append(dict(row))
                else:
                    results.append({c: row.get(c) for c in ast['columns']})
        return results

    if ast['type'] == 'INSERT':
        table = db.get_table(ast['table'])
        row = dict(zip(ast['columns'], ast['values']))
        table.insert(row)
        return [{'affected': 1}]

Step 5: Tying It Together

def query(db, sql):
    tokens = tokenise(sql)
    parser = Parser(tokens)
    keyword = tokens[0][1].upper()
    if keyword == 'SELECT':
        ast = parser.parse_select()
    elif keyword == 'INSERT':
        ast = parser.parse_insert()
    else:
        raise NotImplementedError(f"Unsupported: {keyword}")
    return execute(db, ast)

    results = []
    for key, rows in groups.items():
        count = len(rows)
        if having_count is None or count > having_count:
            results.append({group_col: key, 'count': count})

    return results
▸ Part C.8 — hash join
def hash_join(left_rows, right_rows, left_key, right_key):
    # Phase 1: build hash table from smaller (left) table
    ht = defaultdict(list)
    for row in left_rows:
        ht[row[left_key]].append(row)

    # Phase 2: probe
    results = []
    for row in right_rows:
        for match in ht.get(row[right_key], []):
            results.append({**match, **row})

    return results

Nested loop: 1000 × 50,000 = 50,000,000 comparisons. Hash join: 1000 inserts + 50,000 lookups = 51,000 operations. ~1000× fewer.
